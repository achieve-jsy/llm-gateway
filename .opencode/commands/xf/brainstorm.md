针对一个新需求进行头脑风暴，发散探索后自动进入澄清确认，完成需求规范。

适用于需求非常模糊、完全没概念的情况。如果需求已经大致清楚，可直接使用 `/xf/clarify`。

## 用户输入

```
$ARGUMENTS
```

如果用户提供了需求描述，以此作为起点；否则要求用户描述想法。

## 前置条件

- `xspec/constitution.md` 必须存在
- `xspec/modules/PRODUCT.md` 必须存在且包含模块结构
- **结构不变量校验（硬停）**：执行 `node .xflow/scripts/xf-check-invariants.mjs`。如退出码非 0，**必须立即终止本命令**，把脚本输出的诊断报告原样转发给用户后结束（不搜索、不分析、不试图绕过）：
  ```
  ❌ 结构不变量违反：<脚本输出的报告>

  请按报告建议修复后重试。
  ```
- **phase 入口校验（硬停）**：执行 `node .xflow/scripts/xf-check-phase.mjs --command brainstorm`。如退出码非 0，**必须立即终止本命令**，把脚本输出的诊断报告原样转发给用户后结束（不搜索、不分析、不试图绕过；尤其禁止把新模块"并入"已经进入 design / detail / task / implement 的活跃变更）：
  ```
  ❌ phase 入口不合法：<脚本输出的报告>

  请按报告建议处理后重试。
  ```

## 步骤 0：Profile 分支加载（始终先于其他步骤执行）

1. 执行 `node .xflow/scripts/xf-profile.mjs --value-only` 读取当前 `project_profile`
2. 显眼打印一行：`📌 project_profile = <profile>`
3. 如果 `.xflow/profiles/<profile>/brainstorm.md` 存在，**读取该文件**并作为本次运行的行为覆写规则优先执行：
   - 指令 `终止整条命令` → 按方言固定输出打印并结束，**不执行下文任何步骤**
   - 指令 `跳过 <步骤>` → 执行到该步骤时直接跳过
   - 指令 `替换 <步骤>` → 改用方言文件中的替代内容（收敛阶段常用）
   - 指令 `追加 <位置>` → 在该位置附加方言文件的内容
4. 方言文件不存在或 profile 为 `general` 时，按下文通用流程执行

> 原则：本文件只维护通用逻辑；领域方言统一在 `.xflow/profiles/<profile>/` 下管理。**禁止**在本文件硬编码 `if profile == xxx` 分支。

## 第一阶段：头脑风暴（发散）

### 步骤 1：加载上下文

1. 读取 `xspec/constitution.md` 了解项目原则和约束
2. 读取 `xspec/modules/PRODUCT.md` 了解产品定位、模块结构和现有功能
3. 扫描 `xspec/modules/` 了解已有模块

### 步骤 1.5：制品要点摘要（强制，先于发散提问）

在向用户发起发散式提问之前，必须先输出**简短摘要**（各 3-8 条要点，只摘与本次需求可能相关的部分）：

1. **`constitution.md`**：与本需求可能相关的原则与约束。
2. **`PRODUCT.md`**：定位、目标用户/角色、产品级边界、相关模块。

**硬规则（第一阶段也必须遵守）**：

- **禁止**在发散阶段用「项目级」问题让用户重复描述已在宪章/PRODUCT 中写清的内容（例如「产品是干什么的」「目标用户是谁」）。
- **允许**的发散提问应围绕：**本需求本身**、理想体验、参考案例、开放联想；若涉及用户/场景，应建立在摘要已列的 PRODUCT 结论之上（例如「在已定位 [X 用户] 的前提下，这个功能上你还有哪些担心或想象？」）。
- 若用户口述与制品冲突，温和标出并请其选择以何者为准，而不是假装制品不存在。

### 步骤 2：引导发散（保留苏格拉底式开放式探索）

以开放式问题引导用户自由思考，**不做判断、不否定**（**本阶段**适合苏格拉底式发散，与 `/xf/clarify` 的差量结构化风格区分）：

- "关于这个需求，你脑海中还有哪些相关的想法？"
- "这个功能的理想状态是什么样的？"
- "有没有类似的产品或功能可以参考？"
- "如果没有任何限制，你最希望它是什么样的？"

记录所有想法，不做筛选。如有想法明显违反宪章原则，温和提醒但不阻断。

如某个方向涉及**技术可行性存疑**（如"不确定这个技术能不能做"），可使用 `xf-research` subagent 快速验证可行性，避免在不可行的方向上浪费发散精力。

### 步骤 3：整理发散结果

当用户表示想法已充分时，整理头脑风暴结果：

1. 按「功能方向」「用户场景」「参考案例」「开放问题」分类归纳
2. 初步标注哪些方向最值得深入

### 步骤 4：生成 brainstorm.md

1. 在 `xspec/changes/` 下生成 `brainstorm.md`
2. 基于 `.xflow/templates/_shared/brainstorm.md` 模板填充实际内容

## 第二阶段：自动澄清确认

头脑风暴完成后，自动进入澄清确认环节（用户无需再手动执行 `/xf/clarify`）。

### 步骤 5：收敛与需求确认（与 `/xf/clarify` 步骤 2 同节奏）

**说明**：开放式引导**仅保留在第一阶段发散**；收敛阶段采用**差量结构化**，且与 `clarify.md` **步骤 2.0** 完全一致：

- **最多 5 个**实质问题、**一次只展示一题**、**选择题（2–5 项 + 推荐项）或极短答（≤15 汉字 / `是`/`推荐`/`采纳`）**、题内纠偏不占新题、用户可早停、不剧透后续题目。

必要时用 1-2 句**重申**步骤 1.5 的制品要点即可，勿冗长复述。

**内部建议顺序**（合计仍 ≤5 题，按需跳过低优先级）：

1. **聚焦方向**（必占 1 题）：整理头脑风暴方向 ①②③… 后，用**一题**选择题让用户选定本次聚焦组合或优先级（可含「推荐：选项 X」）。
2. **变更级边界与验收**（占 0–3 题）：**每一子点单独一题**，禁止把「输入输出 / 不做 / 衡量标准」拼在同一则消息里。内容须相对 PRODUCT 为**差量**（不重复产品级已写边界）。
3. **模块影响确认**（必占 1 题）：写法与 `clarify.md` **步骤 2.3** 相同（先陈述建议划分，再 A 同意 / B 需调整）。

若差量题与 5 题上限冲突，**优先保留模块确认题**，并砍掉影响最低的差量题。

如需求涉及 `PRODUCT.md` 中不存在的模块，提醒用户后续需通过 `/xf/split` 更新模块结构。

### 步骤 6：生成产物

用户确认后：

1. 按 `.xflow/templates/_shared/change.yaml` 模板生成 `xspec/changes/change.yaml`（**绝对路径从仓库根起算，禁止省略 `xspec/` 前缀，否则会在项目根目录误建 `changes/` 目录**），确保：
   - `status` 设为 `"in-progress"`，`phase` 设为 `"clarify"`
   - 填写 `scope.include` / `scope.exclude`（功能范围边界）
   - 填写所有 `affected_modules`（含 `change_type`、`module_type`、`summary`）
2. 按 `change_type` 为每个受影响模块生成需求规范（路径同样从 `xspec/` 起算）：
   - `change_type: added`（新增模块）→ 生成 `xspec/changes/<name>/spec.md`（完整需求规范）
   - `change_type: modified`（变更模块）→ 先读取 `xspec/modules/<name>/spec.md` 和 `module.yaml` 了解现状及版本，生成 `xspec/changes/<name>/spec.delta.md`（增量需求变更，格式见 `/xf/clarify` 中的 spec.delta.md 格式定义）
3. 对新模块执行骨架创建：
   ```bash
   node .xflow/scripts/xf-scaffold.mjs --module <module-name> --type <module_type>
   ```

## 步骤 6.5：Spec 内容质量检查（强制，在脚本自检之前）

写完 spec.md / spec.delta.md 后，立即逐项检查：

1. **无技术实现泄漏**：功能描述中不出现框架名、库名、API 路径、表名
2. **验收标准完整**：每条 AC 都有完整的 Given/When/Then 三要素
3. **验收标准可衡量**：不含模糊词（等、若干、适当、合理、正常、部分）
4. **成功指标技术无关**：不提及具体技术组件（数据库、缓存、CDN 等）
5. **用户故事有优先级**：每个 US 都标注了 P0/P1/P2
6. **边界场景不为空**：每个功能至少列出 2 个异常/边界情况
7. **[待确认] 标记上限**：整个 spec 中 [待确认] 不超过 3 处

发现问题则**立即修复并重新检查该项**（不等到步骤 7），最多 2 轮。

---

## 步骤 7：产出自检（强制）

1. 执行脚本验证：
   ```bash
   node .xflow/scripts/xf-validate.mjs --phase clarify
   ```

2. 如果 `pass: false`：
   - 逐个修复 `failures` 中的问题
   - 重新执行脚本验证
   - 最多修复 3 轮；仍不通过则在完成报告中列出未解决项及原因

3. 脚本通过后，读取 `.xflow/validate-rules.yaml` 中 `clarify` phase 的 `semantic_checks` 清单，
   逐项执行语义检查。按 `target` 找检查对象，按 `basis` 找判定依据，按 `fail_condition` 判定。
   输出结构化逐项报告：
   ```
   [PASS/FAIL] <name> — <具体说明>
   ```
   发现 FAIL 则修复后重新检查该项。

4. 全部通过后输出完成报告

## 输出产物

- `xspec/changes/brainstorm.md`（发散记录）
- `xspec/changes/change.yaml`（变更元数据 + 功能范围边界）
- `xspec/changes/<module>/spec.md`（新增模块的完整需求规范）
- `xspec/changes/<module>/spec.delta.md`（变更模块的增量需求变更）
- `xspec/changes/<module>/`（新模块骨架文件）

## 行为规则

- 需要用户做选择时，遵循 CLAUDE.md 全局交互规则（选项式 + 推荐 + 最小化）
- 第一阶段**纯发散**：不做判断、不收敛、不确认需求范围；**必须先完成步骤 1.5** 再开始发散提问
- 第一阶段**苏格拉底式**；第二阶段**结构化差量确认**，且遵守**最多 5 题、一次一题、选择题/极短答**（与 `clarify.md` 步骤 2.0 一致）
- 鼓励用户自由表达，记录所有想法
- **禁止**重复追问宪章/PRODUCT 已写清的项目级事实；收敛阶段只补缺与确认
- 宪章违规仅温和提醒
- 模块影响确认以 PRODUCT.md 为基准
- 技术可行性存疑时可使用 `xf-research` subagent 快速验证（非强制）
- 所有输出使用中文
