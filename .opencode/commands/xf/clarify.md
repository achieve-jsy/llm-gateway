## 步骤 1.5：制品要点摘要（强制，先于任何追问）

在第一次向用户提问之前，必须输出一段**简短摘要**（各 3-8 条要点即可，只摘与本次需求可能相关的部分）：

1. **来自 `constitution.md`**：核心原则、技术方向、不可违背约束（引用原文短语或短句，勿冗长照抄）。
2. **来自 `PRODUCT.md`**：产品定位、目标用户/角色、产品级边界（做什么/不做什么）、模块结构中与本次相关的模块。

**硬规则（必须遵守）**：

- **禁止**用开放式问题让用户重复描述已在上述制品中写清的内容（例如不要再泛泛问「目标用户是谁」「产品是干什么的」）。
- **允许**在以下情况追问：① 用户本次输入与制品**不一致**需对齐；② 需要确认制品中的结论**是否仍适用于本变更**；③ 需要**功能级/变更级**细化（例如：相对 PRODUCT 中的用户画像，本功能主要覆盖哪条路径或哪类角色）。
- 若某方向在制品中已有答案，应写为**陈述 + 请确认是否仍适用**，而不是假装不知道从头问。

## 步骤 2：差量澄清（逐题交互，最少提问）

### 2.0 问题预算与筛选（强制）

- **实质问题上限**：整场**最多 3 个**需要用户作答的实质问题（不含步骤 1.5 摘要、不含步骤 3 的最终确认段落）。
- **一次只展示一题**：每一则回复里**只允许有 1 个**待用户回答的实质问题。
- **答法强约束**（每题必须二选一形态）：
  - **选择题**：**2–3 个**互斥选项（A/B/C）。文首写 **`推荐：选项 X — 理由（1–2 句）`**，下方用 Markdown 表格列出「选项 | 说明」。通过平台原生选择工具呈现（见 CLAUDE.md 全局交互规则）。
  - **极短答**：若不适合选题型，写 **`建议：〈你的提议〉— 理由（1–2 句）`**，并要求用户用**不超过 15 个汉字**作答；用户也可回复 **`是`** / **`采纳`** 表示接受建议答案。
- **题内纠偏**：用户对当前题答得含糊时，可在**同一题**内追问 1 次，**不计**为新的一题。
- **早停**：用户说「够了」「没有」「跳过」「进总结」等，**立即停止**后续排队问题，进入步骤 3。
- **不剧透**：不要列出「接下来还会问…」的后续题目清单。

### 2.1 问题筛选（不展示给用户，强制执行）

在发出**第一题**之前，先识别所有候选缺口，然后**严格过滤**：

**以下问题禁止询问用户（AI 自主决策并记录理由）**：
- **技术实现细节**：存储方案、错误处理策略、缓存策略、日志范围等 → 留给 `/xf/design` 和 `/xf/detail` 阶段
- **宪章已有答案**：宪章核心原则或技术方向已明确约束的 → 直接采用宪章结论
- **PRODUCT.md 已有答案**：产品边界、目标用户等已写清的 → 不重复问
- **有合理默认值**：行业惯例或常见做法可以覆盖的 → 采用默认值并记录

**仅保留以下类型的问题**：
- **功能范围歧义**：用户描述的需求存在多种理解，影响做什么/不做什么
- **业务优先级**：多个功能点之间的优先级不明确
- **模块影响确认**：本次变更涉及哪些模块（固定占最后 1 题，见 2.3）

过滤后，**差量补缺题最多 2 道** + **模块影响确认 1 道** = 合计不超过 3 道。若判断**无高影响缺口**，差量题可为 0 道，仅发模块确认 1 题。

### 2.2 逐题循环

每收到上一题的有效答案后，用**一两句话**工作记忆当前结论，再发下一题；直到：队列为空、或已达 3 题、或用户早停。

### 2.3 模块影响确认（必占 1 题，通常放最后）

基于 `PRODUCT.md` 的模块列表，先陈述你建议的划分，再**同一题内**用选择题收束：

> ⚠️ **added vs modified 客观判据（务必先按此分类，再展示给用户）**：
>
> - 仅当 `xspec/modules/<name>/spec.md` **物理存在** 时，该模块才算 `modified`
> - 否则一律视为 `added`（即便 PRODUCT.md "模块列表"里已注册并标"规划中"，也是 added——
>   因为还没有 spec.md 基线可供 delta 引用）
>
> **禁止**仅凭 PRODUCT.md 中模块名是否出现来判断 added/modified——PRODUCT.md 的"规划中"
> 状态意味着该模块尚未物化（无 spec.md），首次为它撰写规范就是 added。

```
基于需求分析，我建议本次变更涉及：

新增模块（added，xspec/modules/<name>/spec.md 不存在）：
  - <module-a> (web-backend)：[一句话描述]

变更模块（modified，xspec/modules/<name>/spec.md 已存在）：
  - <module-b> (web-frontend)：[影响说明]

> 模块类型参考 `.xflow/templates/CATALOG.md`（类型导读）；查看当前已注册类型可执行 `node .xflow/scripts/xf-manifest.mjs --list-types`

模块依赖影响（如有）：
  - <module-b> → <module-a>
```

**推荐：选项 A — 理由（1–2 句）**

| 选项 | 说明 |
| :--- | :--- |
| A | 同意上述模块划分 |
| B | 需调整（极短说明改哪条） |

如需求涉及 `PRODUCT.md` 中不存在的模块，选项中须包含「需先 `/xf/split`」类提示，或先提醒执行 split 再澄清。

## 需求确认摘要

- [明确排除的内容]

## 步骤 4：生成产物

用户确认后：

1. 按 `.xflow/templates/_shared/change.yaml` 模板生成 `xspec/changes/change.yaml`（**绝对路径从仓库根起算，禁止省略 `xspec/` 前缀，否则会在项目根目录误建 `changes/` 目录**），确保：
   - `status` 设为 `"in-progress"`，`phase` 设为 `"clarify"`
   - 填写 `scope.include` / `scope.exclude`（功能范围边界）
   - 填写所有 `affected_modules`（含 `change_type`、`module_type`、`summary`）
   - **`change_type` 严格按步骤 2.3 客观判据填写**（看 `xspec/modules/<name>/spec.md` 是否物理存在），
     **不要**根据 PRODUCT.md 中的注册情况推断
2. 按 `change_type` 为每个受影响模块生成需求规范（路径同样从 `xspec/` 起算）：
   - `change_type: added`（新增模块）→ 生成 `xspec/changes/<name>/spec.md`（完整需求规范）
   - `change_type: modified`（变更模块）→ 先读取 `xspec/modules/<name>/spec.md` 和 `module.yaml` 了解现状及版本，生成 `xspec/changes/<name>/spec.delta.md`（增量需求变更，格式见下方）
3. **仅对 `change_type: added` 的模块**执行骨架创建（modified 模块**不要**调用 scaffold，
   delta 文件由本步第 2 项 AI 自己撰写就够了；scaffold 在 modified 入参时会 no-op，但不应依赖它兜底）：
   ```bash
   node .xflow/scripts/xf-scaffold.mjs --module <module-name> --type <module_type>
   ```
   > 历史教训：曾经因为这条不区分 added/modified，对 modified 模块也跑了 scaffold，结果在
   > `changes/<name>/` 下同时出现 `spec.delta.md`（AI 写的）和 `spec.md`/`hld.md`/...（scaffold 铺的），
   > 形成歧义。务必按 added/modified 分类执行。

### spec.delta.md 格式

```markdown
# [模块名] 需求变更 — [变更ID]

> 基线：xspec/modules/<name>/spec.md (v<version>)

## 变更摘要
[一句话描述本次需求变更核心内容]

## 新增需求
- [新增的功能点/用户故事]

## 修改需求
- [原需求引用] → [修改后的内容]

## 新增验收标准
- [新增的 AC]

## 修改验收标准
- [原 AC 引用] → [修改后的内容]
```

## 步骤 4.5：Spec 内容质量检查（强制，在脚本自检之前）

写完 spec.md / spec.delta.md 后，立即逐项检查：

1. **无技术实现泄漏**：功能描述中不出现框架名、库名、API 路径、表名
2. **验收标准完整**：每条 AC 都有完整的 Given/When/Then 三要素
3. **验收标准可衡量**：不含模糊词（等、若干、适当、合理、正常、部分）
4. **成功指标技术无关**：不提及具体技术组件（数据库、缓存、CDN 等）
5. **用户故事有优先级**：每个 US 都标注了 P0/P1/P2
6. **边界场景不为空**：每个功能至少列出 2 个异常/边界情况
7. **[待确认] 标记上限**：整个 spec 中 [待确认] 不超过 3 处

发现问题则**立即修复并重新检查该项**（不等到步骤 5），最多 2 轮。

## 步骤 5：产出自检（强制）

1. 执行脚本验证：
   ```bash
   node .xflow/scripts/xf-validate.mjs --phase clarify
   ```

2. 如果 `pass: false`：
   - 逐个修复 `failures` 中的问题
   - 重新执行脚本验证
   - 最多修复 3 轮；仍不通过则在完成报告中列出未解决项及原因

3. 脚本通过后，读取 `.xflow/validate-rules.yaml` 中 `clarify` phase 的 `semantic_checks` 清单，
   逐项执行语义检查。按 `target` 找检查对象，按 `basis` 找判定依据，按 `fail_condition` 判定。
   输出结构化逐项报告：
   ```
   [PASS/FAIL] <name> — <具体说明>
   ```
   发现 FAIL 则修复后重新检查该项。

4. 全部通过后输出完成报告

## 行为规则

- 所有交互使用中文
- 需要用户做选择时，遵循 CLAUDE.md 全局交互规则（选项式 + 推荐 + 最小化）
