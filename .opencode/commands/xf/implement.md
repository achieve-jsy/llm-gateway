按任务清单执行代码实现。

## 用户输入

```
$ARGUMENTS
```

用户可选指定任务范围（如 `T001-T005` 或 `阶段1`）。

## 前置条件

- `xspec/constitution.md` 必须存在
- 模块内 `task.md` 必须存在
- `xspec/changes/change.yaml` 的 phase 为 `task` 或 `implement`
- **结构不变量校验（硬停）**：执行 `node .xflow/scripts/xf-check-invariants.mjs`。如退出码非 0，**必须立即终止本命令**，把脚本输出的诊断报告原样转发给用户后结束（不搜索、不分析、不试图绕过）：
  ```
  ❌ 结构不变量违反：<脚本输出的报告>

  请按报告建议修复后重试。
  ```
- **phase 入口校验（硬停）**：执行 `node .xflow/scripts/xf-check-phase.mjs --command implement`。如退出码非 0，**必须立即终止本命令**，把脚本输出的诊断报告原样转发给用户后结束（不搜索、不分析、不试图绕过）：
  ```
  ❌ phase 入口不合法：<脚本输出的报告>

  请按报告建议处理后重试。
  ```

## 步骤 0：Profile 分支加载（始终先于其他步骤执行）

1. 执行 `node .xflow/scripts/xf-profile.mjs --value-only` 读取当前 `project_profile`
2. 显眼打印一行：`📌 project_profile = <profile>`
3. 如果 `.xflow/profiles/<profile>/implement.md` 存在，**读取该文件**并作为本次运行的行为覆写规则优先执行：
   - 指令 `终止整条命令` → 按方言固定输出打印并结束，**不执行下文任何步骤**
   - 指令 `跳过 <步骤>` → 执行到该步骤时直接跳过（例如 xuanwu-activity 下跳过步骤 7 跨模块集成任务）
   - 指令 `替换 <步骤>` → 改用方言文件中的替代内容（例如 xuanwu-activity 下替换步骤 3 为调用 code-generator SKILL）
   - 指令 `追加 <位置>` → 在该位置附加方言文件的内容
4. 方言文件不存在或 profile 为 `general` 时，按下文通用流程执行

> 原则：本文件只维护通用逻辑；领域方言统一在 `.xflow/profiles/<profile>/` 下管理。**禁止**在本文件硬编码 `if profile == xxx` 分支。
> 门禁边界：方言的覆写动词**仅作用于步骤 0 之后的业务步骤**。"前置条件"段落（含 `xf-check-invariants.mjs` 结构校验）对方言不可见、不可改——implement 命令本身无门禁，但前置条件的结构校验、`change.yaml.phase` 校验同样不允许方言绕过；方言本身也必须遵守 xflow 的结构不变量。

## 步骤 1：加载上下文

1. 读取各模块 `task.md`，解析任务列表和当前进度（已勾选 vs 未勾选）。如需了解跨模块依赖关系，可运行 `node .xflow/scripts/xf-deps.mjs --module <name>` 查询
2. 如存在 `xspec/changes/integration.md`，读取跨模块协调视图，了解集成任务（I 编号）和质量门禁
3. 读取所有设计文档作为实现约束。对每个模块调用 manifest 获取完整制品清单（**不要硬编码 6 项文件名**——不同 `module_type` 产出文件集不同）：
   ```bash
   node .xflow/scripts/xf-manifest.mjs --module-type <module_type> --all-phases --change-type <added|modified>
   ```
   按 manifest 返回的 `files[]` 逐一读取。典型映射：
   - `spec.md` / `spec.delta.md`：功能范围和验收标准
   - `hld.md` / `hld.delta.md`：概要设计（技术范围和架构方向）
   - `design.md` / `design.delta.md`：详细技术方案
   - `data-model.md` / `data-model.delta.md`：数据结构定义
   - `contracts.md` / `contracts.delta.md`：接口定义（仅 manifest 含此项）
   - `evaluation.md` / `evaluation.delta.md`：Agent 评测约束（仅 `ai-agent`）
   - `task.md`：任务清单（在步骤 1-1 已加载）

   额外读取（可选）：`research.md`（技术决策参考，读取课题索引表获取结论；如需深入看 `research/` 子文件）
4. 了解项目技术栈（从已有代码和设计文档中推断）
5. **检测可用验证命令**（后续步骤复用此清单）：
   - 检查 `package.json` 中的 scripts（`lint`、`typecheck`、`build`、`test` 等）
   - 检查 `tsconfig.json` 是否存在（TypeScript 项目 → `npx tsc --noEmit`）
   - 检查其他技术栈标志：`Cargo.toml`（Rust → `cargo check`）、`go.mod`（Go → `go build ./...`）、`pyproject.toml`（Python → 对应 lint 工具）等
   - 将结果记为「验证命令清单」，格式如：`类型检查: npx tsc --noEmit`、`Lint: npm run lint`、`构建: npm run build`
   - 如项目无任何可用验证命令，至少使用 IDE 的 ReadLints 检查变更文件

## 步骤 2：初始化与确定范围

1. 首次开始实现时，将 `xspec/changes/change.yaml` 的 `phase` 更新为 `implement`
2. 如用户指定了任务范围（如 `T001-T005` 或 `阶段1`），只执行指定范围
3. 否则从第一个未完成的任务开始，按阶段顺序执行
4. 检查前置依赖是否已完成

## 步骤 3：逐任务执行

对每个待执行的任务：

1. **理解任务**：读取任务描述，关联对应的设计文档章节
2. **执行实现**：根据技术方案和接口定义编写代码
3. **设计对照**：
   - 实现是否符合 spec 的功能描述
   - 接口是否符合 contracts 定义
   - 数据操作是否符合 data-model 定义
   - 代码风格是否符合项目约定和宪章要求
4. **代码验证**（按步骤 1 检测的验证命令清单执行）：
   - 对本任务新增/修改的文件执行 ReadLints 检查，确认无 lint 错误
   - 如有类型检查命令（如 `npx tsc --noEmit`），执行并确认无类型错误
   - 如有 lint 脚本（如 `npm run lint`），执行并确认通过
   - 构建命令（如 `npm run build`）在任务级不强制执行（开销大），留到阶段验证统一执行
   - 发现错误 → 立即修复 → 重新验证，循环直到全部通过
   - **验证未通过的任务禁止标记为 `[x]`**
5. **标记完成**：全部验证通过后，在对应的 `task.md` 中将该任务的 `[ ]` 改为 `[x]`
6. 进入下一个任务

## 步骤 4：异常处理

**设计文档与实际冲突**：暂停实现，说明冲突点，给出 1 个推荐方案 + 最多 2 个备选，等待用户决策。

**需要额外技术决策**：暂停实现，描述问题，给出推荐方案并说明理由，最多列 3 个选项。不要一次列出所有可能的方案——先推荐最合适的 1-2 个，用户不满意再补充。

**任务粒度不合适**：太大建议拆分，太小可合并。

**依赖未满足**：跳到依赖任务先执行；外部依赖暂停并说明。

## 步骤 5：阶段验证

每完成一个阶段的所有任务后，执行一次项目级验证：

1. 如项目有构建命令（如 `npm run build`），执行完整构建确认无编译错误
2. 如项目有 lint 脚本，执行全量 lint 检查
3. 如项目有类型检查命令，执行类型检查
4. 如项目有测试套件且本阶段涉及已有测试，运行相关测试

如有失败项，先修复再继续。修复后重新验证直到通过。

## 步骤 6：阶段性报告

阶段验证通过后，输出进度报告：

```
📊 阶段 X 完成

已完成任务：
  - [x] T001 [描述]
  - [x] T002 [描述]

总进度：X/Y 任务已完成 (XX%)

阶段验证：
  构建：✅ 通过 / ⚠️ 不适用
  Lint：✅ 通过 / ⚠️ 不适用
  类型检查：✅ 通过 / ⚠️ 不适用

继续执行阶段 X+1？
```

## 步骤 7：执行集成任务

当所有模块的阶段任务完成后，如存在 `integration.md`，按其中的 I 编号集成任务执行跨模块联调：

1. 按 `integration.md` 中的集成任务顺序执行
2. 每个集成任务完成后执行步骤 3 中的代码验证流程
3. 完成后在 `integration.md` 中将 `[ ]` 改为 `[x]`
4. 逐项检查质量门禁清单
5. 所有集成任务完成后，执行一次步骤 5 的项目级验证

如 `integration.md` 不存在（单模块变更），跳过此步骤。

---

## 步骤 8：最终验证

所有任务完成后，执行一次最终全量验证：

1. 项目构建通过（如有构建命令）
2. 全量 lint 检查无错误（警告可接受但需在报告中注明数量）
3. 类型检查通过（如适用）
4. 测试套件通过（如有）
5. 对所有本次变更涉及的文件执行 ReadLints 检查

如有错误级别的失败项，修复后重新验证。全部通过后才输出完成报告。

## 实现原则

1. **遵守宪章**：核心原则和技术方向以 constitution.md 为最高准则
2. **忠于设计**：严格遵循设计文档，不自行扩展功能
3. **增量推进**：完成一个任务验证通过后立即标记，保持进度可追踪
4. **及时沟通**：遇到问题暂停而非猜测
5. **不碰 SoT**：只修改 `xspec/changes/` 目录和项目源码，不修改 `xspec/modules/`
6. **代码可运行**：每个任务完成后确保项目可编译、无语法错误；不引入 lint 错误和类型错误

## 行为规则

- 严格按任务清单顺序执行
- 每完成一个任务立即更新 task.md
- 遇到设计偏差暂停沟通
- 不修改 `xspec/modules/` 目录
- 所有交互使用中文
