## 覆写动作：用预置宪章模板替代 3 轮交互式问答

玄武麻将游戏项目的核心原则与技术方向已由行业实践与工程规范固化（协议一致、麻将游戏隔离、安全优先 + TypeScript + FGUI / C++ 双端栈），逐条追问用户徒增交互成本且信息量低。本 profile 下直接输出 `xwRef/xuanwu/xuanwu-mahjong-game/constitution.md` 作为候选宪章，用户一键确认或在此基础上改动即可。

### 作用范围

- **仅覆写场景一（首次创建）**
- **不覆写场景二（修订）**：已有宪章的修订走通用 `/xf/constitution` 的场景二流程——修订本身只改局部，reference 预置模板不应覆盖用户既有宪章。若 AI 加载本方言时检测到 `xspec/constitution.md` 已存在（场景二），**本方言全部动作作废**，按通用流程继续执行。

### 保留不动

- **步骤 0（Profile 分支加载）**
- **步骤 1（项目上下文推断）**：scaffold 信号 / client/server 目录识别等仍照常做，用于给用户"选中 xuanwu-mahjong-game 是对的"的信心
- **步骤 1.5（项目 profile 选择）**：强制选择题必须经过，确保 profile 是用户明确决策的结果
- **步骤 1.6（Profile 方言延迟加载）**：通用命令在此插入方言加载点；本方言在此被激活

### 跳过 step 2（交互式问答）

通用 step 2 要求走 3 轮问答（项目理解 / 核心原则 / 技术方向）。本 profile 下整段跳过：

- 玄武麻将游戏项目**无需**向用户追问"最重要的 2-5 条原则是什么"——预置宪章已给出三条原则（协议一致 / 麻将游戏隔离 / 安全优先），这三条是玄武架构既定事实
- 玄武麻将游戏项目**无需**向用户追问技术方向——预置宪章已给出双端技术栈（TypeScript + FGUI / C++ / {server_module_name} + common_game 复用）
- 若用户有特殊项目级原则需补充，走下方 step 4 的"B. 需要修改"分支处理

### 替换 step 3（生成宪章）

通用 step 3 会读 `.xflow/templates/_shared/constitution.md` 模板并按问答结果填充占位符。本 profile 下整段替换为：

1. 读取 `xwRef/xuanwu/xuanwu-mahjong-game/constitution.md` 作为**候选宪章内容**（**绝对路径从仓库根起算，禁止省略 `xwRef/` 前缀**）
2. 替换候选内容中的占位符：
   - `**创建日期**：<日期>` → 填当天日期（`YYYY-MM-DD`）
   - `**最后修订**：<日期>` → 填当天日期
   - `**版本**：1.0.0` 保持不变（首次创建固定为 1.0.0）
3. 校验 `project_profile` 字段与 step 1.5 的 `selected_profile` 一致（reference 模板里已写死为 `xuanwu-mahjong-game`；若因模板维护差异出现不一致，以 `selected_profile` 为准覆盖）
4. **不**执行通用 step 3 的"未涉及板块移除"——reference 模板所有板块都是玄武工程必需品，不做裁剪
5. 把填充后的候选内容保存在内存，进入 step 4

### 替换 step 4（确认并写入）

通用 step 4 的"展示完整宪章 + A/B 选项"二选一保留形式，但选项语义调整为玄武专属：

1. 展示候选宪章全文（step 3 替换完日期与 profile 的版本）
2. 向用户确认（遵循 CLAUDE.md 交互规则，优先使用平台原生选择工具）：

   ```
   📜 玄武麻将游戏项目宪章候选稿已生成

   ⚠️ 本宪章基于玄武麻将游戏工程的既定范式预置（双端栈 + 三条核心原则 +
      技术方向表格 + 治理板块），未经 3 轮交互式问答。

   请确认：
     推荐：A
     A. 不需要修改，直接使用（推荐）
     B. 需要修改（请具体说明要改什么，例如：
        - "核心原则新增一条：禁止麻将游戏代码直接读写玩家存档，必须通过 PlayerDataService"
        - "技术方向表里把客户端编码规范从 ESLint + Prettier 改为 Biome"
        - "删除原则二里的 `mahjong_<game_id>_<name>` 命名约束（项目不用这套命名）"
       ）
   ```

3. 用户选择 **A** → 直接写入 `xspec/constitution.md`
4. 用户选择 **B** 并给出修改说明 → AI 在候选内容基础上**直接应用**这些修改，得到修订稿；不要退回到通用 step 2 的 3 轮问答流程
   - 若用户提出的修改会从根本上推翻三条核心原则或双端栈（如"把服务端改成 Node.js"），提醒用户："此类修改意味着本项目可能不适合 `xuanwu-mahjong-game` profile，建议考虑切回 `general`"，但仍按用户意图应用——profile 选择由用户自主决定，本方言不越俎代庖
   - 应用修改后再展示一次修订稿，循环 A/B 确认直到用户选 A
5. 最终确认后写入 `xspec/constitution.md`

### 理由

- **用户反馈**：玄武项目 3 轮问答繁琐且信息量低，核心原则与技术栈早已固化
- **减少决策疲劳**：预置模板把"需要用户拍板的事"收敛到"这个模板够不够用"这一个问题
- **保留逃生通道**：B 分支仍允许任意自定义，不限制用户表达力
- **不破坏通用命令**：场景二修订逻辑完全不动，本方言只处理"首次创建"这一个热路径
