## 1. 项目背景

公司目前通过开源 [LiteLLM](https://github.com/BerriAI/litellm) 为全员提供统一模型调用入口，已接入 100+ 人。但随着接入规模扩大和厂商增多，LiteLLM 暴露出以下不可绕过的问题：

1. **组织架构不匹配**：通用型租户模型与公司部门 / 岗位体系无法直接映射，权限管控灵活度有限。
2. **UI 过度臃肿**：集成 MCP、Agent、向量库等数十项与"网关"无关的功能，分散使用者注意力。
3. **国内厂商适配差**：核心团队在国外，对阿里百炼、DeepSeek 等国产厂商响应慢、Bug 多；企业版功能闭源不可定制。
4. **定制化受限**：项目庞大，深度修改后无法跟进上游更新，运维成本极高；无法实现精细化限额、设备监控等公司专属需求。
5. **安全治理缺位**：缺乏 Key 设备使用监控、TPM/RPM/并发限制等防滥用机制。

> **结论**：自建一个**贴合公司组织架构、聚焦核心场景、深度适配国产厂商**的模型网关，逐步替换 LiteLLM。

## 2. 项目目标

### 2.1 一句话定位

> **公司唯一的、组织感知的、可观测的、安全可控的大模型统一调用入口。**

### 2.2 阶段性目标

| 阶段 | 时间 | 目标 |
| :--- | :--- | :--- |
| MVP（V0.1 – V0.4） | W1 – W4 | 完成核心转发、Key 自助、模型组、限额管控，可承载试点部门流量 |
| RC（V0.5 – V0.7） | W5 – W7 | 部门权限、可观测、设备监控、性能优化全部到位，全公司灰度 |
| GA（V1.0） | W8 | 完整压测验证后正式发布，逐步替换 LiteLLM |

详见 [`02-ROADMAP.md`](./02-ROADMAP.md) 与 [`versions/`](./versions/)。

## 3. 目标用户

### 3.1 主要用户：全公司员工（100+ → 全员）

| 痛点 | 期望 |
| :--- | :--- |
| 多套厂商系统，缺统一入口，门槛高 | 一处登录、一处建 Key、一处调用所有模型 |
| 不知道自己用了多少、用得怎样 | 个人用量、习惯、Token 进度可视化 |
| 模型质量不稳时，不知道用哪个 | 全员可见的服务质量看板（延迟、报错率、TTFT） |

### 3.2 次要用户

#### 系统管理员

| 痛点 | 期望 |
| :--- | :--- |
| Key 分发依赖手工 | 员工自助、平台代理、Key 与员工身份绑定 |
| 模型底层变动业务感知 | 模型组抽象 + 后台动态切换 |
| 缺预算限额、并发限制 | 按 Key / 模型 / 部门多维 TPM/RPM/并发 配置 |
| 无法按部门差异化管控 | 部门权限模型组 + 部门用量套餐 |

#### 业务开发团队

| 痛点 | 期望 |
| :--- | :--- |
| 业务代码与具体模型强绑定 | 按"智力等级"调用模型组，底层热切换无感 |
| 选型困难 | 模型组（低 / 中 / 高智力）抽象 |
| 不知道自己能用什么模型 | 基于 SSO 身份的「我能调的模型列表」查询接口 |

## 5. 差异化优势（vs. LiteLLM）

| 对比维度 | LiteLLM | 模型网关（自建） |
| :--- | :--- | :--- |
| 🏢 组织架构匹配 | 通用租户模型，无部门权限 | 贴合公司组织，部门 / 个人 / 模型三维管控 |
| 🎛️ UI 体验 | 功能臃肿 | 极致聚焦：Key + 模型 + 日志 + 限额 + 权限 |
| 🇨🇳 国产厂商适配 | 适配慢、Bug 多、企业版闭源 | 深耕百炼 / DeepSeek 等，按需快速适配 |
| 🔧 定制化能力 | 改源码后无法跟进上游 | 自主可控，架构精简，长期低成本 |
| 🔐 安全便捷 | 无设备监控、无 SSO 动态模型列表 | 设备监控 + SSO 模型列表动态同步 |

## 6. 成功指标（North Star Metrics）

> 本节是**所有版本验收的最终对齐目标**。每个版本的 [验收标准] 应回扣到这里的一项或多项。

### 6.1 当前阶段四大核心指标（用户已确认）

| 指标 | 含义 | V1.0 目标 |
| :--- | :--- | :--- |
| **接入用户数** | 在网关创建过 Key 的活跃员工数 | ≥ LiteLLM 现有 100 人，6 个月内覆盖全员 |
| **日均请求数** | 网关日均完成的模型调用次数 | 替换 LiteLLM 后 ≥ 其当前日均量，月环比 ≥ 15% |
| **接口健康可用率（SLA）** | 网关 `/v1/*` 接口 5xx 占比的可用度 | ≥ 99.9% |
| **TTFT P95 时延** | 流式响应首 Token 到达时延（P95） | 较 LiteLLM 下降 ≥ 30% |

### 6.2 后续阶段引入的进阶指标（v1.1 PRD 列出）

| 指标 | 目标 | 引入版本 |
| :--- | :--- | :--- |
| 缓存命中率 | ≥ 40%，逐步至 50%+ | V0.6+ |
| TPS | ≥ 1000 次 / 秒 | V1.0+ 压测 |
| 报错率 | ≤ 0.5%（核心厂商 ≤ 0.3%） | V0.6+ |
| 限额管控覆盖率 | 100%（所有部门 / 个人均有限额） | V0.4+ |
| Key 异常使用预警准确率 | ≥ 95% | V0.7+ |
| 权限模型组适配率 | 100%（所有部门均按权限分配） | V0.5+ |
| TPM/RPM/并发拦截率 | ≥ 99%；脚本滥用事件 = 0 | V0.4+ |

## 7. 长期方向（>V1.0）

| 方向 | 愿景 |
| :--- | :--- |
| **重构落地 + 核心能力建设** | 成为公司稳定高性能的模型服务基础设施，全员日常使用 |
| **厂商生态建设** | 覆盖所有主流国产厂商 + 多模态（文生图 / 文生视频） |
| **可观测 + 数据智能** | 智能路由推荐、异常自动检测、成本预测，成为「AI 运维大脑」 |
| **安全管控深化** | Key 有效期、异常登录拦截、自动 revoke；权限按角色 / 项目细化 |

详细演进路径见 [产品愿景原文](#) 的「长期方向」章节。

## 8. 范围说明

### 8.1 in-scope（本项目范围内）

- 多厂商模型转发与抽象（聊天补全、流式、Embedding 等基础能力）
- Key 自助、SSO 绑定、设备监控、异常告警
- 模型组、部门权限、负载均衡、限流（TPM/RPM/并发）
- 用量统计、限额管控、Token 套餐
- 日志审计、核心指标监控（TTFT / 延迟 / 报错率 / 缓存命中）
- 管理后台 UI + 用户自服务 UI

### 8.2 out-of-scope（本项目不做）

- ❌ Prompt 管理 / Prompt 版本控制（交给业务方或独立产品）
- ❌ Agent 编排、工作流引擎、MCP 服务托管（避免重蹈 LiteLLM 臃肿覆辙）
- ❌ 向量数据库托管 / RAG 知识库（独立产品）
- ❌ 训练 / 微调任务调度
- ❌ 模型评测平台（可作为远期独立项目）

> 范围控制是本项目相对 LiteLLM 的**核心差异化**。任何"是否加入 X 功能"的讨论默认从 out-of-scope 出发，需提供「与七大核心价值的直接关联」才考虑纳入。

## 9. 关键约束

| 约束 | 说明 |
| :--- | :--- |
| 协议兼容 | 必须暴露 OpenAI 兼容协议（`/v1/chat/completions` 等），保障业务方零成本切换 |
| 身份系统 | 必须对接公司 SSO（OIDC / 内部账号体系），Key 必须与员工身份绑定 |
| 数据合规 | 调用日志含敏感 Prompt，需脱敏存储 + 权限隔离 |
| 高可用 | 单一厂商故障不得导致网关整体不可用 |
| 替换路径 | 必须能与 LiteLLM 并行运行，平滑灰度切流 |
