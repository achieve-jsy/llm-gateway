## 1. 文档定位与边界

### 1.1 `docs/` 和 `xspec/` 的分工

| 维度 | `docs/`（本目录） | `xspec/`（xflow 制品） |
| :--- | :--- | :--- |
| 解决什么问题 | "项目是什么 / 怎么管 / 什么时候做" | "每个模块怎么设计、怎么落地" |
| 颗粒度 | 项目级（PRD / 架构 / 路线图 / 版本规划） | 模块级（spec / hld / design / contracts / task） |
| 修改方式 | 直接 PR 编辑 + 评审 | 通过 xflow 命令（`/xf:clarify` → `/xf:design` → `/xf:archive`） |
| 保护机制 | 仓库 MR 评审 | xflow 活跃变更保护 + 阶段门禁（详见 `.opencode/AGENTS.md`） |
| 谁来读 | 全员、业务方、新人 | 开发执行、架构评审 |

> **强约束**：`docs/` 不重复 `xspec/` 的细节，也不绕过 xflow 流程直接编辑 `xspec/modules/`。
> 当一个版本要落地到具体模块时，路径必须是：**docs/versions/vX.Y.Z.md 列出范围 → `/xf:clarify` 开变更 → xspec 走完工作流 → `/xf:archive` 归档**。

### 1.2 文档分类

| 类别 | 文件 | 更新频率 |
| :--- | :--- | :--- |
| **稳定型**（产品定位） | `00-PRD.md` | 季度评审 + 大版本前修订 |
| **稳定型**（技术架构） | `01-TECH-STACK.md` | 大版本前修订 + 重大技术决策时 |
| **滚动型**（路线图） | `02-ROADMAP.md` | 每个版本完成后更新进度 |
| **节奏型**（版本规划） | `versions/vX.Y.Z.md` | 每周一个新文件，进入开发前完稿 |
| **规则型**（本文件） | `AGENTS.md` | 流程调整时同步 |

## 2. 版本号管理

### 2.1 版本号格式：语义化 SemVer（vMAJOR.MINOR.PATCH）

```
v0.3.1
│ │ └── PATCH：bugfix / 文档修正 / 紧急回滚
│ └──── MINOR：每周一个版本（V0.1 → V0.7 → V1.0...）
└────── MAJOR：里程碑级（v0.x 预发布，v1.x 正式发布，v2.x 重大重构）
```

| 段位 | 何时 +1 | 示例 |
| :--- | :--- | :--- |
| **MAJOR** | 不兼容的重大变更：技术栈替换、API 重大重构、产品定位转向 | v0.x → v1.0（GA 发布）；v1.x → v2.0（架构重写） |
| **MINOR** | 一个常规版本周期（默认 1 周）完成一组新功能 | v0.3.0 → v0.4.0 |
| **PATCH** | 不引入新功能的修复 / 文档调整 / 灰度回滚 | v0.3.0 → v0.3.1 |

### 2.2 版本生命周期状态

每个 `versions/vX.Y.Z.md` 必须在文档头声明 **STATUS**：

| STATUS | 含义 | 可写操作 |
| :--- | :--- | :--- |
| `📝 Planning` | 规划中（未冻结） | 自由调整范围 / 任务 |
| `🔒 Frozen` | 范围已冻结，进入开发 | 范围不可加，仅可砍 |
| `🚧 In Progress` | 开发中 | 仅更新进度、补充实现细节 |
| `🧪 Testing` | 开发完成，测试中 | 补充测试结果、缺陷登记 |
| `✅ Released` | 已发布 | 仅追加复盘、不再修改范围 |
| `⏸️ Paused` | 暂停（资源被抽走） | 标注暂停原因 + 预期恢复时间 |
| `❌ Cancelled` | 取消 | 标注取消原因 + 影响评估 |

### 2.3 状态流转规则

```
Planning → Frozen → In Progress → Testing → Released
   │          │           │          │
   ├──────────┼───────────┼──────────┴── 任意阶段可 → Paused / Cancelled
   ▼          ▼           ▼
（可重新规划）（必须先评审才能改回 Planning）
```

| 流转 | 准入条件 | 负责人 |
| :--- | :--- | :--- |
| Planning → Frozen | 范围与产品方对齐 + 技术方案有 ADR 或 HLD 兜底 | 项目负责人 |
| Frozen → In Progress | xspec 已开始对应变更（至少 spec 完成） | 开发负责人 |
| In Progress → Testing | 所有任务 ≥ 80% 完成，提测 | 开发负责人 |
| Testing → Released | 验收标准全通过 + 上线确认 | 项目负责人 |

## 3. 需求变更流程

### 3.1 三种变更类型

| 类型 | 触发条件 | 处理路径 |
| :--- | :--- | :--- |
| **A. 同版本内的细节调整** | 不影响范围 / 验收标准 | 直接更新 `versions/vX.Y.Z.md` 的「实现细节 / 进展」段 |
| **B. 同版本内的范围变更** | 加 / 删功能但版本号不变 | 走 §3.2 评审流程；通过后更新版本文档的「范围」段并在「变更记录」追加一行 |
| **C. 跨版本的路线图调整** | 新增功能改变排期 / 推迟功能 / 重排优先级 | 走 §3.3 流程；更新 `02-ROADMAP.md` + 涉及的版本文档 |

### 3.2 同版本范围变更流程（B 类）

```
1. 提出方填写「变更申请」（issue 或简短 markdown）：
   - 变更内容（加 / 删什么）
   - 触发原因
   - 对验收标准的影响
   - 对工期的影响（追加多少天 / 是否影响下个版本启动）
2. 项目负责人评审：是否在本版本承受范围内
   - ✅ 接受：更新版本文档 → 同步 xspec（如已在开发，走 xflow 的 modification 流程）
   - ❌ 拒绝：建议挪到下一个版本，走 C 类流程
3. 更新版本文档的「变更历史」段，记录决策与理由
```

> **硬约束**：`STATUS=Frozen` 后**只允许减、不允许加**。要加功能必须先把版本拉回 `Planning` 并重新评审。

### 3.3 路线图调整流程（C 类）

```
1. 提出方提交「路线图变更提案」（建议用 issue + 投票）
2. 召集项目负责人 + 技术负责人 + 产品方周会评审
3. 评审通过后：
   a) 更新 02-ROADMAP.md 的版本表、矩阵、里程碑
   b) 新增 / 修改 / 取消对应的 versions/vX.Y.Z.md
   c) 在 02-ROADMAP.md 的「变更历史」段追加一行
4. 同步 xspec/changes/changelog.md（如已有活跃变更受影响）
5. 周会同步全员
```

### 3.4 反模式（禁止）

- ❌ 在 `STATUS=Frozen` 后直接往版本范围里加任务
- ❌ 同一个版本文档里把不同功能混在一起（违反"一个版本一个主题"原则）
- ❌ 修改已 `Released` 版本的范围（应该开新 patch 或 minor）
- ❌ 绕过 §3.3 直接改 `02-ROADMAP.md`
- ❌ 在 docs/ 里写模块级详细设计（应该走 xflow → xspec）

## 4. 版本文档维护规范

### 4.1 命名规则

```
versions/
├── README.md                # 版本管理总览（模板说明 / 状态字典）
├── v0.1.0.md                # 项目骨架
├── v0.1.1.md                # （如有 patch）
├── v0.2.0.md
├── ...
└── v1.0.0.md
```

### 4.2 必须包含的章节

每个版本文档 **必须** 按 [`versions/README.md`](./versions/README.md#版本文档模板) 提供的模板组织。核心章节：

1. **元信息**（版本号 / 周次 / STATUS / 负责人 / 关联 xspec change-id）
2. **版本主题**（一句话）
3. **目标**（要解决什么，回扣 PRD 的核心价值）
4. **范围**（in-scope / out-of-scope）
5. **任务清单**（粗任务列表，细任务在 xspec/<module>/task.md）
6. **验收标准**（可测量 / 可验证）
7. **依赖与风险**
8. **进展记录**（开发中更新）
9. **变更记录**（同版本范围调整必须登记）
10. **复盘**（Released 后补充）

### 4.3 创建新版本文档的时机

| 时机 | 建议提前量 |
| :--- | :--- |
| 进入开发前 1 周 | 必须创建并完成 §1 – §7 |
| 当前版本 `Released` 后 | 当周内必须更新当前版本 §10 复盘 + 启动下一版本 |

## 5. AI Agent 协作规则

> AI Agent（Cursor / Codex / Claude）在协助维护 `docs/` 文档时必须遵守。

### 5.1 允许做的

- ✅ 读取所有 `docs/` 文件并基于内容给建议
- ✅ 创建新的 `versions/vX.Y.Z.md`（基于模板）
- ✅ 修改 `docs/` 下任意文档（用 Write/StrReplace），但要遵守本规则
- ✅ 在版本文档更新进展、补充细节
- ✅ 完成版本后自动追加复盘草稿
- ✅ 把 `docs/versions/` 与 `xspec/changes/change.yaml` 中的 change-id 双向关联

### 5.2 禁止做的（硬约束）

- ❌ **禁止**绕过本文件 §3 直接调整路线图或版本范围
- ❌ **禁止**修改 `STATUS` 字段（除非用户明确要求并指明从哪个状态到哪个状态）
- ❌ **禁止**修改已 `Released` 版本的范围段或验收标准（只能追加复盘）
- ❌ **禁止**在 `docs/` 里写模块级详细设计（spec/hld/design/contracts/data-model），必须引导用户走 xflow
- ❌ **禁止**绕过 [`.opencode/AGENTS.md`](../.opencode/AGENTS.md) 的 xflow 流程直接编辑 `xspec/modules/` 或 `xspec/archive/` 或 `xspec/changes/.gates/`
- ❌ **禁止**在 docs/ 中复制 xspec/ 已有的详细设计内容（应该用链接引用）

### 5.3 推荐工作流

```
用户："我想给 V0.3 加一个 X 功能"
  │
  ▼
1. 读取 docs/versions/v0.3.0.md，检查 STATUS
2. 若 STATUS=Frozen 或更后 → 提示走 §3.2 流程，建议挪到下个版本
3. 若 STATUS=Planning → 帮用户更新范围段，并提示在「变更记录」追加一行
4. 若涉及跨版本影响 → 提示同步更新 02-ROADMAP.md
```

```
用户："开始做 V0.3 了"
  │
  ▼
1. 把 v0.3.0.md 的 STATUS 改为 In Progress（用户确认后）
2. 引导用户用 /xf:clarify 在 xspec/changes/ 创建变更
3. 在 v0.3.0.md 元信息段写入对应的 change-id（关联追踪）
```

## 6. 文档与代码的同步

### 6.1 PR 必须同步更新的场景

| 场景 | 必须同步更新 |
| :--- | :--- |
| 完成一个版本的所有任务 | `versions/vX.Y.Z.md` 的进展 + 状态 + 复盘 |
| 新增 / 移除一个厂商接入 | `01-TECH-STACK.md` §3.3 厂商优先级表 |
| 改变技术选型 | `01-TECH-STACK.md` 对应章节 + ADR 追加一条 |
| 新增 / 修改核心价值 | `00-PRD.md` §4 + `02-ROADMAP.md` §4 矩阵 |
| 路线图调整 | `02-ROADMAP.md` 全表 + 受影响版本文档 |

### 6.2 文档评审

| 文档 | 评审者 |
| :--- | :--- |
| `00-PRD.md` | 项目负责人 + 产品方 + 至少 1 个业务方代表 |
| `01-TECH-STACK.md` | 项目负责人 + 技术负责人 + 至少 1 个核心开发 |
| `02-ROADMAP.md` | 项目负责人 + 技术负责人 + 产品方 |
| `versions/vX.Y.Z.md` | 项目负责人 + 该版本负责人 |
| `AGENTS.md` | 项目负责人 |
