## 1. 背景与问题

### 1.1 现状

`call_traces` 的正文（`request_headers` / `request_body` / `response_body` 三个 jsonb 列）直接写入 PostgreSQL，落在 `/data`。

2026-09-23 生产事故：`/data` 可用空间跌至 **7.03 GiB**（98% 占满），正文导致 TOAST 膨胀到 **315 GB**，网关 trace 写入被拒绝，**断流 23 小时 15 分钟，损失约 14 万条 trace**。

应急处置完成了三个动作：导出 14 天正文（595.11 GiB → 127.62 GiB zstd，4.66x）到 `/datalog`、置空 1,539,827 行正文、手动 VACUUM。`/data` 从 7.03 GiB 恢复到 297 GiB。

**但这是止血，不是治本**：网关恢复写入后，`/data` 以约 **37 GiB/天** 重新增长。

### 1.2 根因

**正文的家在 `/data`。** 只要正文先落 PG，`/data` 就必然被撑满；事后归档是补偿措施，且代价是同一份数据**存两份**（PG 一份 + 归档一份）。

### 1.3 本设计要做的

把正文的家从 `/data` 搬到 `/datalog`：**写入时直接落盘，PG 只保留元数据与定位键。**

## 4. 架构与数据流

### 4.1 数据流

```
请求完成
  │
  ├─ TraceEvent.Emit()                                  ← 不变
  │
  ▼
┌─ 网关进程（llm-*-gateway，2 GiB cgroup 限额）────────────────┐
│ TraceWriter.Run()  消费事件                                  │
│  ① 序列化为一整行 JSON（字段与顺序对齐现有归档格式）          │
│  ② 追加明文到 spool（只顺序追加，**不做压缩**）               │
│  ③ 记录 (dt, inst, part_seq, row_seq)                        │
│  ④ 写 PG 元数据行（含定位键）                                 │
└──────────────────────────────────────────────────────────────┘
  │  进程边界：唯一交接物是 /datalog 上的明文 spool
  │  （无进程间传输、无共享内存、无信号；见 §7.2 的发现机制）
  ▼
┌─ sealer 进程（独立 systemd unit，§11.1）─────────────────────┐
│ seal 循环：扫描 spool/dt=*/inst=*/part-*.jsonl                │
│  ⑤ 用 mtime + 封块间隔判定「已停止追加」                       │
│  ⑥ Go 侧顺序扫描 spool，采集每行首字节的未压缩偏移              │
│  ⑦ zstd -19 --long=29 子进程把 spool 流式压成 .tmp            │
│  ⑧ Go 侧追加 trailer（索引）+ footer → fsync → rename         │
│  ⑨ 确认产物落稳 → 删除 spool                                  │
└──────────────────────────────────────────────────────────────┘
```

**关键性质：正文从进入系统到落盘，全程不经过 PG；压缩全程不经过网关内存。**

### 4.2 组件划分

| 组件 | 位置 | 职责 | 依赖 |
|---|---|---|---|
| `internal/tracearchive`（新包） | 新增 | 存储格式：spool 追加、封块（驱动 zstd 子进程）、内嵌索引读写、按定位键取正文 | 标准库 + `os/exec`（调用 **C 版 zstd CLI**）+ `klauspost/compress/zstd`（**仅解码**） |
| `TraceWriter` 改造 | `internal/gateway/observability/trace_event.go` | 正文交给 `tracearchive`，PG 只写元数据 | `tracearchive` |
| gateway 侧封块驱动 | 网关内（**无**） | 网关内**没有**压缩动作；只由写入器周期性 flush 写缓冲，让 spool 的 mtime 反映「仍在追加」 | `tracearchive` |
| sealer 进程 | 新增独立进程（systemd unit，§11.1） | 扫描 spool 目录发现待封块 → 调 zstd CLI 压缩 → 追加 trailer/footer → rename → 删 spool | `tracearchive` + `zstd` 二进制 |
| 点读服务 | `internal/observability/service/` | 按 `request_id` 定位并取回正文 | `tracearchive` |
| 点读接口 | `internal/controlplane/handler/` | 两个 HTTP 端点 | 点读服务 |
| CLI | `cmd/trace-body/`（新） | 运维与验收工具 | 点读服务 |

**依赖说明的更正：** `internal/tracearchive` 的 `klauspost/compress/zstd` 依赖**保留**，但用途收窄为**只解码**（点读路径）；编码改为调用 C 版 zstd CLI 子进程。因此该包同时依赖标准库 `os/exec` 与外部 `zstd` 二进制（部署要求见 §11.1）。

**边界清晰性检查：** `internal/tracearchive` 不依赖 PG、不依赖 gin、不依赖任何 gateway 代码——可以只读它的接口文档就理解用途，可以独立单元测试。这是本设计最重要的解耦点。

### 4.3 复用来源

`internal/archive` 包（分支 `feat/trace-archive-v3`）中的存储层**自包含**（仅依赖标准库 + `klauspost/compress/zstd`），可整体复制为本设计的起点：

| v3 文件 | 复用方式 |
|---|---|
| `partwriter.go` | **部分复用**：spool 先落盘、原子 rename 的骨架照搬；其中**内嵌的 zstd writer 必须换成 CLI 子进程**（方案 C） |
| `local.go` | **直接复用**：存储层与并发闸 |
| `store.go` | 复用接口定义 |
| `index.go` | 复用 codec 参数校验（级别/窗口），但参数映射目标从 `zstd.EOption` 改为 CLI 参数（`-19 --long=29`） |
| `readbody.go` | **需重写**：其前提是"按 `request_id` 排序写 + 二分"，本设计的写入为乱序到达，前提不成立（§5.4） |

> 依赖变更：新分支需新增 `github.com/klauspost/compress/zstd` 并 `go mod vendor`（仓库使用 vendor 构建）。**方案 C 下该依赖只服务解码**（§4.2）；编码侧新增的运行时依赖是**外部 `zstd` 二进制**，它不进入 `go.mod`，属部署项（§11.1）。

## 5. 存储格式规格

### 5.1 目录布局

```
/datalog/trace-archive-v4/                       ← 新根，不碰任何现有目录
  dt=2026-09-24/
    inst=blue/
      part-000000.jsonl.zst                      ← 已封块产物
      part-000000.jsonl.zst.tmp                  ← 写入中（rename 前）
    inst=green/
      part-000000.jsonl.zst
  spool/
    dt=2026-09-24/
      inst=blue/part-000001.jsonl                ← 明文，封块成功后删除
```

按 `inst` 分目录的理由：`llm-blue-gateway` 与 `llm-green-gateway` **在生产中同时 Up**，切流期间两者都可能写。按实例隔离，天然不冲突，切流后旧实例的块自然封口。

### 5.2 产物文件物理布局

```
┌─────────────────────────────────────────────────────┐
│ zstd 单帧                                            │
│   全部行的 JSONL 顺序拼接                             │
├─────────────────────────────────────────────────────┤
│ trailer：索引表                                       │
│   条目：row_seq → row 在【未压缩流】中的起始字节偏移    │
│   编码：按偏移升序做差分 + varint                     │
├─────────────────────────────────────────────────────┤
│ footer：32 字节定长                                   │
│   magic(4)="TBA4" | format_version(2)               │
│   | trailer_offset(8) | trailer_len(4)              │
│   | frame_sha256[:8](8) | reserved(6)               │
└─────────────────────────────────────────────────────┘
```

**字段精确定义：**

| 字段 | 含义 |
|---|---|
| `row 起始字节偏移` | 该行第一个字节在**未压缩** JSONL 流中的位置（行首，不含前一行换行符） |
| `frame_sha256[:8]` | 对 **zstd 帧字节**（不含 trailer/footer）计算的 SHA-256 前 8 字节 |
| `format_version` | 当前为 1；冷层合并若扩展索引键为 `(dt, part, row)`，由此字段区分 |

**设计要点：**

- **footer 定长且位于文件末尾** ⇒ 读它只需 `pread` 末尾 32 字节，**不需要解压任何数据**即可知道索引在哪。
- **trailer 在 zstd 帧之外** ⇒ 否则读索引就得先解压全帧，索引的意义就没了。
- **索引与内容出自同一次封块操作** ⇒ 不可能不同步。这直接消灭了事后归档方案的 F2 缺陷（外部 `index.jsonl` 丢失导致点读全部 miss 却表现为"数据不存在"）。
- **`format_version` 是冷层扩展的锚点**（§5.5）——超级文件只需提升版本号并换用扩展索引键，读取侧按版本分派。

### 5.3 压缩选型与封块参数

#### 5.3.1 算法选型

| 候选 | 通用文本压缩比 | 压缩速度 | 解压速度 | 判决 |
|---|---|---|---|---|
| snappy | 1.5~2.0× | 250~500 MB/s | 1~2 GB/s | ✗ 比为极致速度设计，压缩比不足 |
| lz4 | 1.8~2.5× | 400~700 MB/s | 3~5 GB/s | ✗ 解压快，但我们的瓶颈是**磁盘容量**不是解压速度 |
| gzip/zlib | 2.5~3.5× | 20~40 MB/s | 250~400 MB/s | ✗ 比 zstd 慢约 25 倍、压缩比还低约 15%，两头不占 |
| zstd -3 | 2.5~3.5× | 300~500 MB/s | 1~2 GB/s | ✗ 实时场景选择，我们后台压缩不需要这个速度 |
| **zstd -19** | **4.0~6.0×** | 3~10 MB/s | 1~2 GB/s | ✅ **选定** |
| zstd -22 | 4.5~7.0× | 1~3 MB/s | 1~2 GB/s | ✗ 比 -19 仅多 10~16%，压缩耗时增 1.7 倍且内存更高 |

**关键性质（决定点读体验）**：zstd 的**解压速度几乎与压缩级别无关**。因此选 -19 只付出压缩侧代价，**点读延迟与选 -3 相同**。

参考：[CERN ZSTD 材料](https://indico.cern.ch/event/860690/contributions/3624882/attachments/1947679/3231550/ZSTD_compression_algorithm_in_ROOT.pdf)、[多编解码器对比研究](https://arxiv.org/pdf/2602.03839v2)。

**⚠️ 外部资料甄别**：评审期间曾出现一份声称 zstd -9 = 93.6×、-19 = 122.2× 的对照表。**该表不可用于本决策**：

```
· 其定性结构正确（解压速度与级别无关、压缩耗时随级别上升、全部无损）
· 但其压缩率为本设计实测值的 10~25 倍
· 其解压速度 6772~8157 MB/s 属"小样本全部驻留 CPU 缓存"的量级
· 其自述为"从记忆里补齐"，即非实测

本设计一律采用本节列出的自有实测值。
```

#### 5.3.1.1 编码器标定（2026-09-24 实测）：Go 库 vs C 版 CLI

上一节的选型只确定「用 zstd、用 -19」，**没有回答「用 Go 库还是 C 版 CLI」**。原设计假定在网关内嵌 Go 库 `klauspost/compress/zstd`（512 MiB 窗口），2026-09-24 用真实数据标定后**该假定被推翻**（U7/U8 的实测答案，见 §15）。

样本 = `/datalog/emergency-archive/dt=2026-09-18` 的前 8 个 part，解压后 **2078.7 MB**（2,179,635,659 字节），以 embedding 请求为主，是最难压的真实数据。生产机 8 核，逐点单进程，`VmHWM` 采样峰值 RSS：

**Go 库 `klauspost/compress`（流式，与生产封块路径一致）**

| 级别 | 窗口 | 产物 | 压缩比 | 耗时 | 峰值 RSS |
|---|---|---|---|---|---|
| 9 | 128 MB | 557.6 MB | 3.73x | 20.5s | 265.2 MB |
| 9 | 256 MB | 557.6 MB | 3.73x | 20.2s | 523.2 MB |
| 9 | 512 MB | 557.6 MB | 3.73x | 33.9s | 1035.6 MB |
| 19 | 128 MB | 423.0 MB | 4.91x | 109.8s | 295.3 MB |
| 19 | 256 MB | 387.7 MB | 5.36x | 103.5s | 553.3 MB |
| **19** | **512 MB** | **384.0 MB** | **5.41x** | **212.9s** | **1066.2 MB** |
| 22 | 128 MB | 423.0 MB | 4.91x | 146.1s | 295.2 MB |
| 22 | 512 MB | 384.0 MB | 5.41x | 239.8s | 1065.7 MB |

**C 版 zstd CLI 对照**

| 级别 | 窗口参数 | 产物 | 压缩比 |
|---|---|---|---|
| 9 | `--long=29`（512 MiB） | 224.8 MB | 9.25x |
| **19** | **`--long=29`（512 MiB）** | **202.6 MB** | **10.26x** |
| 19 | `--long=27`（128 MiB） | 397.1 MB | 5.23x |
| 19 | 缺省窗口（无 `--long`） | 535.1 MB | 3.88x |

**⚠️ 版本标注（承重）**：以上 C 版 CLI 的数字**全部出自生产机上的 `zstd` v1.4.8**（`/usr/bin/zstd`，2022-03 的系统包）。该版本上 `--long=29` 实测**可用且有效**（这正是产出 202.6 MB 的那条命令；`zstd --long=31 -19 -c </dev/null` 也被接受，退出码 0），**因此不需要升级 zstd**。但 **10.26× 是「zstd v1.4.8 + `-19 --long=29`」专属的结果，不是该参数组合的通用值** ——换版本必须重新标定压缩比（§11.1）。

**三条结论：**

1. **U7 不成立**：Go 库级别 19/512 MiB = 384.0 MB，C 版 CLI 同条件 = 202.6 MB ⇒ **Go 库是 CLI 的 1.90 倍**（原设计的验收线是 ≤1.30 倍）。
2. **`WithWindowSize` 在 Go 库上只花内存、几乎不给收益**：级别 9 下窗口 128→512 MiB 产物**一个字节都没变**（557.6→557.6 MB）；级别 19 只降 9.2%（423.0→384.0 MB）。同条件 C 版 CLI 降 **49.0%**。收益源自 C 版 `--long` 的**长距离匹配器**，`klauspost/compress` 没有等价实现——**这是能力缺口，不是参数没调好**。
3. **内存**：Go 库 512 MiB 窗口实测峰值 RSS **1066 MB（≈窗口 × 2.08）**；C 版 CLI 同窗口 **570 MB（≈窗口 × 1.08）**。规格 §5.3.3 原先引用的正是后者。

**裁决（协作方 2026-09-24）：方案 C——封块移出网关，由独立 sealer 进程使用 C 版 zstd CLI（`-19 --long=29`）完成。**

| 维度 | 方案 A（原设计：网关内嵌 Go 库） | 方案 C（本次裁决） |
|---|---|---|
| 压缩比（09-18 样本） | 5.41× | **10.26×** |
| 压缩后日增（绝对量口径） | 384.0 MB / 2078.7 MB 原始样本 | **202.6 MB / 2078.7 MB 原始样本** |
| 编码器内存归属 | 网关 2 GiB cgroup 内，实测 1066 MB | **sealer 主机，实测 570 MB；网关内为 0** |
| 部署单元 | 无新增 | 新增 sealer 的 systemd unit（形态参考生产机已有 `trace-archive.{service,timer}`） |
| 发现机制 | 网关内协程轮询 + 阈值信号 | 独立进程按目录内容发现（mtime + 封块间隔，§7.2），幂等可重启 |

**附带收益**：failure mode 更清晰——独立 unit 可 `Restart=on-failure` 且有日志，而「网关内协程静默死掉」不可观测。**读取侧不变**：仍是 Go 库解码（`klauspost/compress/zstd` 继续作为依赖，只用于解码；解码器内存 ≈ 窗口，需 `WithDecoderMaxWindow`，见 §8.4）。

**为什么不是「网关内起 CLI 子进程」（方案 B）**：那会让**网关镜像必须携带 `zstd`**，且子进程的内存仍算在网关的 2 GiB cgroup 里。而生产机上 `/usr/bin/zstd` **已经存在**（系统包，v1.4.8），并且已经在用**同一种模式**跑归档任务（`/etc/systemd/system/trace-archive.{service,timer}` 调宿主机的 `/root/daily-trace-archive.sh`）⇒ 方案 C 的 sealer 直接做成**宿主机 systemd unit**、用宿主机的 `/usr/bin/zstd`，**网关镜像零改动**（§11.1）。

#### 5.3.2 杠杆排序（实测，**随内容结构变化**）

**核心结论：杠杆的重要性排位不是固定的，取决于数据里重复是"近距离"还是"远距离"。**

```
难压数据（embedding 为主）    ① 窗口  > ② 合并  > ③ 级别
易压数据（文本/排障为主）     ① 合并  > ② 级别  > ③ 窗口
```

| 128 MiB | 162 MB | — | 295.3 MB | × 2.31 |
| 256 MiB | 298 MB | — | 553.3 MB | × 2.16 |

**规律：C 版 CLI 的 RSS ≈ 窗口 × 1.08；Go 库的 RSS ≈ 窗口 × 2.08（本次标定，级别 19）。** 方案 C 用 CLI，因此按 **570 MB**（512 MiB 窗口，= 窗口 × 1.08）做 sealer 主机的内存预算，**网关侧为 0**。

**⚠️ 一处未消除的口径不一致（诚实标注）**：本表 C 版 CLI 的 `-19`/512 MiB 记 **852 MB**，而 §5.3.1.1 的标定口径给出 C 版 CLI ≈ 窗口 × 1.08 = **570 MB**。**本设计采用 570 MB 作为方案 C 的内存口径**（这也是规格原先引用的数字）；852 MB 那一格的测量条件（输入、级别、是否开 `--long`）无留档记录，**待实测复核**。两种取值都不改变「编码器不再占用网关内存」这一结论。

**为什么取 512 MiB 而不是 1024 MiB：**

```
1024 MiB 窗口比 512 MiB 只多压 7%（-70.7% vs -63.8%）
但编码器内存从 570 MB 涨到 1190 MB（C 版 CLI 实测），多 620 MB
512 MiB 已由 §5.3.1.1 标定：C 版 CLI 570 MB / 产物 202.6 MB（10.26×）
512 MiB 是可配置值；sealer 主机内存富余且实测划算时可上调至 1024 MiB
```

**⚠️ 内存计量的适用边界（原 U8，已实测闭合）**：原先这一节只能标注「以上全部是 C 版 CLI 的数据，Go 库未实测」。2026-09-24 标定已给出答案（§5.3.1.1 结论 3）：**Go 库 ≈ 窗口 × 2.08，C 版 CLI ≈ 窗口 × 1.08**。方案 C 选 CLI，编码器内存因此完全落在 sealer 主机上；**解码侧仍用 Go 库**，其内存 ≈ 窗口，约束见 §8.4。

**⚠️ 编码器校准的口径冲突 —— 已实测钉死（原 U7）**

设计期间对"Go 库 `better` 比 CLI 同级别大多少"出现过两个口径（一个约 -22%，一个约 -26%），**二者不一致，当时不采信任一具体值**，只保留"约 20~30%"的区间。2026-09-24 标定（§5.3.1.1）给出了确凿答案：**同数据、同级别（19）、同窗口（512 MiB）下，Go 库产物 384.0 MB，C 版 CLI 产物 202.6 MB ⇒ Go 库是 CLI 的 1.90 倍（+90%）**，远超原验收线 ≤1.30 倍，也超出"20~30%"的猜测区间。**编码器裁决为 C 版 zstd CLI（方案 C）；Go 库退居解码侧。**

#### 5.3.4 块大小的定稿规则（U1 实验）

```
用生产真实数据（含 embedding 大正文，不可只用 09-13 那类易压样本）测：
  候选块大小 B ∈ {256 MB, 768 MB, 1536 MB, 3072 MB}
  对每个 B 测两个量：
    r(B) = 压缩比
    l(B) = 点读 P99 延迟
  选【满足 l(B) ≤ 1.5 秒 的最大 B】

若 3072 MB 仍满足延迟约束，则取 3072 MB，并重新评估上限。
内存约束：窗口固定 512 MiB（§5.3.3），与 B 无关；spool 已在磁盘，故 B 不受网关内存限制。
  方案 C 下编码器内存计入 sealer 主机（约 570 MB），不计入网关 2 GiB cgroup。
```

依据：D3 明确"优先压缩比"，因此在不突破延迟约束的前提下取最大块。

### 5.4 为什么定位键不是字节偏移

```
压缩后的字节偏移只有在封块结束那一刻才知道。
若要在写入时就把偏移写进 PG，就必须在封块后回填 UPDATE
  → 每天约 9 万次 UPDATE
  → 且形成"PG 元数据 ↔ 产物文件"的双向依赖，失败语义复杂化
```

**因此定位键为 `(dt, inst, part_seq, row_seq)`**：四个分量在写入追加时即可确定，无需回填。

### 5.5 冷层合并的格式预留（本期不实现）

冷层若要按月合并成超级文件，其索引只需从 `row_seq → offset` 扩展为 `(dt, part_seq, row_seq) → offset`。

**PG 中已存的定位键无需任何修改，也不需要回填 UPDATE。** 这是把定位键设计成复合键而非物理偏移的核心收益。

## 7. 写入路径

### 7.1 追加（请求路径上，必须极快）

```
1. 序列化为一行 JSON
2. 追加到 spool 文件（带缓冲）
3. row_seq = 当前块内自增计数
4. 组装元数据行（含定位键）
```

**请求路径上只做顺序追加，不做压缩**——压缩全部在**独立 sealer 进程**里完成。理由：网关是延迟敏感路径；且磁盘顺序追加的成本远低于压缩。

**⚠️ 方案 C 新增的必做项：网关必须周期性 flush 写缓冲。** 方案 A 下网关内协程封块，`PendingSeals()` 会在封块前 flush；方案 C 下 sealer 是**另一个进程**，它只能看到已经 `write(2)` 到文件的内容——若缓冲一直未落盘，sealer 会读到一个**被截断的 spool**（静默丢数据），而 spool 文件的 mtime 又因为「没有真正写盘」而显得很旧，正好骗过 §7.2 的「已停止追加」判断。因此：**写入器必须按不超过 `seal_interval` 的周期（建议 1 分钟）flush 缓冲**，且 `seal_interval` 必须远大于该 flush 周期。**该周期性 flush 必须无条件执行**（不设「本轮是否要封块」的前置条件）：否则一个刚建立的块在其生命周期前 `seal_interval`（15 分钟）内磁盘上始终是空文件、mtime 停在创建时刻，sealer 会把这个「安静的活跃块」判成「已停止追加」，封出空产物并删掉 spool —— 缓冲里的正文全部丢失且无任何报错（与「忘了 flush」是同一类静默丢数据）。

**⚠️ `Append` 必须拒绝行内裸换行与空行（写入前置校验 `validateLine`；已落地在 `771d7985`）。** 公开入口 `Append` 在落盘前校验两件事：正文（去掉末尾换行后）内部不含裸 `\n`/`\r`；且去掉末尾换行后不为空。承重不变量是「一次 `Append` == 一条物理行」——正文自带换行时一次调用会产出多条物理行而行号只 +1，此后 `row=N` 就会读到第 `N+1` 行的正文。**为什么是拒绝而不是转义**：产物必须是**逐字节的原始 JSONL**；写入侧若转义，读取侧就必须反转义，那等于给读取路径引入一个变换，并让产物不再是「原样 JSONL」——任何按行解析的工具都会读到非原字节。而 JSON 序列化本身**不会**产生裸换行（正文里的 `\n` 会被序列化成 `\\n`），所以含裸换行的输入只可能是**调用方 bug**，快速失败优于静默改造。空行同理：它不是合法 JSON，任何按行解析 `.jsonl` 的工具都会在它上面失败（与标记行不取空行是同一个理由）。

**⚠️ 未成文义务（调用方契约；不写下来就是隐性 bug）**：`Append` 的 `line` 必须是**单行 JSON 对象**，且**不得是字面量 `null`**——`null` 正是 `AppendFailed` 的失败标记行（下一段），读取侧按整行相等识别它（§8.2），一条内容恰好为 `null` 的真实正文会被误判成「正文从未落盘」。生产侧正文是结构体序列化（恒为 `{...}`），因此实际安全；但这是**调用方义务，不是本模块的保证**（本模块若校验 `null`，会连标记行一起禁掉）。若将来允许把裸 JSON 标量写进正文，这条必须重新评估。

**⚠️ 落盘逻辑必须抽到内部共享函数（`appendLineLocked`），且 `validateLine` 只放在公开 `Append` 上。** `AppendFailed` 复用同一段落盘代码（让标记行与真实正文由构造共享同一套不变量：trim / 换行 / 行号连续 / 字节计数），因此校验**不能**放进共享路径——否则**标记行会被自己的守卫拒绝**。

**⚠️ `AppendFailed` 必须写一个标记行——「只推进行号、不写字节」是不可实现的。** spool 追加失败时（盘满/权限），元数据行仍照写、该行标 `body_missing=true`（§9.1），写入器侧对应 `AppendFailed(dt)`：**推进行号的同时写一个内容为 `null` 的标记行**，使「物理行序 == `row_seq`」恒成立。

为什么不能「只推进行号不写字节」——这是**格式强制**，不是取舍：

- 32 字节 footer 里的 `row_count` 是**产物内行数**（§5.2）
- trailer 是「每行一个差分 varint」的偏移表（§5.2 第 2 项），而该差分 varint 编码**没有表达「本行没有偏移」的能力**——它假定行是**稠密**的
- 读取侧两条路径都是「按行序取第 row 行」（§8.2）

三者不可能同时成立：写侧稀疏、格式要求稠密、读侧按行序 ⇒ 该行之后的物理行序整体比 `row_seq` 少 1，**`row=N` 会被读成第 `N+1` 行的正文**——静默返回错误的正文，是本设计最不能接受的一类缺陷。

标记内容取 `null`（合法 JSON，4 字节 + 换行）：

- **不用空行**——产物是 `.jsonl`，每一行都应是合法 JSON 对象，空行会让任何按行解析的工具炸掉
- **不用 `{}`**——它与「合法的空正文」无法区分
- spool 的每一行存的都是正文对象（`request_headers`/`request_body`/`response_body` 那组键），因此 `null` 不可能与真实正文混淆

读取侧据此识别：**产物路径与 spool 路径都要把标记行映射成「正文从未落盘」**（§8.2），不得把 `"null"` 当作正文递出去。

**⚠️ `Append` 写失败必须隔离该块——残行是承重不变量的唯一无守卫入口（已落地在 `771d7985`）。** 写失败（典型是 ENOSPC 盘满）时 `bufio` 的错误是**粘性**的（此后同一块的任何写入都失败），且一次短写可能在盘上留下**没有换行收尾的残行**。残行的后果一条响亮、一条静默：封块侧 `scanSpoolOffsets` 会以 `ErrSealFailed` 拒绝封块（该块永远封不掉、告警与重试不止）；读取侧 spool 兜底是「顺序取第 row 行」，一旦在残行之后继续追加，残行就占掉一个行位，其后每一行整体错位 ⇒ `row=N` 静默读到第 `N+1` 行的正文。因此硬要求是：**残行永远不可被封块、也不可再有后续行追加进同一个文件**。机制四步：

| 步 | 动作 | 为什么 |
|---|---|---|
| ① | 回退到**最后一个 `\n` 边界**，抹掉写了一半的残行 | 反向**有界**扫描（界 = **本次失败那一行的长度**：正文内不含裸换行，所以文件里最后一个 `\n` 之后只可能是一条半行）；若整个文件没有任何 `\n`（首次追加即失败）⇒ `Truncate(0)` |
| ② | **隔离改名** `part-NNNNNN.jsonl` → `part-NNNNNN.jsonl.zst` | 该后缀由**两条已冻结的规则**共同保证安全（见下） |
| ③ | **毒化**该块：不再写入、`PendingSeals` 不报它、`Close` 只释放 fd | 后续 `Append`/`AppendFailed` 自动换到 N+1，调用方无需重置任何状态 |
| ④ | 改名失败 ⇒ `Truncate(0)`；再失败则在错误里**如实说明** | 0 字节 spool 产不出残行（只会被 sealer 封成 0 行产物 ⇒ 该 part 的读请求一律行号越界，响亮报错） |

**②为什么安全（必须由命名规则而不是流程纪律来挡）**：这个后缀由两条既有冻结规则共同给出——`ListPendingSeals` **只收 `.jsonl` 结尾**的名字 ⇒ sealer **永远看不到**隔离件（进程外目录扫描这条发现路径被堵死）；而 `parsePartSeq` **接受** `.jsonl.zst` ⇒ 写指针仍把序号 N 算作**已用** ⇒ **N 永不被复用**（复用会让旧 PG 里 `(part=N, row=r)` 静默读到另一个 part 的正文——最坏的一类错）。注意隔离名必须经 `partName(part, suffix)` 生成，**不能**把后缀直接拼到 spool 名后面（那会得到 `part-NNNNNN.jsonl.jsonl.zst`，`parsePartSeq` 拒绝它 ⇒ N 被复用）。

**⚠️ 已知副作用（有意接受，必须写明）**：隔离件的内容是**明文 JSONL 而不是 zstd 帧**，但名字与产物等价。若一条毒化**之前**已成功写入的 PG 元数据带着 `body_ref_part=N` 去点读，读取侧**查不到它**——§8.2 的读取只按两条**精确路径**查找（产物 `<root>/dt=D/inst=I/part-N.jsonl.zst` 与 spool `<root>/spool/dt=D/inst=I/part-N.jsonl`），而隔离件在 **spool 目录**下、名字是 `.jsonl.zst`，两条都不是它 ⇒ 实际返回 **`ErrNotArchived`**（响亮、500 类、需人工介入），**不是** `ErrFooterCorrupt`（后者要求产物目录里放着一个非 zstd 文件，本机制不产生这种文件）。**读取侧不为它新增分支或哨兵。**

**运维判据（供部署文档）**：spool 目录下若出现「内容是明文 JSONL 的 `part-*.jsonl.zst`」，即表示该块因写入失败被隔离，其中正文已不能通过正常路径读取；释放空间后把它**改回** `part-NNNNNN.jsonl` 即可让 sealer 正常封块（文件已回退到行边界，故产物行数 = 真实完整行数；尾部丢失的行读出来是行号越界，仍是响亮报错）。

**【已知代价：持续 ENOSPC 下块序号与目录项无界增长（登记，不修）】** 持续盘满时每次失败 `Append` 都换新 part，而序号计算每次都重扫产物目录与 spool 目录 ⇒ **本地无上限、无退避**：块序号与目录项会无界增长，且每次 `Append` 付一次 O(n) 目录扫描。这里**刻意不加计时器或计数器**：正确修法是**背压**——磁盘满时网关应放弃正文并标 `body_missing=true`，而不是持续重试写盘（见 §15 R9，计划 2 的职责）。它**不产生静默错正文**。

### 7.2 封块（独立 sealer 进程）

```
发现机制（sealer 每轮）：
  扫描 <root>/spool/dt=*/inst=*/part-*.jsonl
  只收 .jsonl 结尾的名字（.tmp、产物名 .jsonl.zst、非 part- 前缀一律忽略）
  dt/inst 取自目录名，必须通过校验（dt = 合法日期、inst ∈ {blue,green}）；
  不合法则【跳过该目录】而不是中断整轮扫描（见下）
  对每个 spool：若 mtime ≤ now - minAge（即「已停止追加」，minAge 默认 3 小时），进入封块
  否则跳过——正在写的 spool 一律不碰

步骤（全部在 sealer 进程内）：
  0. spool 必须以换行符结尾；遇未终止的尾行 ⇒ 拒绝封块（保留 spool、删 .tmp、不产生产物，见下）
  1. Go 侧先顺序扫描 spool，按行记录每行首字节的未压缩偏移
     （一次顺序读，成本可忽略；见下方「为什么偏移在压缩前采集」）
  2. 启动子进程之前依次完成三项判定：产物存在性检查 → 行数交叉校验 →
     zstd 版本探测（探测必须在这两项【不依赖编码器】的判定之后、任何文件创建之前，见下）
  3. 启动子进程：zstd -19 --long=29 -T1 -c，stdin = spool 文件，stdout = .tmp
     （Go 侧只负责喂数据；编码器内存全部计入 sealer，不计入网关）
  4. 子进程退出码非 0 ⇒ 封块失败：保留 spool、删除 .tmp、下轮重试（见 §9.2）
  5. 在 .tmp 末尾追加 trailer（差分 varint）
  6. 追加 footer（32 字节）
  7. fsync(.tmp)
  8. rename(.tmp → part-NNNNN.jsonl.zst)
  9. fsync(目录)
  10. 删除 spool 文件（**必须在第 8、9 步成功之后**）
```

**为什么偏移在压缩前采集**：方案 A 是「边压边从喂入流里数行」，因为压缩与索引由同一个 Go 函数完成。方案 C 下 CLI 是独立进程、Go 侧不再看到压缩过程中的行边界，所以改为**在喂给 CLI 之前先按行扫一遍 spool**。这是一次额外的顺序读（成本可忽略），换来的是索引与帧内容仍然出自**同一次封块操作**（I3 不破）。

**为什么发现机制是「mtime + 封块间隔」而不是信号**：sealer 是独立进程，网关无法给它发信号（且进程间信号会引入网关→sealer 的耦合）。用 **mtime + 间隔**判断「已停止追加」不需要任何进程间通信，并且**幂等且可重启**——任何一轮崩溃后，下一轮扫描会重新发现同一个 spool 并重试。**代价**：封块最坏延迟 = 一个轮询周期 + `minAge`（默认 3 小时，见下）；另有两个前提：网关必须周期性 flush（§7.1），且**网关必须自己周期滚动 part（R8，滚动间隔 ≤ 1h）**，否则 sealer 删除 spool 后网关继续追加同一 part 会把字节写进已 unlink 的 inode（D7，永久丢失正文）。

**并发封块**：同一 `(dt, inst)` 同时只允许一个封块动作（sealer 进程内互斥）。跨进程不存在冲突——`inst` 已隔离；`rename` 之前先检查产物是否已存在（§7.3）。

**⚠️ 残行守卫：spool 必须以换行符结尾（已落地在 `76042bcd`）。** 遇未终止的尾行 ⇒ **拒绝封块**（保留 spool、删 `.tmp`、不产生产物）。守卫在**创建任何文件之前**生效，因此「保留 spool、不产生产物」由构造保证，而不依赖后续清理。理由：封块器有两条发现路径——`SealTask.Rows > 0`（写入器自己报的块）能靠行数交叉校验把残行挡成 `ErrRowCountMismatch`；而 `ListPendingSeals` **目录扫描**路径下 `Rows == 0`，**没有行数交叉校验可依赖**，所以这个守卫是那条路径**唯一的确定性保护**。没有它，残行会被当成一整行静默烤进产物，其后的行边界全部错位，点读于是静默返回错误的正文。

**⚠️ zstd 版本锁定必须被强制执行（已落地在 `e0b0084f`）。** §11.1 原先只写「版本必须锁定」，没有任何代码强制。现在 sealer 会在封块前探测 `<ZstdBinary> --version`，并与可配置的**期望版本**比对（`SealerOptions.ExpectedZstdVersion`，空则取 `defaultZstdVersion = "1.4.8"`）。四条错误路径**全部响亮失败**，且只用既有的 `ErrSealFailed`（不新增哨兵）：① 二进制缺失；② 探测进程非零退出；③ 输出不可解析（含 `"1.5"`、`"1.5.7-beta"` 这类非严格三段式）；④ 版本不符（错误里同时带上期望值与实际值）。理由：§5.3.1.1 的压缩比标定（10.26×）**是版本特定的**（10.26× 来自生产 v1.4.8），**换版本必须重新标定**，绝不能让它静默通过。本机开发环境是 v1.5.7、与生产 v1.4.8 不同，这正是「期望版本必须可配置」的原因之一（本地真封块用例显式传本机版本）。

**⚠️ 探测位置的判定原则（重要）**：版本探测必须在**不依赖编码器的判定之后**（产物存在性检查、行数交叉校验）、**任何文件创建之前**。这是实现过程中一次真实的红→绿得出的：把探测放在 `Seal` 最前面，会让「产物已存在（`ErrPartExists`）」「行数不符（`ErrRowCountMismatch`）」两条用例转红——**配错的编码器会掩盖这两类真实数据问题**，运维看到的根因就是错的。放在这里同时保证：确认编码器可信之前，不创建任何文件（含 `.tmp`）。

**⚠️ `minAge` 默认 = 3 小时（已落地在 `e0b0084f`）**，推导链写全如下（便于审计）：

- 实测摄取速率 ≈ 37 GiB/天 ≈ **1.54 GiB/小时**
- 块目标 `defaultBlockBytes` = 1536 MiB ⇒ 满流量下约 **1 小时**填满一个块
- **网关的滚动间隔应取 ~1 小时**：让**大小**阈值先触发，从而保住已标定的 10.26× 压缩比（滚动过短会把块截成 ~400 MB，压缩比退到未标定的区间）
- ⇒ `minAge` = 3 × 1h = **3h**（3 倍余量）。它必须**严格大于**网关的滚动间隔，本进程无法区分「已停止追加」与「暂时空闲」，这个时间差是唯一的保护
- 成本：未封块 spool ≈ 3h × 1.54 GiB/h ≈ **4.6 GiB** 未压缩驻留，相对 `/datalog` 240 GiB 可用空间可忽略
- **对端约束 R8**：网关滚动间隔 **≤ 1h**（计划 2 落地；现有 `defaultSealInterval = 15m` 已满足该约束，且 3h 对它有 12 倍余量）

**⚠️ `ListPendingSeals` 必须校验目录名（已落地在 `e0b0084f`）**：`dt` 必须是合法日期、`inst ∈ {blue, green}`，不合法则**跳过该目录**（**不中断整轮扫描**——一个坏目录不应让当天的封块全停）。**校验的理由是健壮性与对称性，不是防路径穿越**（更正见下）：一个畸形目录名不应产出一个语义不通的 `SealTask`，且列举侧必须与写入侧的严格校验**对称**。

**⚠️ 更正：「取值来自目录名 ⇒ 会越过 spool 子树」这个前提不成立（Task 6 评审实测，改理由、保留校验）。** 早期版本的理由是「`dt`/`inst` 来自目录名，而 `filepath.Join` 会做路径清理——`PartDir(dt, "../x")` 会越过子树」。实测：`filepath.Join(root, "dt=..", "inst=blue")` = `root/dt=../inst=blue`，**不折叠**——`dt=..` 是**字面目录名**而不是父目录记号（`PartDir`/`SpoolDir` 拼的是 `"dt="+dt` / `"inst="+inst`），而**目录名不可能含 `/`** ⇒ `..` 恒以字符串一部分的形式出现、不会成为裸 `..` 元素。**在这条列举路径上不存在穿越。**

**精确表述（不得简化成「穿越根本不可能」）**：穿越在**一般情形**下并非不可能——值里若含 `/../`，`Join` 就会看到**裸 `..` 元素**并折叠。例如 `PartDir("2026-09-24/../..", "blue")` ⇒ 元素 `dt=2026-09-24`、`..`、`..` ⇒ 两层 `..` 把 `dt=2026-09-24` 连同 `root` 一并清掉，结果落到 `root` **之外**（实测 `root` = `/root` ⇒ `/inst=blue`）；`Inst="../../green"` ⇒ 元素 `inst=..`、`..`、`green` ⇒ 折叠成 `root/dt=X/green`。**本路径不适用**：`dt`/`inst` 取自目录名（不含 `/`），故不成立。**写入侧的 `dt`/`inst` 则确实属于这类「含 `/` 的调用方输入」**，那里的校验按路径分量理解是成立的（见计划 Task 5）。

**⚠️ API 形态偏离：由包级函数改为方法 `(*Sealer).ListPendingSeals()`（已落地在 `e0b0084f`）**。计划原先登记的是包级函数 `ListPendingSeals(root, minAge)`，实际落地的只有**方法**形态：方法天然带上 `ZstdBinary`/`ExpectedZstdVersion`，计划 4 的循环构造一次 `Sealer` 即可发现并封块；包级签名允许 `root` 与 `minAge` 来自不同来源，会产生「用 A 实例的 root 配 B 实例的 minAge」这类组合错误。**计划里的包级函数登记须一并更正。**

### 7.3 写指针的位置（幂等性的锚点）

写指针用于确定"下一个 `part_seq` 是多少"，必须满足 I4（同一 `(dt, inst, part_seq)` 只被封块一次）。

```
权威来源：产物目录的实际内容
   next_seq = max( 目录中已存在的 part-NNNNN.jsonl.zst 的 NNNNN ) + 1
             以及 spool 中已存在的 part-NNNNN.jsonl 的 NNNNN

规则：
  · 进程启动时扫描一次目录建立内存态
  · 运行时由内存态自增
  · 每次封块前用 spool 文件名中的 seq（即权威值）写入，而非内存计数

不引入 PG 表或独立指针文件：目录内容本身即指针，少一个需要保持一致的状态。
若产物已存在（重复封块），则【拒绝覆盖】并告警——宁可留下 spool，不可覆盖唯一副本。
```

## 8. 读取路径

### 8.1 最小闭环接口

```
GET /internal/v1/trace-body?request_id=<uuid>      InternalAuth（网关/内部调用）
GET /api/v1/trace/:request_id/body                 JWTAuth（管理面调用）

响应：
  200 + 正文 JSON
  404 + body_missing=true        正文写入时即失败，从未落盘
  410 + body_missing=true        正文曾落盘但产物缺失（需人工介入）
  500 + 明确诊断                  区分"文件缺失"与"从未归档"
```

### 8.2 读取算法

```
1. 按 request_id 查 PG → (dt, inst, part, row, body_missing)
2. body_missing = true               → 410/404
3. <root>/dt=<dt>/inst=<inst>/part-<part>.jsonl.zst 存在
     → 读末尾 32 字节 footer
     → 校验 magic；读 trailer；二分查 row → 解压后偏移 off
     → 【R10】校验 footer 的 frame_sha256[:8] 与帧字节（[0, trailer_offset)）一致
        （不符 ⇒ 500 + 诊断「产物损坏」，不得静默返回不存在）
     → 流式解压，累计到 off 后取该行（读到目标行立即停止）
     → 该行是标记行 null（正文写入时即失败）→ 404 + body_missing=true（见 §7.1）
4. 否则明文 spool 存在
     → 路径：<root>/spool/dt=<dt>/inst=<inst>/part-<part>.jsonl
     → 按 row_seq 顺序读取第 row_seq 行（无需索引：行号即顺序）
     → 【R10】末行若未以换行符结尾 ⇒ 拒绝读取（不得 trim 后当正文返回）
     → 该行是标记行 null                 → 404 + body_missing=true
5. 都不存在                          → 500 + 诊断
```

**标记行 ⇒ `body_missing`（404），不得当作正文返回。** `AppendFailed` 写的标记行（§7.1）在**产物路径与 spool 路径上都必须被显式识别**：读取侧是逐字返回行内容、**不做 JSON 校验**的，若不加识别，字符串 `null` 会被原样递给调用方——那等于把「正文从未落盘」（§8.1 的 404 + `body_missing=true`）伪装成「正文就是 `null`」，正是本设计要消灭的一类错误。识别标记行是两条路径**共同的要求**，不是 spool 兜底的额外分支。

**⚠️ R10：读取路径的三项硬要求（`internal/tracearchive/reader.go` 尚未落地——以下是必须实现的「要求/待落地」，不是已完成的现状）：**

1. **`readFromSpool` 必须拒绝未以换行符结尾的末行**，**不得** trim 掉残字节后当正文返回。这是**真正的静默错正文路径**（封块侧的残行守卫只是响亮拒绝）：若末行不完整而写入器在其后继续追加，残行占掉一个行位，其后所有行整体错位 ⇒ `row=N` 静默读成第 `N+1` 行。判据与封块侧同源（「EOF 时仍带回了非空字节」；0 字节 spool 是合法状态）。
2. **读取产物时必须校验 footer 的 `frame_sha256[:8]`**：重算 zstd 帧字节（`[0, trailer_offset)`）的 SHA-256 前 8 字节并与 footer 比对，不符 ⇒ 500 + 诊断（产物损坏）。该字段目前**只写不读**，等于完整性检查从未执行——而「发现半写 / 位腐」正是它存在的全部理由。
3. **遇标记行返回 `ErrBodyMissing`**（404 + `body_missing=true`）：产物路径与 spool 路径**都**要识别（计划已登记，保持不变）。

前两条必须各有能区分它们的用例（全局约束的变异判据）：删掉末行终止符守卫、删掉 `frame_sha256` 校验，分别要有用例转红。

**第 3/4 步天然无竞态**：spool 只在产物 `fsync` + `rename` + 目录 `fsync` 全部成功后才删除（§7.2 第 9 步），因此任何时刻**恰好有一个存在**。

**未封块的近期 trace 直接读明文**，无需等待封块。这解决了"大块 ⇒ 近期正文读不到"的体验问题。

### 8.3 读取的空间硬约束（强制性）

以下四条是**规格级强制要求**，不是建议。违反任意一条都会造成"读取导致磁盘持续增长"：

| # | 约束 | 理由 |
|---|---|---|
| C1 | **流式解压到内存，命中目标行立即停止** | 峰值内存 ≈ 一行正文（约 880 KB），与块大小无关 |
| C2 | **不落任何临时文件** | 禁止"解压到 /tmp 再读"的实现 |
| C3 | **不缓存已解压的块** | 禁止为加速而缓存块内容 |
| C4 | **读 spool 直接 seek，不复制** | 明文 spool 原地读 |

**补充说明（POSIX 语义）**：读取期间该文件被并发删除是安全的——已打开的 fd 仍可读。因此 C1~C4 下，**任意次读取对磁盘占用的增量恒为 0**。

### 8.4 解码侧的内存约束（大窗口的连锁代价）

⚠️ **窗口参数（§5.3.3 的 512 MiB）不只影响写入侧，也影响读取侧：**

```
zstd 解码器内存占用 ≈ 压缩时使用的窗口大小
  写入用 512 MiB 窗口  ⇒  每次点读的解码器需约 512~600 MB
```

而这发生在 **control-plane**（2 GiB 限额）中，与 §8.3 的 C1（流式解压）叠加：

| # | 约束 | 值 |
|---|---|---|
| C5 | **点读并发数必须有上限** | 按 600 MB/并发估算：2 GiB 限额下最多 **2 个并发点读**，超出须排队 |
| C6 | **读 spool 明文路径不受此限** | 它不涉及解压，无窗口内存开销 |

**这是选择大窗口换压缩比的真实代价：它同时抬高了写入侧与读取侧的内存门槛。** U8 的实测结论（§5.3.1.1 结论 3）是 **Go 库 ≈ 窗口 × 2.08、C 版 CLI ≈ 窗口 × 1.08**——但**方案 C 把编码器（1066 MB 的 Go 库或 570 MB 的 CLI）整体移出网关**，因此上表的 C5 只需按**解码侧**估算：解码器 ≈ 窗口（512 MiB），**待实测**。若实测解码器内存显著高于窗口、或点读并发瓶颈不可接受，则须下调窗口（每降一档约损失 15~20% 压缩比，见 §5.3.2）。

## 9. 失败语义与降级

### 9.1 事件级

| 情形 | 行为 | 数据后果 |
|---|---|---|
| spool 追加失败（盘满/权限） | 该行标 `body_missing=true`，**元数据行照写** | 正文丢失，元数据（延迟/错误）保留 |
| PG 写入失败 | 沿用现有逻辑：批量降级逐条，坏记录跳过 | 沿用现状 |

### 9.2 块级

| 情形 | 行为 |
|---|---|
| **zstd 子进程非零退出 / 启动失败（`zstd` 二进制缺失）** | **保留 spool**、删除 `.tmp`、**不产生产物**；下轮重试；连续失败 N 次告警 |
| **zstd 版本探测失败 / 版本不符（§7.2）** | 同上（**保留 spool、删除 `.tmp`、不产生产物**、下轮重试）。四条错误路径（二进制缺失 / 探测非零退出 / 输出不可解析 / 版本不符）一律以既有 `ErrSealFailed` 响亮失败，**绝不静默通过**；期望版本可配置（`SealerOptions.ExpectedZstdVersion`，默认 `"1.4.8"`） |
| **spool 末尾未终止（残行，§7.2 残行守卫）** | **拒绝封块**：保留 spool、删除 `.tmp`、不产生产物。它应被当作**写入侧事故**（盘满短写）而不是「压缩失败」来处理——残行若被封进产物，其后的行边界全部错位（静默错正文） |
| 压缩（I/O）/ fsync / rename 失败 | **保留 spool**，下轮重试；连续失败 N 次告警，**绝不删 spool** |
| 产物已存在（重复封块） | 拒绝覆盖、保留 spool、告警（§7.3） |
| 磁盘水位超过 `disk_watermark_percent` | 停止接收新正文（标 `body_missing=true`），元数据照写，告警 |
| 产物 footer 校验失败 | 读取返回 500 + 诊断，**不静默返回"不存在"** |

**关于「独立 unit 的 failure mode」**：sealer 是独立 systemd unit，因此「子进程反复失败」「sealer 静默死掉」这两类故障有明确的可观测信号（unit 状态 + 日志 + `Restart=on-failure`），而方案 A 的「网关内协程静默死掉」不可观测。这是方案 C 的附带收益。

### 9.3 关键设计意图

**磁盘满时系统退化到"只记元数据"，而不是像 2026-09-23 那样把整个服务拖垮。**

- 可用性优先于正文完整性
- 退化事件有明确可观测信号（`body_missing` 速率）
- 元数据（`request_id` / `ts` / 阶段耗时 / `error_code`）几乎不占空间，可继续记录

## 10. 不变量与崩溃窗口分析

### 10.1 不变量

| # | 不变量 |
|---|---|
| I1 | 元数据行存在 ⇒ (产物文件 XOR spool 文件 存在) 或 `body_missing=true` |
| I2 | 产物文件只能通过 `rename` 出现，永不出现半个文件 |
| I3 | 产物的内容与内嵌索引出自同一次封块操作，不可能不同步 |
| I4 | 单个 `(dt, inst, part_seq)` 只被封块一次（写指针 + 幂等） |
| I5 | 删 spool 之前必须已确认产物 `fsync` 成功且目录 `fsync` 成功 |

### 10.2 崩溃窗口

| 崩溃时刻 | 盘上状态 | PG 状态 | 后果 | 处理 |
|---|---|---|---|---|
| 追加后、PG 写入前 | spool 有该行 | 无元数据行 | **孤儿正文**（无害） | 定期清理（可选） |
| PG 写入后 | spool 有该行 | 有元数据行 | 正常 | 封块后转产物 |
| 压缩中 | `.tmp` 残留 | 有元数据行 | spool 仍在，下轮重试 | sealer 启动时清理 `.tmp` |
| rename 后、删 spool 前 | 产物 + spool 都在 | 有元数据行 | 读取优先产物，无害 | 下轮封块发现 spool 已被处理 |
| 删 spool 后 | 只有产物 | 有元数据行 | 正常 | — |

**关键性质：任何崩溃点都不会出现"元数据行指向不存在且不可恢复的正文"。** 最坏情况是孤儿正文（占用空间，可清理）或 spool 残留（下轮重试）。

## 11. 部署变更

### 11.1 必需变更

**① 网关：只需要能写 spool，不再需要 zstd。**

```yaml
# deploy/blue-green/docker-compose.{blue,green}.yml
llm-*-gateway:
  volumes:
    - /datalog:/datalog              # 新增：网关需要写正文 spool
  environment:
    TRACE_BODY_ROOT: /datalog/trace-archive-v4
    TRACE_BODY_BLOCK_MB: "1536"       # 待 U1 实验定稿
    TRACE_BODY_SEAL_INTERVAL: "15m"   # §5.3.3，凭直觉设定，待定
    # 方案 C：zstd 级别/窗口已不在网关使用（编码在 sealer 进程），
    # 但网关必须按 flush 周期落盘写缓冲，且该周期须远小于 SEAL_INTERVAL（§7.1）
    TRACE_BODY_FLUSH_INTERVAL: "1m"

llm-*-control-plane:
  volumes:
    - /datalog:/datalog              # 点读服务需要读正文
  environment:
    TRACE_BODY_ROOT: /datalog/trace-archive-v4
```

**② 新增 sealer 的部署单元（方案 C 的核心代价，也是它更省的地方）。** sealer **不进容器**，做成**宿主机 systemd unit**：直接用宿主机的 `/usr/bin/zstd`（v1.4.8），**网关镜像零改动、不需要安装 `zstd`**。形态参考生产机上已有的 `/etc/systemd/system/trace-archive.{service,timer}`（见 §12）：

```ini
# /etc/systemd/system/trace-body-sealer.service（新增，宿主机 unit）
[Unit]
Description=调用链正文封块器（spool → zstd -19 --long=29 产物）
After=local-fs.target

[Service]
# 二选一：Type=oneshot + 配套 timer 周期触发，或 Type=simple + 进程内循环
ExecStart=/usr/local/bin/trace-body-sealer \
  --root /datalog/trace-archive-v4 \
  --zstd-binary /usr/bin/zstd \
  --zstd-level 19 --zstd-window-mb 512 \
  --block-mb 1536 --seal-interval 15m

# 独立 unit 的 failure mode 明确可观测（方案 A 的网关内协程做不到）
Restart=on-failure
RestartSec=30s

[Install]
WantedBy=multi-user.target
```

```ini
# /etc/systemd/system/trace-body-sealer.timer（若用 oneshot 形态）
[Timer]
OnBootSec=5min
OnUnitActiveSec=5min
[Install]
WantedBy=timers.target
```

**③ 依赖与挂载矩阵（必需）：**

| 单元 | 形态 | `/datalog` 权限 | 额外依赖 |
|---|---|---|---|
| gateway | 容器（docker-compose） | **spool 目录可写**（产物目录可由 sealer 独占写） | 无（**镜像不需要 `zstd`**） |
| sealer | **宿主机 systemd unit** | **读写**（读 spool、写 `.tmp`/产物、删 spool、`fsync` 目录） | 宿主机的 `/usr/bin/zstd`（v1.4.8，须支持 `--long`） |
| control-plane | 容器 | 只读（点读） | 无 |

**⚠️ zstd 版本必须锁定（承重）**：方案 C 的 10.26× 出自 **v1.4.8**（§5.3.1.1 的版本标注）。sealer 必须固定使用某个已知版本（生产机现状：`/usr/bin/zstd` = v1.4.8），**变更 zstd 版本必须重新标定压缩比并复核解压兼容性**；不要把 `zstd` 的版本随镜像/基础镜像漂移。

**该锁定现已由代码强制执行（已落地在 `e0b0084f`）**：sealer 封块前探测 `zstd --version` 并与可配置的期望版本（`SealerOptions.ExpectedZstdVersion`，默认 `"1.4.8"`）比对，二进制缺失 / 探测非零退出 / 输出不可解析 / 版本不符四条路径全部以既有 `ErrSealFailed` 响亮失败（§7.2、§9.2）。**「默认期望版本在生产上探测通过」这件事仍未实测**（本机是 v1.5.7，与生产 v1.4.8 不同）——见 §15 的生产侧验收清单。

**待实测（不要臆断）**：sealer 与 gateway **分处宿主机与容器**（`/datalog` 在容器内的路径映射与属主、sealer 以哪个用户运行、`fsync` 对目录的权限）——见 §11.2 V5。此外容器内用户对 `/datalog/spool` 的属主关系也仍未验证（V2）。

**④ 部署变更清单（来源：读本仓库部署文件，尚未在生产机验证）**

已核实的现状：

```
deploy/blue-green/docker-compose.{blue,green}.yml
  · network_mode: host          ← 共享宿主网络
  · deploy.resources.limits.memory: 2g
  · 【没有 volumes: 段，全文提到 datalog 0 次】⇒ 容器当前没有任何 /datalog 挂载

根 Dockerfile
  · builder: golang:1.22-alpine
  · runtime: alpine:3.19 + apk add --no-cache ca-certificates tzdata
  · COPY --from=builder /app/gateway .
```

由此得到本设计的部署变更：

| # | 单元 | 变更 | 是否动镜像 |
|---|---|---|---|
| 1 | gateway 容器 | **唯一变更是新增一个 `/datalog` 的 bind mount**（compose 当前没有 `volumes:` 段，需要新增该段）。需要一次容器重启，走仓库既有的蓝绿脚本 `deploy/blue-green/deploy-blue-green.sh` | **不改** |
| 2 | sealer | 新增**宿主机 systemd unit** + timer，使用宿主机的 `/usr/bin/zstd`（v1.4.8）。不涉及容器 | **不改** |
| 3 | control-plane 容器 | 新增 `/datalog` 挂载（只读，点读需要） | **不改** |

**明确写出这一点：方案 C 下根 `Dockerfile` 一行都不用改。** 这是相对**方案 B**（网关内起 CLI 子进程）的实质优势——方案 B 必须给运行时镜像加 `apk add zstd`（并因此引入一个随基础镜像漂移的 zstd 版本，与 §11.1② 的版本锁定要求冲突）。

**⚠️ `network_mode: host` 不解决问题**：它共享的是**网络命名空间**，文件系统仍然隔离，所以 bind mount 是必需的、不能因为 host 网络而省略。

## 13. 容量与保留期

### 13.1 现状账（实测）

```
/datalog 总计 589.5 GiB   已用 319.9   可用 239.6
  /datalog/archive            189 GiB  遗留 gzip（唯一副本）

  杂项（p0-bench/leakscan-*） 约 1.6 GiB

```

**实测压缩比（14 天归档，256 MB 分块 + Go `better`）——跨度极大：**

```
09-18  3.48×  ← 最难压（embedding 为主）
09-20  3.61×      09-15  4.88×      09-11  5.75×      09-12  8.18×
09-21  3.72×      09-16  5.29×      09-10  5.51×      09-19  9.59×
09-22  4.59×      09-17  5.30×      09-09  6.20×      09-13 14.80×  ← 最易压
                      09-14  5.33×

```

**⚠️ 压缩比是流量的函数，不是一个可钉死的常数。** 同一份数据在不同日期的比值差 4.3 倍，取决于当天 embedding 请求的占比。**必须按月复测。**

### 13.2 预期压缩比（本设计，方案 C 基线）

```
预期比 = 内容基线 × 调优增益（C 版 CLI -19 --long=29 + 大块单流）

内容基线（实测；口径 = 生产在用的 256 MB 分块 + Go better）
  难压天（09-18 全天）        3.48×   ← §13.1 的逐日账
  难压天样本（09-18 前 8 part）3.71×   ← §5.3.1.1 标定所用样本
  整体 14 天                  4.66×
  易压天（09-13）            14.80×
  今天（09-23）               2.77×

本设计（方案 C：C 版 CLI -19 --long=29）——【实测】
  难压天样本 09-18           10.26×   ← 同数据实测，§5.3.1.1
  相对基线的增益              2.77×   = 10.26 ÷ 3.71

预期结果——【外推，整体尚未在新编码器下复测】
  难压天    3.48×  →  约 9.6×    （3.48 × 2.77，用实测增益外推）
  整体      4.66×  →  约 9×      ← 规划口径
  易压天   14.80×  →  约 30×     （估算，未直接实测；§5.3.2 在 09-13 上实测
                                   -19/128 MB 窗口已到 34.0×，512 MB 窗口只会更高）
```

**规划口径取 9×。** 说明两点：

1. 按同一实测增益（2.77×）直接外推整体会得到 **12.9×**（4.66 × 2.77）；但易压数据上长距离匹配的增益更小（§5.3.2：09-13 上窗口 128→1024 MB 只值 -12.9%），因此**外推取保守值 9×**。
2. **这个 9× 此前是「按 C 版 CLI 折算」的外推，而实现假定用的是 Go 库**——而 Go 库在同参数下只有 **5.41×**（§5.3.1.1）。**方案 C 让这个规划口径第一次真正可实现**；这也是容量账从「Go 库口径约 17 天」提升到「29 天」的原因（§13.3）。

**但必须保留的警告**：压缩比是流量的函数。实测同盘不同日差 4.3 倍。**若内容结构变化（例如出现大量已压缩内容、加密内容、或高熵二进制），比值会显著回落。** 必须按月复测。

### 13.3 不同方案的容量账

计算过程（分母用日增原始量）：

```
今日原始产出     89,669 条/天 × 890 KB = 79.8 GB/天 = 74.3 GiB/天
某压缩比 r 的日增 = 74.3 GiB/天 ÷ r
可撑天数         = 239.6 GiB ÷ (74.3 GiB/天 ÷ r)

r =  9×   ⇒ 日增  8.26 GiB/天 ⇒ 239.6 ÷ 8.26  = 29.0 天
r = 10.26× ⇒ 日增  7.24 GiB/天 ⇒ 239.6 ÷ 7.24  = 33.1 天
r =  5.41× ⇒ 日增 13.74 GiB/天 ⇒ 239.6 ÷ 13.74 = 17.4 天   ← Go 库口径
```

| 本设计 + 冷层月度合并（估算再 -65%，**未实测**） | ≈2.9 GiB/天 | ≈83 天 |
| 上面 + 子项目 1 榨干（+120 GiB） | ≈2.9 GiB/天 | ≈124 天 |

**口径标注**：`74.3 GiB/天` 与 `239.6 GiB` 是实测；`2.77× / 5.41× / 10.26×` 是实测；`9×`（及其 29 天）是外推的规划口径；`33.1 天`（10.26×）是把**难压样本**实测值直接当整体用的**保守下界**（整体比值只会更高，因为其余日子都比 09-18 易压）；`17.4 天`（5.41×）是方案 C 被推翻时的对照值。

**较上一版（21 天）提升约 38%**，来源是窗口参数被实测修正；而相对「编码用 Go 库」的 17.4 天，方案 C 又提升了约 67%。

### 13.4 诚实结论

**「不删除」在 589 GiB 的盘上，天花板是几十天量级。** 一年需要约 1.8 TiB。

这不是本设计的缺陷——本设计让**日增从 64 GiB 降到 7.24~8.26 GiB（改善约 7.7~8.8 倍）**，且 `/data` 完全止血。但**单调增长的算术没有被消除**，只是被推远了。

**唯一能真正实现长期「不删除」的路径是扩容或改用对象存储。** 本设计的定位键与目录布局都不绑定本地文件系统，存储后端可在后续子项目中替换为对象存储实现。

### 15.1 计划 2（网关接入）的对端要求（R8 / R9）

本计划（存储原语）只交付 `internal/tracearchive` 的写入器与封块器；下面两条**不是**本计划的交付物，而是已交付原语**对计划 2（网关接入）提出的要求**。之所以登记在规格里：任务 5/6 的实现已把前提写进代码注释，若计划 2 不满足，本规格的安全性结论就不成立。

| # | 要求 | 依据与后果 |
|---|---|---|
| **R8** | 网关必须**自己周期滚动 part**（拿到新 part 即关闭旧 fd），且**滚动间隔 ≤ 1h**（**严格小于** sealer 的 `minAge` = 3h） | §7.2 的 `minAge` 是 sealer 侧唯一的保护。**D7 缺口**：网关与 sealer 之间**没有信号通道**，sealer 封块后会**删除 spool**，而网关若继续往同一 part 追加，字节会写进**已 unlink 的 inode** ⇒ 落盘却永久不可达（其 `Ref` 仍指向一个行数更少的产物）⇒ **永久丢失正文**。**缓解不充分之处**：流量停 15 分钟后恢复正是触发条件（spool 的 mtime 早已超过 `minAge`，sealer 认为「已停止追加」，而网关仍持有旧 fd 且未滚动）。注意 `defaultSealInterval = 15m` 只是一个**与滚动间隔同名但本身不滚动任何 part** 的常量——滚动动作必须由计划 2 实现 |
| **R9** | **背压**：磁盘满时网关应**放弃正文并标 `body_missing=true` 继续服务**，而不是持续重试写盘 | §7.1 的【已知代价】正是这一条的依据：否则每个请求都要走一遍「写失败 + 反向扫描 + 改名」，且块序号与目录项**无界增长**、每次 `Append` 付一次 O(n) 目录扫描。这也是本计划**刻意不加计时器/计数器**的原因——正确修法属计划 2 |

**另有一条可选优化（登记备查，非要求）**：`PendingSeals` 持锁做最多 1 MiB 的 `Flush`，与请求路径的 `Append` 争**同一把锁**（`w.mu`）；慢盘 / ENOSPC 时 flush 延迟会被加到请求路径上。要彻底消除需把 flush 与请求路径解耦（独立 flush 协程或双缓冲），不在本计划内。
