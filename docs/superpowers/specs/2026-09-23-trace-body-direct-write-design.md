## 1. 背景与问题

### 1.1 现状

`call_traces` 的正文（`request_headers` / `request_body` / `response_body` 三个 jsonb 列）直接写入 PostgreSQL，落在 `/data`。

2026-09-23 生产事故：`/data` 可用空间跌至 **7.03 GiB**（98% 占满），正文导致 TOAST 膨胀到 **315 GB**，网关 trace 写入被拒绝，**断流 23 小时 15 分钟，损失约 14 万条 trace**。

应急处置完成了三个动作：导出 14 天正文（595.11 GiB → 127.62 GiB zstd，4.66x）到 `/datalog`、置空 1,539,827 行正文、手动 VACUUM。`/data` 从 7.03 GiB 恢复到 297 GiB。

**但这是止血，不是治本**：网关恢复写入后，`/data` 以约 **37 GiB/天** 重新增长。

### 1.2 根因

**正文的家在 `/data`。** 只要正文先落 PG，`/data` 就必然被撑满；事后归档是补偿措施，且代价是同一份数据**存两份**（PG 一份 + 归档一份）。

### 1.3 本设计要做的

把正文的家从 `/data` 搬到 `/datalog`：**写入时直接落盘，PG 只保留元数据与定位键。**

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 可验证形式 |
|---|---|---|
| G1 | 正文不再进入 PG | 新增行的 `request_body`/`response_body`/`request_headers` 恒为 NULL |
| G2 | `/data` 不再被正文撑大 | 元数据行约 40 字节/行 ⇒ 增速降至 < 1 GiB/天 |
| G3 | 正文可原样读回 | 给定 `request_id` 取回正文，**逐字节**等于写入前 |
| G4 | 磁盘满时不拖垮服务 | 退化到只记元数据 + 明确告警，网关继续服务 |

| G6 | 存储格式对冷层合并留有余地 | 定位键 `(dt, inst, part, row)` 在合并后依然有效（§13） |

- 管理后台 UI 接入（子项目 3）

## 4. 架构与数据流

### 4.1 数据流

```
请求完成
  │
  ├─ TraceEvent.Emit()                                  ← 不变
  │
  ▼
TraceWriter.Run()  消费事件
  │  ① 序列化为一整行 JSON（字段与顺序对齐现有归档格式）
  │  ② 追加明文到 spool
  │  ③ 记录 (dt, inst, part_seq, row_seq)
  │  ④ 写 PG 元数据行（含定位键）
  │
  ▼
封块协程（独立 goroutine；30s 轮询 + 阈值信号）
  │  ⑤ 命中封块条件 → 流式 zstd 压缩 spool
  │  ⑥ 生成内嵌索引 → 写 trailer + footer
  │  ⑦ fsync → 原子 rename
  │  ⑧ 确认产物落稳 → 删除 spool
```

**关键性质：正文从进入系统到落盘，全程不经过 PG。**

### 4.2 组件划分

| 组件 | 位置 | 职责 | 依赖 |
|---|---|---|---|
| `internal/tracearchive`（新包） | 新增 | 存储格式：spool 追加、封块压缩、内嵌索引读写、按定位键取正文 | 标准库 + `klauspost/compress/zstd` |
| `TraceWriter` 改造 | `internal/gateway/observability/trace_event.go` | 正文交给 `tracearchive`，PG 只写元数据 | `tracearchive` |
| 封块协程 | 新增（随 gateway 启动） | 定时 + 阈值触发封块 | `tracearchive` |
| 点读服务 | `internal/observability/service/` | 按 `request_id` 定位并取回正文 | `tracearchive` |
| 点读接口 | `internal/controlplane/handler/` | 两个 HTTP 端点 | 点读服务 |
| CLI | `cmd/trace-body/`（新） | 运维与验收工具 | 点读服务 |

**边界清晰性检查：** `internal/tracearchive` 不依赖 PG、不依赖 gin、不依赖任何 gateway 代码——可以只读它的接口文档就理解用途，可以独立单元测试。这是本设计最重要的解耦点。

### 4.3 复用来源

`internal/archive` 包（分支 `feat/trace-archive-v3`）中的存储层**自包含**（仅依赖标准库 + `klauspost/compress/zstd`），可整体复制为本设计的起点：

| v3 文件 | 复用方式 |
|---|---|
| `partwriter.go` | **直接复用**：spool 先落盘再流式压缩、原子 rename |
| `local.go` | **直接复用**：存储层与并发闸 |
| `store.go` | 复用接口定义 |
| `index.go` | 复用 codec 参数校验（级别/窗口） |
| `readbody.go` | **需重写**：其前提是"按 `request_id` 排序写 + 二分"，本设计的写入为乱序到达，前提不成立（§5.4） |

> 依赖变更：新分支需新增 `github.com/klauspost/compress/zstd` 并 `go mod vendor`（仓库使用 vendor 构建）。

## 5. 存储格式规格

### 5.1 目录布局

```
/datalog/trace-archive-v4/                       ← 新根，不碰任何现有目录
  dt=2026-09-24/
    inst=blue/
      part-000000.jsonl.zst                      ← 已封块产物
      part-000000.jsonl.zst.tmp                  ← 写入中（rename 前）
    inst=green/
      part-000000.jsonl.zst
  spool/
    dt=2026-09-24/
      inst=blue/part-000001.jsonl                ← 明文，封块成功后删除
```

按 `inst` 分目录的理由：`llm-blue-gateway` 与 `llm-green-gateway` **在生产中同时 Up**，切流期间两者都可能写。按实例隔离，天然不冲突，切流后旧实例的块自然封口。

### 5.2 产物文件物理布局

```
┌─────────────────────────────────────────────────────┐
│ zstd 单帧                                            │
│   全部行的 JSONL 顺序拼接                             │
├─────────────────────────────────────────────────────┤
│ trailer：索引表                                       │
│   条目：row_seq → row 在【未压缩流】中的起始字节偏移    │
│   编码：按偏移升序做差分 + varint                     │
├─────────────────────────────────────────────────────┤
│ footer：32 字节定长                                   │
│   magic(4)="TBA4" | format_version(2)               │
│   | trailer_offset(8) | trailer_len(4)              │
│   | frame_sha256[:8](8) | reserved(6)               │
└─────────────────────────────────────────────────────┘
```

**字段精确定义：**

| 字段 | 含义 |
|---|---|
| `row 起始字节偏移` | 该行第一个字节在**未压缩** JSONL 流中的位置（行首，不含前一行换行符） |
| `frame_sha256[:8]` | 对 **zstd 帧字节**（不含 trailer/footer）计算的 SHA-256 前 8 字节 |
| `format_version` | 当前为 1；冷层合并若扩展索引键为 `(dt, part, row)`，由此字段区分 |

**设计要点：**

- **footer 定长且位于文件末尾** ⇒ 读它只需 `pread` 末尾 32 字节，**不需要解压任何数据**即可知道索引在哪。
- **trailer 在 zstd 帧之外** ⇒ 否则读索引就得先解压全帧，索引的意义就没了。
- **索引与内容出自同一次封块操作** ⇒ 不可能不同步。这直接消灭了事后归档方案的 F2 缺陷（外部 `index.jsonl` 丢失导致点读全部 miss 却表现为"数据不存在"）。
- **`format_version` 是冷层扩展的锚点**（§5.5）——超级文件只需提升版本号并换用扩展索引键，读取侧按版本分派。

### 5.3 压缩选型与封块参数

#### 5.3.1 算法选型

| 候选 | 通用文本压缩比 | 压缩速度 | 解压速度 | 判决 |
|---|---|---|---|---|
| snappy | 1.5~2.0× | 250~500 MB/s | 1~2 GB/s | ✗ 比为极致速度设计，压缩比不足 |
| lz4 | 1.8~2.5× | 400~700 MB/s | 3~5 GB/s | ✗ 解压快，但我们的瓶颈是**磁盘容量**不是解压速度 |
| gzip/zlib | 2.5~3.5× | 20~40 MB/s | 250~400 MB/s | ✗ 比 zstd 慢约 25 倍、压缩比还低约 15%，两头不占 |
| zstd -3 | 2.5~3.5× | 300~500 MB/s | 1~2 GB/s | ✗ 实时场景选择，我们后台压缩不需要这个速度 |
| **zstd -19** | **4.0~6.0×** | 3~10 MB/s | 1~2 GB/s | ✅ **选定** |
| zstd -22 | 4.5~7.0× | 1~3 MB/s | 1~2 GB/s | ✗ 比 -19 仅多 10~16%，压缩耗时增 1.7 倍且内存更高 |

**关键性质（决定点读体验）**：zstd 的**解压速度几乎与压缩级别无关**。因此选 -19 只付出压缩侧代价，**点读延迟与选 -3 相同**。

参考：[CERN ZSTD 材料](https://indico.cern.ch/event/860690/contributions/3624882/attachments/1947679/3231550/ZSTD_compression_algorithm_in_ROOT.pdf)、[多编解码器对比研究](https://arxiv.org/pdf/2602.03839v2)。

**⚠️ 外部资料甄别**：评审期间曾出现一份声称 zstd -9 = 93.6×、-19 = 122.2× 的对照表。**该表不可用于本决策**：

```
· 其定性结构正确（解压速度与级别无关、压缩耗时随级别上升、全部无损）
· 但其压缩率为本设计实测值的 10~25 倍
· 其解压速度 6772~8157 MB/s 属"小样本全部驻留 CPU 缓存"的量级
· 其自述为"从记忆里补齐"，即非实测

本设计一律采用本节列出的自有实测值。
```

#### 5.3.2 杠杆排序（实测，**随内容结构变化**）

**核心结论：杠杆的重要性排位不是固定的，取决于数据里重复是"近距离"还是"远距离"。**

```
难压数据（embedding 为主）    ① 窗口  > ② 合并  > ③ 级别
易压数据（文本/排障为主）     ① 合并  > ② 级别  > ③ 窗口
```

**09-18（embedding 为主，难压）上的完整扫描**——这是最需要压缩、也最能反映未来流量的一类：

| 配置 | 产物 | 比值 | 对现状 |
|---|---|---|---|
| 现状：256 MB 分块 + Go `better` | 559 MB | 3.71× | — |
| 合并单流 · -9 · 窗口 128 MB | 432.5 MB | 4.81× | -22.8% |
| 合并单流 · -19 · 窗口 128 MB | 397.1 MB | 5.23× | -29.1% |
| 合并单流 · -9 · 窗口 256 MB | 319.7 MB | 6.50× | -42.9% |
| 合并单流 · -9 · 窗口 512 MB | 224.8 MB | 9.25× | -59.8% |
| **合并单流 · -19 · 窗口 512 MB** | **202.6 MB** | **10.26×** | **-63.8%** |
| 合并单流 · -9 · 窗口 1024 MB | 180.9 MB | 11.49× | -67.7% |
| **合并单流 · -19 · 窗口 1024 MB** | **164.3 MB** | **12.65×** | **-70.7%** |
| 合并单流 · -9 · 窗口 2048 MB | 153.3 MB | 13.56× | -72.6% |

**增量收益拆解（难压数据）：**

```
① 窗口 128 → 512 MB          -47.9%   ★ 最大
② 合并单流（256MB 分块 → 单流） -22.8%
③ 窗口 512 → 1024 MB         -19.1%
④ 级别 -9 → -19（512MB 窗口）  -9.9%
```

**09-13（文本为主，易压）上同样的杠杆却是另一个排序：**

| 配置 | 产物 | 比值 | 对现状 |
|---|---|---|---|
| 现状：256 MB 分块 + Go `better` | 140.7 MB | 14.6× | — |
| 合并单流 · -9 · 128 MB 窗口 | 76.0 MB | 28.3× | -46.0% |
| 合并单流 · -19 · 128 MB 窗口 | 63.2 MB | 34.0× | -55.1% |

```
① 合并单流     -46.0%   ★ 最大
② 级别 9 → 19  -16.8%
③ 窗口 128 → 1024 MB  -12.9%   ← 在易压数据上窗口几乎不值钱
```

**⚠️ 这一节是设计过程中被实测推翻后重写的**，见 §5.3.3 的修正说明。**不能用单一易压样本外推窗口的价值**——这正是早期版本犯的错。

#### 5.3.3 参数终值

| 参数 | 值 | 依据 |
|---|---|---|
| **块大小阈值** | 暂定 1536 MB，由 U1 实验定稿 | 最大杠杆，见 5.3.2 |
| **时间阈值** | 15 分钟（**凭直觉设定，无实测依据**） | 低峰天若不按时间封块，块永远达不到大小阈值 ⇒ 正文写了却读不到。**若近期正文的可读性要求更严，此值须下调，代价是块变小、压缩比下降** |
| **zstd 级别** | **19** | 5.3.1 选型结论 |
| **zstd 窗口** | **512 MiB**（可配置；实测内存 852 MB，见下） | §5.3.2：难压数据上窗口是**第一杠杆**（128→512 MiB 值 -47.9%） |
| **`EncoderConcurrency`** | **1** | 多并发会把流切成独立块，显著削弱压缩比 |
| **编码器实现** | 不可直接复用 v3 `partwriter` 的默认配置 | 实测 Go 库 `better` 产物比 CLI 同级别大约 20~30%，需重新校准 |

**⚠️ 窗口参数的两次修正（设计过程中被实测推翻两次，如实记录）**

```
第 1 版：窗口 ≥ 块大小（1~2 GB）
  理由：窗口越大压缩越好
  推翻：无内存依据，纯假设

第 2 版：窗口 128 MiB
  理由：易压样本（09-13）显示窗口只值 13%
        + 估算"1 GB 窗口需 2~3 GB 内存，网关放不下"
  推翻：两个理由都是错的 ——
        · 难压数据（09-18）上窗口值 -47.9%，不是 13%
        · 1 GB 窗口实测 1190 MB，不是 2~3 GB（估算高估一倍多）

第 3 版（本版）：窗口 512 MiB
  依据：以下全部为实测
```

**zstd 编码器峰值 RSS 实测**（输入 1.03 GB，确保窗口被填满；`VmHWM` 采样）：

| 窗口 | -9 峰值 RSS | -19 峰值 RSS | 2 GiB 限额余量（-19） |
|---|---|---|---|
| 128 MiB | 162 MB | — | — |
| 256 MiB | 298 MB | — | — |
| **512 MiB** | 570 MB | **852 MB** | **1196 MB** ✓ 安全 |
| 1024 MiB | 1105 MB | **1190 MB** | 858 MB △ 可行但紧 |
| 2048 MiB | 2204 MB | — | ✗ 超限 |

**规律：RSS ≈ 窗口 × 1.08（-9）；-19 在 512 MiB 窗口上额外 +282 MB。**

**为什么取 512 MiB 而不是 1024 MiB：**

```
1024 MiB 窗口比 512 MiB 只多压 7%（-70.7% vs -63.8%）
但内存多 338 MB，2 GiB 限额余量从 1196 MB 降到 858 MB
而 Go 库（klauspost/compress）的内存行为尚未实测（U8），
它还要叠加 Go 运行时自身的堆开销 —— 保守留余量
512 MiB 是可配置值，U8 实测后若确认 Go 库开销与 C 版一致，可上调至 1024 MiB
```

**⚠️ 内存计量的适用边界**：以上全部是 **C 版 zstd CLI** 的数据。Go 库用 `WithWindowSize` 表达同样的语义，但两者的缓冲分配策略是否一致**未经实测**，见 U8。

**⚠️ 编码器校准的口径冲突（诚实标注）**

设计期间对"Go 库 `better` 比 CLI 同级别大多少"出现过两个口径（一个约 -22%，一个约 -26%），**二者不一致，本设计不采信任一具体值**，只保留"约 20~30%"的区间。实施阶段必须以同数据、同级别复测并钉死，作为编码器选项调优的依据。

#### 5.3.4 块大小的定稿规则（U1 实验）

```
用生产真实数据（含 embedding 大正文，不可只用 09-13 那类易压样本）测：
  候选块大小 B ∈ {256 MB, 768 MB, 1536 MB, 3072 MB}
  对每个 B 测两个量：
    r(B) = 压缩比
    l(B) = 点读 P99 延迟
  选【满足 l(B) ≤ 1.5 秒 的最大 B】

若 3072 MB 仍满足延迟约束，则取 3072 MB，并重新评估上限。
内存约束：窗口固定 512 MiB（§5.3.3），与 B 无关；spool 已在磁盘，故 B 不受网关内存限制。
```

依据：D3 明确"优先压缩比"，因此在不突破延迟约束的前提下取最大块。

### 5.4 为什么定位键不是字节偏移

```
压缩后的字节偏移只有在封块结束那一刻才知道。
若要在写入时就把偏移写进 PG，就必须在封块后回填 UPDATE
  → 每天约 9 万次 UPDATE
  → 且形成"PG 元数据 ↔ 产物文件"的双向依赖，失败语义复杂化
```

**因此定位键为 `(dt, inst, part_seq, row_seq)`**：四个分量在写入追加时即可确定，无需回填。

### 5.5 冷层合并的格式预留（本期不实现）

冷层若要按月合并成超级文件，其索引只需从 `row_seq → offset` 扩展为 `(dt, part_seq, row_seq) → offset`。

**PG 中已存的定位键无需任何修改，也不需要回填 UPDATE。** 这是把定位键设计成复合键而非物理偏移的核心收益。

## 6. PG schema 变更

```sql
-- atlas 迁移：atlas-migrations/<timestamp>_add_trace_body_ref.sql
ALTER TABLE call_traces
  ADD COLUMN body_ref_dt     date,
  ADD COLUMN body_ref_inst   text,
  ADD COLUMN body_ref_part   integer,
  ADD COLUMN body_ref_row    integer,
  ADD COLUMN body_missing    boolean NOT NULL DEFAULT false,
  ADD COLUMN body_bytes      integer;
```

**`body_bytes` 的定义**：写入时 `len(request_headers) + len(request_body) + len(response_body)`（**原始字节数**，与现有 `TraceWriter` 的 `traceEventBodyBytes` 口径一致）。用途：审计与压缩比核算，不参与业务逻辑。

**说明：**

- 现有 `request_body` / `response_body` / `request_headers` **保留列、不删**。新行恒为 NULL。理由：删列要重写 557 万行的表，代价高且无收益；保留也维持了对历史代码与查询的兼容。
- **不加新索引。** 点读仍走现有 `call_traces_pkey`（按 `request_id`）；定位键只是随行返回的附加列。
- 迁移使用 PG 11+ 快速默认值，**不触发表重写**。
- schema 改动必须走 `atlas-db-migration` skill（仓库存量规则）。

## 7. 写入路径

### 7.1 追加（请求路径上，必须极快）

```
1. 序列化为一行 JSON
2. 追加到 spool 文件（带缓冲）
3. row_seq = 当前块内自增计数
4. 组装元数据行（含定位键）
```

**请求路径上只做顺序追加，不做压缩**——压缩全部在后台协程完成。理由：网关是延迟敏感路径；且磁盘顺序追加的成本远低于压缩。

### 7.2 封块（后台协程）

```
触发条件：spool 大小 ≥ block_bytes  或  距上次封块 ≥ block_interval
  或  进程关停（尽力封块）

步骤：
  1. 打开读 spool，流式喂给 zstd encoder，边压边写 .tmp
  2. 压缩过程中累积 row_seq → 未压缩偏移
  3. 写 trailer（差分 varint）
  4. 写 footer
  5. fsync(.tmp)
  6. rename(.tmp → part-NNNNN.jsonl.zst)
  7. fsync(目录)
  8. 删除 spool 文件（**必须在第 6、7 步成功之后**）
  9. 推进写指针（幂等，见 §7.3）
```

**并发封块**：同一 `(dt, inst)` 同时只允许一个封块动作（进程内互斥）。跨进程不存在冲突——`inst` 已隔离。

### 7.3 写指针的位置（幂等性的锚点）

写指针用于确定"下一个 `part_seq` 是多少"，必须满足 I4（同一 `(dt, inst, part_seq)` 只被封块一次）。

```
权威来源：产物目录的实际内容
   next_seq = max( 目录中已存在的 part-NNNNN.jsonl.zst 的 NNNNN ) + 1
             以及 spool 中已存在的 part-NNNNN.jsonl 的 NNNNN

规则：
  · 进程启动时扫描一次目录建立内存态
  · 运行时由内存态自增
  · 每次封块前用 spool 文件名中的 seq（即权威值）写入，而非内存计数

不引入 PG 表或独立指针文件：目录内容本身即指针，少一个需要保持一致的状态。
若产物已存在（重复封块），则【拒绝覆盖】并告警——宁可留下 spool，不可覆盖唯一副本。
```

## 8. 读取路径

### 8.1 最小闭环接口

```
GET /internal/v1/trace-body?request_id=<uuid>      InternalAuth（网关/内部调用）
GET /api/v1/trace/:request_id/body                 JWTAuth（管理面调用）

响应：
  200 + 正文 JSON
  404 + body_missing=true        正文写入时即失败，从未落盘
  410 + body_missing=true        正文曾落盘但产物缺失（需人工介入）
  500 + 明确诊断                  区分"文件缺失"与"从未归档"
```

### 8.2 读取算法

```
1. 按 request_id 查 PG → (dt, inst, part, row, body_missing)
2. body_missing = true               → 410/404
3. <root>/dt=<dt>/inst=<inst>/part-<part>.jsonl.zst 存在
     → 读末尾 32 字节 footer
     → 校验 magic；读 trailer；二分查 row → 解压后偏移 off
     → 流式解压，累计到 off 后取该行（读到目标行立即停止）
4. 否则明文 spool 存在
     → 路径：<root>/spool/dt=<dt>/inst=<inst>/part-<part>.jsonl
     → 按 row_seq 顺序读取第 row_seq 行（无需索引：行号即顺序）
5. 都不存在                          → 500 + 诊断
```

**第 3/4 步天然无竞态**：spool 只在产物 `fsync` + `rename` + 目录 `fsync` 全部成功后才删除（§7.2 第 8 步），因此任何时刻**恰好有一个存在**。

**未封块的近期 trace 直接读明文**，无需等待封块。这解决了"大块 ⇒ 近期正文读不到"的体验问题。

### 8.3 读取的空间硬约束（强制性）

以下四条是**规格级强制要求**，不是建议。违反任意一条都会造成"读取导致磁盘持续增长"：

| # | 约束 | 理由 |
|---|---|---|
| C1 | **流式解压到内存，命中目标行立即停止** | 峰值内存 ≈ 一行正文（约 880 KB），与块大小无关 |
| C2 | **不落任何临时文件** | 禁止"解压到 /tmp 再读"的实现 |
| C3 | **不缓存已解压的块** | 禁止为加速而缓存块内容 |
| C4 | **读 spool 直接 seek，不复制** | 明文 spool 原地读 |

**补充说明（POSIX 语义）**：读取期间该文件被并发删除是安全的——已打开的 fd 仍可读。因此 C1~C4 下，**任意次读取对磁盘占用的增量恒为 0**。

### 8.4 解码侧的内存约束（大窗口的连锁代价）

⚠️ **窗口参数（§5.3.3 的 512 MiB）不只影响写入侧，也影响读取侧：**

```
zstd 解码器内存占用 ≈ 压缩时使用的窗口大小
  写入用 512 MiB 窗口  ⇒  每次点读的解码器需约 512~600 MB
```

而这发生在 **control-plane**（2 GiB 限额）中，与 §8.3 的 C1（流式解压）叠加：

| # | 约束 | 值 |
|---|---|---|
| C5 | **点读并发数必须有上限** | 按 600 MB/并发估算：2 GiB 限额下最多 **2 个并发点读**，超出须排队 |
| C6 | **读 spool 明文路径不受此限** | 它不涉及解压，无窗口内存开销 |

**这是选择大窗口换压缩比的真实代价：它同时抬高了写入侧与读取侧的内存门槛。** 若 U8 实测表明 Go 库开销高于 C 版，或点读并发瓶颈不可接受，则须下调窗口（每降一档约损失 15~20% 压缩比，见 §5.3.2）。

## 9. 失败语义与降级

### 9.1 事件级

| 情形 | 行为 | 数据后果 |
|---|---|---|
| spool 追加失败（盘满/权限） | 该行标 `body_missing=true`，**元数据行照写** | 正文丢失，元数据（延迟/错误）保留 |
| PG 写入失败 | 沿用现有逻辑：批量降级逐条，坏记录跳过 | 沿用现状 |

### 9.2 块级

| 情形 | 行为 |
|---|---|
| 压缩 / fsync / rename 失败 | **保留 spool**，下轮重试；连续失败 N 次告警，**绝不删 spool** |
| 磁盘水位超过 `disk_watermark_percent` | 停止接收新正文（标 `body_missing=true`），元数据照写，告警 |
| 产物 footer 校验失败 | 读取返回 500 + 诊断，**不静默返回"不存在"** |

### 9.3 关键设计意图

**磁盘满时系统退化到"只记元数据"，而不是像 2026-09-23 那样把整个服务拖垮。**

- 可用性优先于正文完整性
- 退化事件有明确可观测信号（`body_missing` 速率）
- 元数据（`request_id` / `ts` / 阶段耗时 / `error_code`）几乎不占空间，可继续记录

## 10. 不变量与崩溃窗口分析

### 10.1 不变量

| # | 不变量 |
|---|---|
| I1 | 元数据行存在 ⇒ (产物文件 XOR spool 文件 存在) 或 `body_missing=true` |
| I2 | 产物文件只能通过 `rename` 出现，永不出现半个文件 |
| I3 | 产物的内容与内嵌索引出自同一次封块操作，不可能不同步 |
| I4 | 单个 `(dt, inst, part_seq)` 只被封块一次（写指针 + 幂等） |
| I5 | 删 spool 之前必须已确认产物 `fsync` 成功且目录 `fsync` 成功 |

### 10.2 崩溃窗口

| 崩溃时刻 | 盘上状态 | PG 状态 | 后果 | 处理 |
|---|---|---|---|---|
| 追加后、PG 写入前 | spool 有该行 | 无元数据行 | **孤儿正文**（无害） | 定期清理（可选） |
| PG 写入后 | spool 有该行 | 有元数据行 | 正常 | 封块后转产物 |
| 压缩中 | `.tmp` 残留 | 有元数据行 | spool 仍在，下轮重试 | 启动时清理 `.tmp` |
| rename 后、删 spool 前 | 产物 + spool 都在 | 有元数据行 | 读取优先产物，无害 | 下轮封块发现 spool 已被处理 |
| 删 spool 后 | 只有产物 | 有元数据行 | 正常 | — |

**关键性质：任何崩溃点都不会出现"元数据行指向不存在且不可恢复的正文"。** 最坏情况是孤儿正文（占用空间，可清理）或 spool 残留（下轮重试）。

## 13. 容量与保留期

### 13.1 现状账（实测）

```
/datalog 总计 589.5 GiB   已用 319.9   可用 239.6
  /datalog/archive            189 GiB  遗留 gzip（唯一副本）
  /datalog/emergency-archive  128 GiB  本次 zstd 归档（14 天）
  /datalog/backup             2.2 GiB
  杂项（p0-bench/leakscan-*） 约 1.6 GiB

实测增速（2026-09-23）：89,669 条/天，行均原始 890 KB
```

**实测压缩比（14 天归档，256 MB 分块 + Go `better`）——跨度极大：**

```
09-18  3.48×  ← 最难压（embedding 为主）
09-20  3.61×      09-15  4.88×      09-11  5.75×      09-12  8.18×
09-21  3.72×      09-16  5.29×      09-10  5.51×      09-19  9.59×
09-22  4.59×      09-17  5.30×      09-09  6.20×      09-13 14.80×  ← 最易压
                      09-14  5.33×
────────────────────────────────────────────────────────────────────
整体 4.66×        行均原始 405 KB → 行均压缩 87 KB
```

**⚠️ 压缩比是流量的函数，不是一个可钉死的常数。** 同一份数据在不同日期的比值差 4.3 倍，取决于当天 embedding 请求的占比。**必须按月复测。**

### 13.2 预期压缩比（本设计）

```
预期比 = 内容基线 × 调优增益（-19 级别 + 512 MiB 窗口 + 大块单流）

内容基线（实测）
  难压天（embedding 为主）  3.48×
  整体 14 天                 4.66×
  易压天（文本为主）        14.80×
  今天（09-23）              2.77×

预期结果
  难压天    3.48×  →  约 9.6×    （由 09-18 实测 10.26× 折算，可信度高）
  整体      4.66×  →  约 9×      ← 规划口径
  易压天   14.80×  →  约 30×     （估算，未直接实测）
```

**规划口径取 9×**（较上一版的 6.5× 上调，因为窗口这个第一杠杆此前被严重低估）。

**但必须保留的警告**：压缩比是流量的函数。实测同盘不同日差 4.3 倍。**若内容结构变化（例如出现大量已压缩内容、加密内容、或高熵二进制），比值会显著回落。** 必须按月复测。

### 13.3 不同方案的容量账

以今日原始产出 79.8 GB/天（89,669 条 × 890 KB）计：

| 方案 | 日增 | 239.6 GiB 可撑 |
|---|---|---|
| 今天（正文进 PG + 归档副本，2.77×） | 64 GiB/天 | **3.7 天** |
| 本设计，按旧口径（2.77×） | 27 GiB/天 | 8.9 天 |
| **本设计，实测规划口径 9×** | **8.3 GiB/天** | **29 天** |
| 本设计 + 冷层月度合并（估算再 -65%，**未实测**） | ≈2.9 GiB/天 | ≈83 天 |
| 上面 + 子项目 1 榨干（+120 GiB） | ≈2.9 GiB/天 | ≈124 天 |

**较上一版（21 天）提升约 40%**，来源是窗口参数被实测修正。

### 13.4 诚实结论

**「不删除」在 589 GiB 的盘上，天花板是几十天量级。** 一年需要约 1.8 TiB。

这不是本设计的缺陷——本设计让**日增从 64 GiB 降到 5~13 GiB（改善 5~13 倍）**，且 `/data` 完全止血。但**单调增长的算术没有被消除**，只是被推远了。

**唯一能真正实现长期「不删除」的路径是扩容或改用对象存储。** 本设计的定位键与目录布局都不绑定本地文件系统，存储后端可在后续子项目中替换为对象存储实现。
