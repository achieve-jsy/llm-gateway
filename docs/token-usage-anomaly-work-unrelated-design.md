# 严重异常 3.6「与工作无关占比过高」· 内容语义判断完整设计

> 目的：把 v0.6 §3.6 落成可实现方案。它是**五种用法问题之外的单独一条**，必须出现在部门/工作室报告并置顶。
> 与 3.2/3.3 的语义判断**不能复用**：3.6 指向「个人可能拿公司资源干私事」，合规敏感度高一个量级，且**结论天花板永远是「待核查」，绝不自动认定违纪**。
> 前提沿用：GLM5.3-flash 量化版（512K），口径 A（大模型只作证据），本文额外收紧红线。
> 配套：`session-content-analysis-design-v2.md`（3.2/3.3 语义）、`context-analysis-design.md`（元数据）。

---

## 0. 红线（先写死，比其他五类都硬）

1. **不认定违纪**：v0.6 原文「Token 只能给线索，不能自动认定为违纪；现阶段标『待核查』，由负责人确认」。→ **无论时间窗还是大模型判定，结论天花板都是「待核查」**，系统永不输出「违规/滥用/私用」定论。
2. **大模型判「非工作」≠ 定性**：大模型输出只是**给负责人排优先级的线索**，不是「升级为定性」（这点和 3.2/3.3 不同——那两个双条件可升定性，3.6 双条件也只到待核查）。
3. **合规前置**：读正文判「是否私人事务」比判「任务切换」更敏感，PII/审计/权限要求更高，上线必须过合规评审，且默认关闭。
4. **可申诉**：每条待核查对被指向的个人可见、可申诉，负责人终裁并回写状态。
5. **排除优先**：已备案（夜间批处理/跨时区/发布值班）先排除，宁可漏报不可误伤。

---

## 1. 两层判定（时间窗 → 内容语义）

v0.6 给的「可计算口径」有两种，分两层，大模型只在层 2：

| 层 | 判据 | 用大模型 | 产出 |
| --- | --- | :--: | --- |
| 层1 时间窗（v0.6 主口径） | 凌晨/周末 + 未备案的消耗占比 > 20% | ❌ | 金额、占比、时段、模型、Key |
| 层2 内容语义（v0.6「明显非工作场景」） | 读正文判这批消耗内容是否明显私人 | ✅ | 证据信号 work_related/not_work/uncertain |

**层1 单独就能产出「待核查」**（v0.6 认可的可计算口径）。层2 是**给负责人加线索、排优先级**，不是定罪。

---

## 2. 层1 · 时间窗判定（元数据，免费，不读正文）

### 2.1 无关消耗口径

```sql
-- 个人维度（排除 Service Key），按上海时间判定时段
WITH u AS (
  SELECT user_id, user_name,
    SUM(est_cost_usd) AS total_cost,
    SUM(est_cost_usd) FILTER (
      WHERE EXTRACT(hour FROM ts AT TIME ZONE 'Asia/Shanghai') < 7        -- 00:00–07:00
         OR EXTRACT(dow  FROM ts AT TIME ZONE 'Asia/Shanghai') IN (0,6)   -- 周末
    ) AS offhours_cost,
    array_agg(DISTINCT model) AS models
  FROM call_logs
  WHERE ts >= :from AND ts < :to_excl
    AND (COALESCE(NULLIF(key_type,''),'personal') <> 'service')
    AND (:scope_where)
  GROUP BY user_id, user_name
)
SELECT *,
  offhours_cost / NULLIF(total_cost,0) AS unrelated_ratio
FROM u
WHERE offhours_cost / NULLIF(total_cost,0) > 0.20;   -- >20% 阈值
```

### 2.2 排除备案（不误伤）

命中后先扣除已备案部分：

```sql
-- offhours_filing：user_id / dept_id / key_id + 时间范围 + 类型(批处理/跨时区/值班)
LEFT JOIN offhours_filing f
  ON f.subject_id = cl.user_id AND cl.ts BETWEEN f.start_at AND f.end_at
-- 命中备案的消耗从 offhours_cost 里剔除
```

无备案表阶段（P0）：`excluded` 里写明「未接备案表，跨时区/值班可能误报」，结论仍只到待核查。

### 2.3 层1 产出

| 指标 | 口径 |
| --- | --- |
| unrelated_cost | 未备案的非工作时段消耗金额 |
| unrelated_ratio | unrelated_cost ÷ 个人总成本（> 20% 命中） |
| top_hours / top_model / top_key | 主要时段/模型/Key |
| status | `pending_review`（待核查） |

## 3. 层2 · 内容语义判定（大模型，只对层1命中者，读那批消耗的内容）

### 3.1 只判「层1 已命中」的那批消耗

- 不全量读正文；只对**层1 命中的用户、且命中的那批非工作时段消耗**读内容。
- 从这批消耗对应的会话里，取正文（`call_traces`，三态回读，复用 v2 §3 抽取），抽「用户意图指纹」。
- 目的：判这批凌晨/周末的消耗，**内容像工作还是像私事**。

### 3.2 送 GLM5.3-flash（判工作/非工作，不做内容评价）

**system prompt**：
```
你是资源用途分类器。仅根据用户请求的意图，判断这批请求整体更像“工作相关”还是“明显的私人/非工作事务”。
- work_related：编程、调试、文档、数据、业务分析等工作场景。
- not_work_related：明显私人事务（如私人信件、娱乐创作、闲聊、与岗位无关的个人事项）。
- uncertain：无法明确判断，或信息不足。
不要评价内容好坏，不要复述正文，不做道德judgment。只输出 JSON。
```

**输出契约**：
```json
{ "signal": "not_work_related", "confidence": 0.78, "reason_tag": "personal_writing" }
```
- 强制 JSON；解析失败/超时/`confidence < 0.7`（比 3.2/3.3 的 0.6 更高，更保守）→ `uncertain`。
- 只取结构化字段，`reason_tag` 是短标签供审计，**不作为对个人的呈现文案**。

### 3.3 层2 产出（只是线索，不改结论天花板）

| 字段 | 用途 |
| --- | --- |
| content_signal | work_related / not_work_related / uncertain |
| content_confidence | 排序/呈现用 |
| —— | 结论仍是 `pending_review`，层2 只影响**核查优先级**，不影响是否命中 |

## 4. 合成：两层如何影响「待核查」（关键，与 3.2/3.3 不同）

3.2/3.3：元数据 AND 语义 → 可**升定性**。
**3.6：两层都只服务「待核查」，语义只排优先级，不定罪。**

| 层1 时间窗 | 层2 内容语义 | 结论 | 核查优先级 |
| --- | --- | --- | --- |
| 命中(>20%) | not_work_related | `待核查` | **高**（时间+内容双线索） |
| 命中(>20%) | uncertain / 未读到 | `待核查` | 中（仅时间线索） |
| 命中(>20%) | work_related | `待核查` | **低**（内容像工作，很可能是加班，提示负责人「可能误报」） |
| 未命中(≤20%) | 任何 | 不进 3.6 | — |

要点：
- **层2 判 work_related 不会取消命中**（时间窗已命中就要核查），但会**明确提示「内容像工作，疑似加班误报」**，帮负责人快速排除——这正是防误伤。
- **层2 判 not_work_related 也不认定违纪**，只是把这条排到核查队列前面。
- 语义单独（层1 未命中）永远不进 3.6。

## 5. 待核查状态机 + 负责人确认 + 申诉

```
[层1命中] → pending_review（待核查）
   │
   ├─ 负责人确认「正常/加班/已备案」 → confirmed_ok（关闭，回写为备案候选）
   ├─ 负责人确认「需进一步核查」     → need_check（升级）
   ├─ 被指向个人申诉「这是工作/已报备」 → appeal → 负责人复核
   └─ 负责人判「误报」               → false_positive（关闭 + 喂回规则调阈值）
```

- 状态存 `anomaly_review`（user_id, period, unrelated_cost, ratio, content_signal, status, reviewer, ts）。
- 每次状态变更有审计轨迹（谁、何时、改成什么）。
- `confirmed_ok`「加班/跨时区/值班」可一键沉淀为 `offhours_filing`，下次自动排除（越查越准）。

## 6. 报告呈现（措辞是红线，只作线索不作定罪）

### 6.1 部门/工作室报告置顶块（v0.6 要求）

```
⚠ 待核查（严重异常）
张三 · 无关消耗 ¥1,050 · 占个人成本 21.4% · 主要时段 01:00–04:00 · 模型 GPT-X · Key xxxx
  核查线索：该时段内容更像「私人写作」（置信 0.78，仅供参考，非认定）
  已排除：跨时区、发布值班、已备案批处理
  状态：待核查   [ 确认正常/加班 ] [ 需核查 ] [ 误报 ]   被指向人可申诉
```

- 文案只出现「待核查」「核查线索」「仅供参考，非认定」，**绝不出现「违规/私用/滥用」**。
- 内容线索用「更像 XX（置信 X）」，明确标非认定；work_related 时显示「内容像工作，疑似加班误报」。

### 6.2 个人报告

- 放基础数据之后、用法分析之前（v0.6 §5.1）。
- 对本人措辞更中性：「本周有 ¥1,050（21.4%）消耗发生在非工作时段且未备案，已提交负责人核查，如属加班/已报备可申诉。」

## 7. 合规与审计（比 3.2/3.3 更严）

- **权限最小**：读正文判用途只在离线 job（服务身份）跑，判定结果只对该用户的直属负责人 + 本人可见，不对同级/横向暴露。
- **脱敏加强**：意图指纹去 PII（同 v2 §3.6），且 `reason_tag` 不落细节，只落粗分类。
- **不落正文副本**：内存用完即弃。
- **审计必留**：谁在何时因何判为待核查、大模型 model/version、负责人处置轨迹、申诉记录。
- **总开关**：层2（内容语义）单独开关，默认关；关闭时 3.6 只用层1 时间窗出待核查，仍可用。
- **偏差监控**：定期抽查 false_positive 率，过高则调阈值/关层2。

---

## 8. 成本控制

- 层1 免费（元数据）。
- 层2 只对「层1 命中用户的那批消耗」读内容判一次 → 命中者通常极少（>20% 无关占比本就罕见），调用量远小于 3.2/3.3。
- 缓存：同一用户同期同内容判过不重判。
- 用 GLM5.3-flash 量化版 + 意图指纹（非全文）→ 单次极小。

## 9. 落地顺序

| 步 | 内容 | 依赖 |
| --- | --- | --- |
| A1 | 层1 时间窗判定（SQL + >20% + 排除备案占位） | 无 |
| A2 | 待核查状态机 + 负责人确认 + 申诉 + 审计 | 迁移 anomaly_review |
| A3 | offhours_filing 备案表 + 一键沉淀 | 迁移 + 录入流程 |
| A4 | 报告置顶呈现（部门/工作室/个人） | A1 + 渲染层 |
| B1 | 合规评审通过（层2 前置） | 非技术 |
| B2 | 层2 内容读取 + 意图抽取（复用 v2 §3） | B1 + call_traces |
| B3 | GLM5.3-flash 判工作/非工作（JSON + 置信0.7 + 降级） | B2 |
| B4 | 合成核查优先级（§4）+ 呈现线索文案 | B3 + A4 |
| B5 | 层2 总开关 + false_positive 监控 | B4 |

> A 系列（时间窗）不读正文、不需合规、可先上，产出「待核查」已满足 v0.6 主口径。B 系列（内容语义）是增强，过合规后再上；未上线时层1 兜底。

## 10. 对 v0.6 §3.6 的守约校验

| v0.6 §3.6 | 落点 |
| --- | --- |
| 看：无关消耗 ÷ 个人总成本 | 层1 unrelated_ratio |
| 占比 > 20% | 层1 SQL 阈值 |
| 报告置顶，写金额/占比/时段/模型/Key | §6.1 呈现块 |
| 口径需可计算（凌晨未备案/非工作场景） | 层1 时间窗（凌晨未备案）+ 层2 内容语义（非工作场景） |
| Token 只给线索，不认定违纪，标待核查 | §0 红线 + §4 结论天花板永为待核查 |
| 由负责人确认 | §5 状态机 + 确认 |
| 排除已备案夜间批处理/跨时区/值班 | §2.2 offhours_filing |
| 必须在部门/工作室报告出现 | §6.1 置顶块 |

> 与其他五类的根本区别：3.2/3.3 大模型可把疑似**升定性**；3.6 大模型只把待核查**排优先级/防误伤**，结论永远停在「待核查」，由人终裁。
