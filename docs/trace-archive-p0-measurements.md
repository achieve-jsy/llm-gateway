## 2. pglz 的真实效果（推翻设计文档前提）

**正确分母是"有正文的行数"，不是总行数。**

```
存量 TOAST / 有正文行数 = 285,444,734,976 / 1,259,124 = 226,700 B/行   （jsonb + pglz）
同一批行的 jsonb 文本   = 188,534 B/行（2026-09-19 抽样 2,380 行，448,712,125 B）
```

**结论：存量 226,700 B/行 > 原文 188,534 B/行，比值 0.83x（存量反而是原文的 1.20 倍）。**

即 **pglz 对这类正文几乎没有净收益**——jsonb 二进制结构的开销（键重复、逐元素头部）吃掉了 pglz 的压缩量。
这与 `trace-archive-compression-design.md:146`「179 GB 是 pglz 压缩后，原始约 400~500 GB」的推测**方向相反**：原文比存量更小。

**这反而使归档方案更有价值**：不是"再压一次已压缩数据"，而是"把几乎未压缩的正文真正压下去"。

## 3. codec 实测（生产语料 440 MiB / 2,355 行）

| codec | 压缩后(B) | 压缩率 |
|---|---|---|
| gzip -6（**原设计**） | 133,078,040 | **3.47x** |
| gzip -9 | 132,078,971 | 3.49x |
| zstd -3 | 87,258,968 | 5.28x |
| zstd -19 | 52,615,718 | 8.76x |
| zstd -19 --long=25 | 39,120,599 | 11.79x |
| zstd -19 --long=27 | 25,501,999 | 18.08x |
| zstd -22 --long=27 | 25,501,999 | 18.08x |
| **zstd -22 --ultra** | **23,511,965** | **19.61x** |
| xz -6 | 50,632,812 | 9.11x |

- `-22 --ultra` **已默认使用 128 MB 窗口（windowLog=27）**，再叠 `--long=27` 零增益（字节数完全相同），且 `-22 --long=27` 反而**更差**（18.08x < 19.61x）。**勿叠加 `--long`。**
- `-19 --long=27` 与 `-22 --long=27` 结果**逐字节相同** → 大窗口模式下级别不再是主导变量。
- **压缩率随文件增大而提升**：同 codec 在 35.5 MB 上 10.90x，在 440 MiB 上 19.61x（窗口可跨越更多行）。
  真实全天文件（~20.8 GB jsonl）应 **≥ 19.61x**；容量估算以此下界为保守值。

## 4. 纯 Go 实现可行性（关键）

原设计的"纯 Go 点读"隐含依赖 `klauspost/compress/zstd`。实测其能力边界：

```
EncoderLevelFromZstd(19) = best
EncoderLevelFromZstd(22) = best      ← 库中 19/22 都退化到自身 best，不存在 CLI 的 -19/-22 档
```

### 4.1 同机同文件对比（真实生产样本 35,571,655 B）

| 实现 | 压缩率 | 耗时 | 吞吐 |
|---|---|---|---|
| CLI gzip -6 | 3.46x | 0.83s | 40.6 MB/s |
| Go `SpeedBestCompression` | 8.46x | 0.46s | ~74 MB/s |
| **Go `Best + WithWindowSize(128MB)`** | **9.57x** | **0.47s** | **~72 MB/s** |
| CLI zstd -19 | 9.40x | 4.50s | 7.5 MB/s |
| CLI zstd -22 --ultra | 10.90x | 5.64s | 6.0 MB/s |

**Go 库以约 1/10 的耗时取得比 CLI `-19` 更好的压缩率**，仅比 CLI `-22` 低 12%。

### 4.2 窗口是决定性参数

同一输入（142 MB）：

| 配置 | 压缩率 |
|---|---|
| Go `Best`（默认窗口） | 8.81x |
| **Go `Best + WithWindowSize(128MB)`** | **37.90x** |
| CLI `-22 --ultra` | 43.41x |

**不加 `WithWindowSize` 收益塌 4.3 倍且不报任何错。** 这是必须写进代码的硬约束。

### 4.3 解码器

Go 库**默认参数**成功解码 CLI 产出的 128 MB 窗口大帧（`n=142286620, err=nil`）→ **无需 `WithDecoderMaxWindow`**；建议仍显式设置以防上游改用更大窗口。

### 4.4 结论

采用 `klauspost/compress/zstd` + `WithEncoderLevel(SpeedBestCompression)` + **`WithWindowSize(128<<20)`**：
压缩率 ≈ CLI `-22` 的 **87~88%**，比 gzip 好 **2.8 倍**，吞吐仅降约 1.8 倍，且免外部二进制依赖。

## 5. 点读时延：真实瓶颈

归档文件（440 MiB jsonl / 25.5 MB 压缩）点读实测：

```
[首] 0.00s      [中] 0.34s      [尾] 0.62s     ← 与 rid 在文件中的位置成线性
```

线性原因：**两段式必须从头解压扫描**（zstd 帧不可随机寻址）。
按整天规模外推（2026-09-19 = 116,891 行 / 样本 2,355 行，×49.6）：

| 位置 | 整天外推 |
|---|---|
| 文件头 | ~0 s |
| 中位 | **~17 s** |
| 尾部（最坏） | **~31 s** |

忙日（18.2 万行）最坏可达 **~48 s**，对 trace 详情页不可接受。

**修正方案（必须做）**：按固定大小**分块独立压缩**（如 256 MB 未压缩/块）+ **每日 rid → 块 索引**。
jsonl 已按 `request_id` 排序，索引可二分查找。实测解压吞吐 **1047 MB/s** → 256 MB 块点读 ≈ **0.24 s**，比整天扫描快 **60~130 倍**。
分块同时解决回填并行化。

## 6. 吞吐、回填与夜间批处理

生产机（8 核，`nice -19 ionice -c3`）实测：

| 操作 | 吞吐 |
|---|---|
| zstd -22 --ultra 压缩 | **3.4 MB/s** |
| zstd -19 --long=25 压缩 | 3.1 MB/s |
| gzip -6 压缩 | 22.0 MB/s |
| zstd 解压 | **1047 MB/s** |

Go 编码器按 §4 的约 10 倍优势折算（生产机约为 Mac 的 0.57 倍 → **估计 ~40 MB/s，待服务端复核**）：

| 场景 | CLI -22 | **纯 Go（估）** |
|---|---|---|
| 单日归档（20.8 GB jsonl） | 1.7 h | **~9 min** |
| 回填现存 11 天（~230 GB jsonl） | ~19 h | **~2 h** |

→ 夜间窗口充裕；回填一次即可完成（**不存在"110 天慢慢补"的问题，因为 6/7/8 月正文已不存在**）。

## 7. 容量重算（替换 §12）

**每行口径**（有正文的行）：

```
存量（jsonb+pglz）  226,700 B/行
jsonb 文本          188,534 B/行
jsonl（+键名/转义） 205,879 B/行   （文本 × 1.092）
归档（Go 保守 9.57x）  21,513 B/行
归档（Go 现实 17.2x）  11,970 B/行   （＝0.878 × CLI-22 的 19.61x）
```

| 项 | 数值 |
|---|---|
| **存量归档**（126 万行） | 保守 **25 GiB** / 现实 **14 GiB**（对比现状 **266 GiB**，缩减 **10~19 倍**） |
| **月增**（3.04 万行/天 × 30） | 保守 **59 GiB** / 现实 **34 GiB** |
| 若误用 gzip（3.47x） | 存量归档 **~236 GiB** ⇒ **几乎零收益** |
| `/datalog` 余量 | 368 GiB ⇒ 归档后约 **6~10 个月**（含存量） |

> ⚠️ 原设计 `max_disk_gb=0`（不限）且**没有归档保留策略** → 按此增速会在 6~10 个月内填满 `/datalog`，必须补保留/轮转策略。

**热窗口容量（决定 /data 能否真省）**

```
每行存量 226,700 B × 101,195 行/天 = 21.4 GiB/天
/data 可用 54 GiB ⇒ 仅能容纳约 2.5 天正文
现存保留窗口 = 11 天 ≈ 236 GiB
```

- 现设计 `hot_window_days = 30` → PG 需保留 30 × 21.4 = **642 GiB**，**/data 完全不可能**。
- 要真正释放 /data，热窗口必须**小于当前的 11 天**：
  - 7 天 → 存量约 150 GiB（较现状省 ~116 GiB）
  - 3 天 → 存量约 64 GiB（较现状省 ~202 GiB）
- 但回收需 `pg_repack`/`VACUUM FULL`，且需等量临时空间（见 §8）。

## 8. ⚠️ 生产风险：/data 约 2.5~5 天写满

实测（60 秒精确对账）：

```
TOAST +8,175,616 B / 60s  = 10.96 GiB/天（/data 同步 +8,445,952 B = 11.33 GiB/天）
流量突发时段另一次 3 分钟测量为 22.92 GiB/天
⇒ 实际区间 11 ~ 23 GiB/天
```

`/data` 可用 **54 GiB** ⇒ **约 2.5 ~ 5 天写满**，届时 PostgreSQL 写入将失败。

**未发现任何自动清理**：

- `crontab -l`（root）为空
- `/etc/cron.d` 仅有 `docker-prune`、`e2scrub_all`
- 未找到任何 `call_traces` blank/null/leakscan 相关计划任务或脚本
- 控制面容器未注入清理/归档相关环境变量

⇒ 06/07/08 月正文的置空是 **leakscan 一次性人工处置**，此后正文只进不出。

**这是本报告最高优先级项**：无论归档方案何时落地，都需要立即处置（恢复滚动置空，或先扩 /data）。

## 10. 磁盘回收（定稿文档缺失章节）

`nullifyOldVerified` 仅执行 `UPDATE ... SET body=NULL`：

- **逻辑上**：TOAST 页变为死元组，新正文可复用该空间（这也是为何本次实测 df 增长与 TOAST 逻辑增长基本同步——新插入在扩展关系）
- **物理上**：文件**不会缩小**，`df` 不会下降

要真正把 266 GiB 还给操作系统，需其一：

| 方案 | 锁 | 需临时空间 | 备注 |
|---|---|---|---|
| `pg_repack -t call_traces --jobs 4` | 仅短时排他（切换瞬间） | ≈ 表大小（~266 GiB） | 首选；可用 `--tablespace` 把工作表放 `/datalog` |
| `VACUUM FULL call_traces` | **全程 ACCESS EXCLUSIVE** | ≈ 266 GiB | 需停机窗口 |

`/data` 仅剩 54 GiB ⇒ **临时空间必须落在 `/datalog`**（368 GiB 可用），否则无法执行。
`pg_repack` 在 TOAST 表上的 `--tablespace` 行为需实测确认。
