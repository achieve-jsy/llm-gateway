## 1. 版本主题

> **OTLP + Langfuse 落地**：调用 Trace 全量入 Langfuse，可追溯、可审计；TTFT / 延迟 / 报错率 / 缓存命中率通过 Prometheus + Grafana 监控；全员能直观看到「该用哪个模型」。

## 2. 目标

- 完整落地 PRD 核心价值 ⑤：可观测
- 让网关「可观测后端」与「核心业务」**彻底解耦**（OTLP 标准协议，后端可换）
- 为 V0.7 的多决策负载策略提供数据基础（必须先有指标才能用指标决策）
- 让试点部门的反馈有数据支撑，准备 RC 阶段全员灰度

## 3. 范围（in-scope）

### 后端 — OTLP 出口完整化

- [ ] V0.1 的 OTLP exporter 骨架升级为完整 Trace 出口：
  - 完整 span 链：`HTTP 入口 → 鉴权 → 限流检查 → 路由决策 → 上游 HTTP 调用 → 流式块`
  - LLM 专属属性（遵循 Langfuse GenAI 语义约定）：
    `gen_ai.system` / `gen_ai.request.model` / `gen_ai.response.model`
    `gen_ai.usage.prompt_tokens` / `completion_tokens` / `total_tokens`
    `gen_ai.user.id` / `dept_id` / `key_id` / `model_group`
    `cached` / `cost.usd` / `ttft_ms`
  - Span event：流式首块到达（用于 TTFT）/ 限流命中 / 熔断 / 降级
- [ ] **Prompt 脱敏策略**（在 exporter 拦截层做，可按用户 / 部门 / 模型差异化配置）：
  - `none`：完全不记录 Prompt / Completion
  - `truncate`：保留前 N 字符
  - `redact`：正则脱敏（手机号 / 身份证 / 邮箱 / 公司专有名词）
  - `full`：完整记录（默认仅对内部测试 Key 开启）
- [ ] OTLP exporter 降级：collector 不可达时本地 ring buffer 缓冲 + 恢复后补发；连续失败超阈值打告警**但不阻塞业务**

### 后端 — Prometheus 指标

- [ ] `/metrics` 暴露：
  - `gateway_requests_total{provider, model, status}`
  - `gateway_request_duration_seconds{provider, model}`（histogram）
  - `gateway_ttft_seconds{provider, model}`（histogram）
  - `gateway_concurrent_requests{model_group}`
  - `gateway_ratelimit_rejects_total{type}`
  - `gateway_cache_hits_total / gateway_cache_misses_total`
  - `gateway_otlp_export_failures_total`（自监控 OTLP 出口）

### 后端 — KV 缓存

- [ ] 简易 KV 缓存（基于 Redis）：
  - 命中条件：相同 Prompt（hash）+ 相同 model + 非 stream（V1.x 再做 stream 缓存）
  - 命中后 OTLP span 上打 `cached=true`，同步累加 Prometheus 命中率指标
  - 可配置 TTL（默认 1h）与是否启用（全局 / 按模型）

### 后端 — 健康看板数据源

> 不依赖 Langfuse 查询 API（避免业务 UI 对可观测后端形成硬耦合），网关进程内维护**滚动指标**给前端直接读。

- [ ] 进程内 1 分钟 / 5 分钟 / 1 小时滚动窗口指标（per provider × model）：
  - 请求数、错误率、TTFT P50/P95、延迟 P50/P95、缓存命中率
- [ ] 暴露 `GET /api/v1/admin/models/health`：返回上述滚动指标快照
- [ ] 单次调用详情：返回 Langfuse 的 trace URL（基于 `trace_id`），由前端跳转外链查看完整 Trace

### 前端

- [ ] 「模型健康看板」（全员可见）：
  - 每个模型 / 厂商的实时延迟 / TTFT P50 / P95 / 报错率
  - 1h / 24h 趋势图（数据源：网关 `/health` 接口 + Prometheus）
  - 不同模型对比视图
- [ ] 「我的调用记录」页：
  - 列表来自 Postgres `usage_daily` 明细补充表（按日 + 时间倒序，仅展示元数据：时间 / 模型 / Token / 成本 / 状态）
  - **「查看完整 Trace」按钮 → 跳转 Langfuse**（外链，带 trace_id）
- [ ] Prompt 脱敏策略配置页（管理员）：按全局 / 部门 / 用户 / 模型粒度配置

### 运维

- [ ] `docker-compose.yml` 加入：
  - Prometheus + Grafana（业务指标）
  - **Langfuse v3+**（OTLP 默认后端，自带 ClickHouse + Postgres，由 Langfuse 自己管，与网关无关）
  - OpenTelemetry Collector（可选，作为汇聚层）
- [ ] 默认 Grafana 仪表盘配置随仓库分发（数据源仅 Prometheus，不引入 ClickHouse 依赖）
- [ ] 日志保留策略：在 Langfuse 端配置（不在网关代码内）

## 6. 验收标准

- [ ] 任何员工登录后能看到「模型健康看板」并对各模型当前可用度有直观判断
- [ ] 完成一次调用，10s 内能在 Langfuse 看到该调用完整 Trace（含上下游 span / Token / TTFT / 缓存标记）
- [ ] 「我的调用记录」页能列出本人调用，点击「查看 Trace」能正确跳转到 Langfuse 对应记录
- [ ] 缓存命中率指标在缓存启用后可见且 > 0%（用同一 Prompt 重复调用验证）
- [ ] Grafana 至少 1 个开箱即用的仪表盘（含请求数 / TTFT / 错误率 / 缓存 / OTLP 出口健康度）
- [ ] 网关日志、OTLP span、Langfuse 记录可通过 `trace_id` / `request_id` 三方关联
- [ ] Prompt 脱敏开关生效（4 档策略均能验证）；脱敏配置后 Langfuse 中不出现原文
- [ ] **OTLP collector 停服 30 分钟后恢复，期间业务请求不受影响，恢复后 buffer 内数据补发成功**

## 7. 依赖与风险

| 项 | 类型 | 说明 | 缓解 |
| :--- | :--- | :--- | :--- |
| Prometheus + Grafana 资源 | 依赖 | 内存 / 磁盘开销 | docker-compose 起步够用，远期接公司监控平台 |
| Langfuse 自部署运维 | 依赖 | Langfuse 自带 PG + ClickHouse | 起步单实例 docker-compose；正式环境与运维 / 数据团队对齐资源 |
| Langfuse 与 OTLP 语义兼容性 | 风险 | Langfuse 对 OpenTelemetry GenAI 语义约定的解析口径可能与上游不一致 | 选定 Langfuse v3+ 固定版本；落地前用样例 trace 端到端验证 |
| OTLP 出口反压影响业务 | 风险 | exporter 队列满时阻塞 | 异步 + drop-on-full 策略；自监控 `gateway_otlp_export_failures_total` |
| 缓存数据一致性 | 风险 | 模型升级后缓存失效 | TTL + 模型版本作为缓存 key 的一部分 |
| 脱敏策略合规 | 风险 | 法务 / 安全可能有要求 | 与公司安全团队对齐策略；4 档可配 |
| **里程碑 M4** | 里程碑 | 本版本完成 → 启动全员灰度 | 准备灰度公告 |
