# Feature Specification: 模型自动恢复 (Model Auto Recovery)

**Feature Branch**: `001-model-auto-recovery`

**Created**: 2026-06-10

**Status**: Draft

**Input**: 当前的模型会自动检测可用性，当不可用的时候会关闭这个模型，但是没有模型可用自动恢复的机制，现在需要增加这个功能，免去人工的手动开启的步骤

## 背景与现状分析

### 现有机制

1. **模型健康检测**（控制面 `runBackgroundModelCheck`）：
   - 定期探测 `enabled=true` 的模型
   - 连续失败达阈值（默认 3 次）后调用 `AutoDisableModel()` 自动禁用该模型
   - **问题**：模型被禁用后 `enabled=false`，检测逻辑直接跳过（`if !*m.Enabled { continue }`）

2. **网关调度器**（`HealthStore.FilterHealthy`）：
   - 运行时根据模型健康状态过滤，只路由到健康模型

### 现有问题

- 模型被自动禁用后，检测逻辑跳过它，导致即使上游恢复正常也无法被检测到
- 模型恢复需要人工手动在管理界面重新启用
- 缺乏模型状态变更的历史记录，难以追溯

### 期望的新机制

```
模型健康检测（持续探测所有模型，包括被自动禁用的）
              ↓
    单个模型状态判断
              ↓
  ┌─────────────────────────────────────┐
  │ 连续失败达阈值 → 自动禁用该模型     │
  │ 被禁用模型检测恢复 → 自动启用该模型 │
  └─────────────────────────────────────┘
              ↓
    模型组轮询（只选健康的模型）
              ↓
       模型状态变更日志（记录启用/禁用的原因和时间）
```

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 被禁用模型自动恢复 (Priority: P1)

作为运维人员，当某个模型因连续健康检测失败被自动禁用后，我希望系统能继续探测该模型的可用性，并在模型恢复正常后自动重新启用，这样我无需手动干预即可恢复服务。

**Why this priority**: 这是核心功能，直接解决用户痛点——避免模型恢复后仍处于禁用状态，需要人工介入才能恢复流量。

**Independent Test**: 可以通过模拟模型故障→自动禁用→模型恢复→自动启用的完整流程来独立测试。

**Acceptance Scenarios**:

1. **Given** 一个模型因连续 3 次健康检测失败被自动禁用，**When** 系统继续执行健康检测且该模型连续 2 次检测成功，**Then** 系统自动将模型重新启用并记录恢复日志。

2. **Given** 一个被自动禁用的模型，**When** 健康检测仍然失败，**Then** 模型保持禁用状态，系统不做任何变更。

3. **Given** 一个被手动禁用的模型（用户在管理界面关闭），**When** 系统执行健康检测，**Then** 系统跳过该模型，不尝试自动恢复（尊重用户的手动操作）。

4. **Given** 一个被自动禁用的模型，**When** 系统执行健康检测，**Then** 该模型仍然被检测（不跳过）。

---

### User Story 2 - 模型状态变更日志看板 (Priority: P2)

作为运维人员，我希望能够在管理界面看到模型状态变更的完整历史，包括什么时间、因为什么原因导致模型被禁用或启用，以便追踪和排查问题。

**Why this priority**: 提供可观测性，帮助运维人员理解系统自动行为的原因。

**Independent Test**: 可以通过触发模型状态变更后检查日志看板的展示来独立测试。

**Acceptance Scenarios**:

1. **Given** 一个模型因连续检测失败被自动禁用，**When** 运维人员查看模型状态变更日志，**Then** 能看到一条"自动禁用"记录，包含：
   - 变更时间
   - 变更类型：自动禁用
   - 触发原因：连续 N 次检测失败
   - 最近的错误信息

2. **Given** 一个模型因检测恢复健康被自动启用，**When** 运维人员查看模型状态变更日志，**Then** 能看到一条"自动恢复"记录，包含：
   - 变更时间
   - 变更类型：自动恢复
   - 触发原因：连续 N 次检测成功

3. **Given** 管理员手动禁用或启用一个模型，**When** 查看模型状态变更日志，**Then** 能看到一条"手动操作"记录，包含操作人信息。

4. **Given** 运维人员在模型管理页面，**When** 点击某个模型的"状态历史"按钮或查看日志看板，**Then** 能看到该模型的所有状态变更记录（时间倒序）。

---

### Edge Cases

- **手动禁用 vs 自动禁用**：系统需要区分这两种状态，只对自动禁用的模型尝试自动恢复。
- **模型恢复后立即再次故障**：应正常触发自动禁用流程，无特殊处理。
- **多个模型同时被禁用**：检测应能并发处理多个模型，不阻塞。
- **检测超时**：检测超时视为失败，计入连续失败次数。
- **恢复成功后的保护期**：恢复后应重置失败计数，避免立即因历史失败再次被禁用。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 模型健康检测 MUST 持续探测所有"自动禁用"状态的模型，不跳过。
- **FR-002**: 模型健康检测 MUST 跳过"手动禁用"状态的模型（尊重用户操作）。
- **FR-003**: 系统 MUST 在被自动禁用的模型连续检测成功达到阈值（默认 2 次）后自动启用该模型。
- **FR-004**: 系统 MUST 在模型被自动恢复后重置其连续失败计数为 0。
- **FR-005**: 系统 MUST 区分模型的"手动禁用"和"自动禁用"状态。
- **FR-006**: 系统 MUST 记录每次模型状态变更的详细日志，包含时间、类型、原因。
- **FR-007**: 管理界面 MUST 提供模型状态变更日志的查看功能。
- **FR-008**: 自动恢复所需的连续成功次数阈值 SHOULD 可配置（默认 2 次）。

### Key Entities

- **Model（模型）**：
  - `enabled`: 是否启用
  - `status`: 状态标识（需确认：0=正常, 3=自动禁用，或使用其他方式区分）
  - `consecutive_failures`: 连续失败次数
  - `consecutive_recovery_successes`: 连续恢复成功次数（新增，用于恢复判断）

- **ModelStatusLog（模型状态变更日志）**：新增实体
  - `model_id`: 模型 ID
  - `model_name`: 模型名称
  - `provider_id`: 所属渠道 ID
  - `provider_name`: 所属渠道名称
  - `change_type`: 变更类型（auto_disabled, auto_recovered, manual_disabled, manual_enabled）
  - `reason`: 变更原因描述
  - `error_message`: 错误信息（禁用时）
  - `operator_id`: 操作人 ID（手动操作时）
  - `created_at`: 变更时间

- **HealthCheckConfig（健康检测配置）**：
  - `recovery_success_threshold`: 恢复所需连续成功次数（新增，默认 2）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 被自动禁用的模型在上游恢复正常后，95% 的情况下能在 2 个检测周期内自动恢复。
- **SC-002**: 自动恢复功能上线后，因"忘记手动恢复模型"导致的运维工单减少 90%。
- **SC-003**: 运维人员能在 30 秒内通过状态变更日志定位到模型禁用的根本原因。
- **SC-004**: 手动禁用的模型不会被系统自动恢复，准确率 100%。

## Assumptions

- 模型表需要新增字段或复用现有字段来区分"手动禁用"和"自动禁用"状态。
- 恢复检测使用与健康检测相同的探测方式，无需额外探测逻辑。
- 自动恢复功能默认启用，以提供开箱即用的体验。
- 恢复成功阈值（默认 2 次）低于禁用阈值（默认 3 次），以在保守与敏捷之间取得平衡。
- Provider（供应商渠道）不参与自动禁用/启用逻辑，保持用户手动控制。
