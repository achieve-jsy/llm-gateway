# 需求规格说明书 · 模型性能看板 · 002

> 状态：需求草稿 · 待评审
> 需求方：运维 / 产品
> 优先级：P2（现有可用性监控已稳定，性能数据可观测性为增强项）
> 关联：001-model-auto-recovery（已规划）、health-monitor 对齐修复（已上线）

---

## 1. 一句话描述

在现有运维控制台新增"模型性能看板"页面，基于真实 API 请求数据（`call_logs`），让用户看到"模型组是否好用"的性能维度，与现有可用性监控互补。

---

## 2. 背景与问题

### 现状

运维控制台目前有两类健康监控：

- **模型健康监控**（`/admin/health-monitor`）：每个"模型 + 渠道端点"的健康时间条
- **模型组健康监控**（`/admin/group-health-monitor`）：每个模型组的健康时间条

两者都基于定时探针（`health_check_logs`），探测间隔约 30s-60s，结果是 pass/fail 二分状态。

### 痛点

1. **探针全绿 ≠ 真的好用**：上游限流、长 context 延迟、缓存命中率低、429 频发，探针感知不到
2. **性能维度缺失**：用户不知道"当前这个模型组平均响应要多久"
3. **failover 感知缺失**：背后某个渠道挂了，failover 已经生效，但前端无任何表现
4. **模型组是用户视角**：用户调用 `claude-sonnet-4-6` 时不知道背后是 deepseek-v4-pro，性能差异无处可看

### 数据基础

`call_logs` 表已实时记录以下字段，可直接消费，无需新增埋点：

- 请求耗时：`duration_ms`、`first_token_ms`
- 阶段耗时：`stage_auth_ms`、`stage_route_ms`、`stage_upstream_ms`、`stage_ttfb_ms`
- 状态码：`status`（HTTP）、`upstream_status`
- 路由信息：`group_name`、`model`、`routed_model`、`provider`
- failover：`failover_used`

## 3. 目标与成功标准

### 主要目标

| # | 目标 | 衡量方式 |
|---|------|----------|
| G1 | 运维能看到"模型组现在好不好用" | 进入页面 1 秒内看到核心指标 |
| G2 | 运维能从模型组下钻到具体后端模型 | 点击展开看流量占比与性能 |
| G3 | 数据实时可信 | 10-60s 内刷新（MVP 阶段） |
| G4 | 不引入主观阈值干扰判断 | 用百分位 + 基线对比，不画红绿灯 |

### 成功标准

- 上线两周后，运维反馈："现在排查慢响应问题不用去查日志了"
- 不再出现"探针绿着但用户说慢"的误判场景

## 4. 用户与场景

### 目标用户

| 用户 | 主要使用 Tab | 主要关心 |
|------|-------------|---------|
| 普通 API 用户 | 模型组视角 | "我用的 `middle-level` 现在快不快" |
| 产品 | 模型组视角 | "claude 替换组最近表现如何" |
| 运维 / SRE | 两个 Tab | "是网关问题还是上游问题；哪个后端模型拖后腿" |
| 研发 | 模型视角 | "deepseek-v4-flash 最近 P95 有没有升高" |

### 典型场景

1. **日常巡检**：运维每天早会看一遍所有主力模型组的成功率与延迟
2. **故障定位**：用户反馈"模型变慢"，运维进页面看 P50/P95 + failover 次数 + 组内模型流量占比
3. **性能评估**：产品想知道"claude 替换组的响应时间比原始 claude 慢多少"，对比不同组
4. **容量评估**：看到高峰期 P95 明显飙升，考虑增加渠道 / 调整策略

## 5. 页面结构

### 新增路由

`/admin/performance`（独立页面，与 `/admin/health-monitor`、`/admin/group-health-monitor` 并列在侧边栏）

### 顶部控件

- **Tab 切换**：模型组视角 / 模型视角（默认模型组视角）
- **时间窗口**：1h（默认）/ 6h / 24h
- **搜索框**：模糊匹配名称
- **刷新按钮**：手动刷新

### 主体内容：卡片网格

每个卡片包含：

| 区域 | 内容 |
|------|------|
| 卡片头 | 名称、路由策略、模型数量（仅组）、时间窗口 |
| 概要行 | 请求量 · 成功率 · failover 次数 |
| 总延迟 | P50 + P95 + "处于 24h Px 水平" 标注 |
| 首 Token | P50 + P95 |
| 可折叠明细 | 组内模型流量占比、各自 P50/P95/成功率 |

## 6. 设计原则

### 原则 1：不定阈值，用百分位对比

不同模型天生速度不同，**不应一刀切定义"P95 > X 毫秒算异常"**。

实现方式：把当前窗口的 P50 与过去 24h 各小时 P50 分布做对比，得出"当前处于 24h 的 Pxx 水平"。

| 显示 | 含义 | 用户理解 |
|------|------|----------|
| 处于 24h 的 P15 水平 | 比平时更快 | "模型今天很给力" |
| 处于 24h 的 P60 水平 | 正常波动 | "还行" |
| 处于 24h 的 P92 水平 | 明显偏慢 | "要查一下" |

### 原则 2：让运维自己判断，不画红绿灯

UI 上不主动标注"健康/警告/异常"状态灯。显示原始数值 + 百分位，让运维基于自己的经验判断。

### 原则 3：数据源与既有页面互补，不替代

| 页面 | 数据源 | 解决什么 |
|------|--------|---------|
| 现有健康监控 | `health_check_logs` 探针 | 可用性（在线/离线） |
| **性能看板** | `call_logs` 真实请求 | **性能（好不好用）** |

两者**都保留**。性能看板可在卡片顶部放一个极简"在线/离线"状态点，与可用性监控交叉参照。

### 原则 4：以真实请求为基础

仅计算 `routed_via_group=true` 的真实请求（组视角），不包含探针、预热、健康检查产生的流量。模型视角可包含全部 `model` 字段的请求。

## 7. 两个 Tab 的视角差异

### Tab 1：模型组视角（默认）

- 分组维度：`group_name`
- 每个卡片：一个模型组
- 信息：组内模型数量、路由策略、总延迟、TTFT、failover、组内明细（可折叠）
- 默认用户：普通 API 用户、产品

### Tab 2：模型视角

- 分组维度：`model` + `provider`（渠道）
- 每个卡片：一个后端真实模型
- 信息：被 N 个组使用、P50/P95、TTFT、成功率、被哪些组使用
- 默认用户：运维、研发

> 模型视角需要标注"被 N 个组使用"，例如 `deepseek-v4-pro` 同时被 claude-sonnet-4-6、claude-opus-4-5、middle-level 等共用。

## 9. 非功能需求

### 性能

- 1h 聚合查询 < 500ms（数据量 < 100 万行）
- 百分位基线查询（24h）< 2s（首次慢，可缓存 1 分钟）
- 页面首屏 < 1.5s

### 兼容

- 与现有 `admin` 路由体系一致
- 权限：**所有登录用户可见**（参考 `/admin/group-health-monitor` 的权限级别）

### 可观测

- 卡片"无数据"状态要有空状态提示，不显示空白
- 百分位基线不足（24h 数据缺失）时，"处于 Px 水平" 标注隐藏，不显示误导信息

## 10. 不做的事（明确排除）

- ❌ 不替代现有的健康监控页面
- ❌ 不引入计费成本视图（另一条线）
- ❌ 不下发告警推送（后续告警系统）
- ❌ 不定义健康阈值和红黄灯
- ❌ 不下钻到 `call_traces` 慢请求详情（后续版本）
- ❌ 不做多个模型组并排对比视图（v2 候选）

## 11. MVP 范围

**MVP 目标**：能用，能看清主要指标，不做高级交互。

### 做（MVP）

| 项 | 描述 |
|---|------|
| ✅ 后端 `GET /api/v1/health/performance` 接口 | 支持 `window`、`view`、`search` 参数 |
| ✅ 前端 `/admin/performance` 页面 | 卡片布局 + 双 Tab |
| ✅ 时间窗口切换（1h/6h/24h） | |
| ✅ 组内模型折叠明细 | |
| ✅ 名称搜索 + 请求数排序 | |
| ✅ 60s 短轮询刷新 | |
| ✅ "处于 24h 的 Px 水平" 百分位指标 | |

### 不做（MVP）

| 项 | 原因 |
|---|------|
| ❌ WebSocket 实时推送 | 复杂度高，短轮询可接受 |
| ❌ 点击卡片查看 24h 趋势图 | v2 再做 |
| ❌ 慢请求日志下钻 | v3 再做 |
| ❌ 错误码分布饼图 | v2 再做 |
| ❌ 多组对比视图 | v2 再做 |

## 12. 待产品确认的开放问题

1. **权限级别**：是否所有登录用户可见？（建议：是，参考 `group-health-monitor`）
2. **空数据的组是否显示**：过去 1h 无请求的模型组是否出现在列表里？（建议：默认不显示，加"显示全部"开关）
3. **是否需要默认选中某个模型组**？无默认，全量平铺显示
4. **MVP 是否需要"百分位基线"指标**？（这是本需求的核心差异点，建议 MVP 就做）
5. **是否复用现有 `HealthTimeline` 组件做交叉显示**？（MVP 不做，v2 考虑）

## 13. 验收标准

| # | 场景 | 验收 |
|---|------|------|
| AC-1 | 运维访问 `/admin/performance` | 1 秒内看到 1h 内请求量最多的模型组，卡片信息完整 |
| AC-2 | 切换 6h / 24h | 数据在 3 秒内刷新，P50/P95 数值随之变化 |
| AC-3 | 搜索 "middle" | 仅显示匹配的模型组 |

| AC-7 | 1h 内无请求的模型组 | 不出现在列表里 |
| AC-8 | 模型组视角卡片数量与 `/admin/group-health-monitor` 基本一致 | 验证 `routed_via_group=true` 过滤正确 |

## 附录

### 术语表

| 术语 | 含义 |
|------|------|
| P50 / P95 / P99 | 分位数，反映延迟分布。P50 即中位数 |
| TTFT（Time To First Token） | 首 token 延迟，流式响应体感速度关键指标 |
| failover | 路由策略在主模型失败时切换到备选 |
| 模型组（group） | 对外暴露的"模型名"，内部可含多个 backend 模型 |
| 模型（model） | 真实后端模型 + 渠道 |
| routed_via_group | `call_logs` 字段，标记请求是否经过组路由 |
