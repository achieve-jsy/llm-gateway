**发起时间**：2026-05-23

---

## 1. 原始需求

> 增加 API Key 管理，包括 SSO 登录、Key CRUD、鉴权中间件、/v1/me/models 接口

---

## 2. 发散想法

### 功能方向

| 编号 | 想法 | 一句话描述 | 值得深入？ |
| :--- | :--- | :--- | :--- |
| F1 | SSO（OIDC）登录 | 员工用公司账号登录平台，SSO 回调写入用户/部门数据 | ⭐ |
| F2 | Key CRUD | 员工自助创建（sk-前缀、明文仅返回一次）、列表脱敏、禁用/启用/删除 | ⭐ |
| F3 | API Key 鉴权中间件 | 替换 V0.1 硬编码 token，调用时鉴权链路 API Key → User → 部门 | ⭐ |
| F4 | /v1/me/models 专属查询 | 基于身份返回当前用户可用的模型列表 | ⭐ |
| F5 | Key 重新生成功能 | 在现有 Key ID 上生成新密钥替换旧密钥 | —（v0.2.0 不纳入，删旧建新即可） |

### 用户场景

- **场景 1**：全公司员工 用公司账号登录平台后 想要自助创建 Key 以便 调用大模型并追溯身份
- **场景 2**：业务开发团队 用 Key 调用网关 想要 请求自动通过鉴权中间件识别身份 以便 无需硬编码 token

### 参考案例

| 产品/功能 | 可借鉴的点 | 与我们的差异 |
| :--- | :--- | :--- |
| OpenAI API Key 管理 | 创建时明文仅返回一次、列表脱敏、sk-前缀 | OpenAI 无组织维度绑定，我们有部门归属 |
| LiteLLM Key 管理 | Key 与 user_id 绑定 | LiteLLM 是我们要替换的方案 |

### 技术可能性

- OIDC 标准协议对接公司 SSO，回调后写入 users + departments 表
- JWT RS256 签发用于管理后台，sk-前缀 Key 用于 API 调用鉴权
- 鉴权中间件在 gateway-api 请求入口拦截，解析 Key → 查 user → 查部门

### 开放问题

- Key 明文安全策略：创建时明文仅返回一次，不提供重新生成（需换就删旧建新）
- SSO 联调可能阻塞：IT 排期不可控，开发模式保留账号密码回退

## 3. 初步聚焦

### 推荐深入的方向

1. **SSO + Key CRUD + 鉴权 + /v1/me/models 全闭环**：v0.2.0 版本规划已明确，完成"身份→Key→调用追溯"最小闭环
2. **Key 明文仅返回一次 + 不提供重新生成**：采纳业界标准做法，降低复杂度

### 建议排除的方向

- **Key 重新生成**：v0.2.0 不纳入，删旧建新足以满足当前需求
- **模型组、限流、用量统计、部门权限、复杂角色权限**：v0.2.0 out-of-scope
