## 2. 发散想法

### 功能方向

| 编号 | 想法 | 一句话描述 | 值得深入？ |
| :--- | :--- | :--- | :--- |
| F1 | 调用埋点 | 每次 LLM 请求异步记录模型/Token/耗时/状态/Key/部门维度 | ⭐ |

### 用户场景

- **场景 1**：管理员在后台查看全公司模型调用成本总览，按部门/模型/时间维度下钻分析
- **场景 2**：员工在自服务页面查看自己名下 Key 的调用量和预估费用
- **场景 3**：部门负责人查看本部门（含下级子部门）的模型调用成本排名和趋势

### 参考案例

| 产品/功能 | 可借鉴的点 | 与我们的差异 |
| :--- | :--- | :--- |
| OpenAI Dashboard Usage | 按 API Key 和日期拆分的用量图表、Token 趋势、成本计算 | 我们需叠加部门维度、支持 CSV/Excel 导出 |
| Langfuse cost tracking | 自定义定价模型、usage_details 细粒度（cached_tokens）、历史成本锁定 | 我们自研，不引入 ClickHouse，Go 原生集成 |

### 技术可能性

- **自研方案**（推荐）：gateway-api 异步写入埋点 → Redis 队列 → Worker 批量写入 PG → 物化视图/预聚合表 → 查询接口
- **Langfuse 方案**（不推荐）：无 Go SDK、需引入 ClickHouse+S3、部门维度不原生支持、违反宪章自主可控原则

### 开放问题

- 实时查询 vs 离线预聚合的权衡（万级 QPS 场景下 PG 聚合查询的性能边界）
- 流式调用中 Token 数是逐步产生的，成本是在调用结束时一次性计算还是过程中累加
