## 2. 内联课题（浅研究）

### [01]：Langfuse vs 自研方案对比

**问题**：LLM Gateway 的调用埋点、用量汇总、成本追踪能力，应该集成 Langfuse 还是自建？

**约束**：宪章「自主可控」——不形成对单一外部方案的不可替代依赖；组织感知——部门维度治理；Go 技术栈。

**备选方案**：

| 维度 | 方案 A：Langfuse 自部署 | 方案 B：自研 PG 表 + Redis 队列 |
| :--- | :--- | :--- |
| **Go SDK** | ❌ 无官方 Go SDK，仅 Python/JS/TS；Go 须走 OTel 端点 + REST API，无原生类型安全 | ✅ 完全 Go 原生，零语言适配成本 |
| **组织维度** | ❌ RBAC 为 Org/Project/Role 模型，无原生部门层级；dept_id 仅能以 tag 形式传入，需外层代理过滤 | ✅ 直接按 dept_id、studio_id 维度建模，原生支持管理员全局/员工自己/部门负责人三种视角 |
| **成本计算** | ⚠️ 支持自定义模型定价和多级定价阶梯，成本在写入时计算并锁定（定价变更不回溯历史）。符合「历史不重算」需求 | ✅ 自定义 pricing 表 + 快照机制，完全可控历史成本锁定策略 |
| **部署复杂度** | ❌ 6 个组件：Web + Worker + PG + ClickHouse + Redis + S3/MinIO。ClickHouse 为硬依赖。与当前 PG+Redis 栈仅部分重叠 | ✅ 复用现有 PG + Redis，零新增基础设施 |
| **可替换性** | ⚠️ 数据存于 ClickHouse + PG，OpenTelemetry 标准格式降低部分迁移难度，但仍需 ClickHouse→PG ETL，迁移成本中等 | ✅ 数据完全自控，格式自由定义 |
| **权限模型** | ❌ Project 级 RBAC 无法原生支持「同一 Project 内按部门数据隔离」；需外部代理层实现用户→部门→数据过滤 | ✅ 自建 user→dept 映射 + 查询条件注入 |
| **写入性能** | ✅ Redis 队列 → S3 → Worker → ClickHouse，良好的削峰和批量写入能力 | ✅ Redis 队列 → Worker → PG 批量 INSERT，适合日均万级调用量，瓶颈在 PG 聚合查询需索引优化 |

**结论**：**强烈推荐自研方案**。

关键理由：
1. **致命缺陷**：Langfuse 无 Go SDK，Go 栈通过 OTel+REST 接入得不偿失
2. **核心需求不匹配**：部门维度的成本归集和「管理员全局/员工自己/部门负责人」三级消费视角，Langfuse 需大量 hack 才能实现，有违「先跑通主链路」的渐进原则
3. **基础设施负担**：引入 ClickHouse + S3 仅为了埋点和用量汇总，ROI 极低。自研 PG 聚合查询对日均万级调用量完全够用
4. **自主可控**：Langfuse 部署后形成新的不可替代依赖，与宪章原则五直接冲突

**前提假设**：
- 日均调用量 ≤ 10 万级（初期按万级预估），PG 聚合查询通过索引和物化视图完全胜任
- 不需要 LLM Trace 的可视化调试能力（Trace Viewer 等），仅需结构化指标
- 成本计算逻辑为 `用量 × 单价 = 估算成本`，不涉及 Tokenizer 级精度
