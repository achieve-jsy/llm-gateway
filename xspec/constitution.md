## 核心原则

### 原则一：单一入口

本项目必须作为公司内模型调用的统一入口，对业务方提供稳定的 OpenAI 兼容接入方式，以最低迁移成本逐步替换现有 LiteLLM 方案。

**约束条件**：
- 面向业务方的主调用入口必须统一收敛到 OpenAI 兼容协议，不得并行演化出多个长期共存的业务接入协议。
- 新能力上线不得要求业务方因网关内部实现变化而批量改造 SDK、调用模式或模型接入路径。
- 任何会削弱 LiteLLM 替换可行性的设计，不得进入主版本范围。

### 原则二：组织感知

网关不是通用代理，而是贴合公司真实组织关系的治理基础设施。身份、Key、权限、模型可见性与限额策略必须围绕公司组织架构展开。

**约束条件**：
- 访问身份、Key 归属、部门权限、模型可见性和限额策略必须能够映射到公司真实组织关系，不得脱离组织维度独立设计。
- 任何治理能力若无法落实到员工、部门或角色等组织主体上，不得视为完成。
- 不得引入绕开组织身份和权限体系的长期例外通道。

### 原则三：渐进演进

项目按版本渐进交付，遵循"先跑通主链路，再补治理能力，最后完成全量替换"的路径，不以一次性铺满能力为目标。

**约束条件**：
- 每个版本只承载与当前阶段目标直接相关的能力，未进入当期主题的事项默认延后。
- 不得为了表面完整性在早期版本引入明显超出阶段目标的复杂能力。
- 若新增需求不能明确归属当前版本阶段目标，则不得进入当前主版本范围。

### 原则四：核心聚焦

项目聚焦统一模型接入、治理、观测与成本控制，不扩展为 Prompt 平台、Agent 平台、向量数据库平台或工作流平台。

**约束条件**：
- 新需求若与统一模型网关无直接关系，默认视为范围外。
- 不得以"顺手支持"为由将 Prompt 管理、Agent 编排、RAG/向量库托管、训练微调、工作流等泛平台能力纳入主线建设。
- 任何版本范围都必须能直接映射到"接入、治理、观测、成本控制"中的至少一类核心职责。
- 成本控制须覆盖调用埋点、用量汇总、模型定价与成本估算的完整链路，不得仅做单一环节。

### 原则五：自主可控

项目必须保留对国产厂商适配和公司内部治理诉求的快速响应能力，逐步形成可维护、可替换、可扩展的自有网关能力。

**约束条件**：
- 架构演进不得形成对单一上游社区方案或单一厂商能力的不可替代性依赖。
- 任何关键能力若只能依赖外部闭源能力实现，默认不视为长期可接受方案。
- 涉及国产厂商适配或公司专属治理需求时，不得因上游限制而放弃项目核心目标。

### 原则六：可验证交付

每个版本都必须具备清晰范围、验收标准、风险识别和状态管理，确保能力可测试、可演示、可回顾。

**约束条件**：
- 任何能力进入版本前，必须能说明其版本归属、验收方式和风险点。
- 任何版本交付都不得以"功能已写完但无法验证"作为完成标准。
- 未建立状态管理、范围边界和回顾依据的事项，不得作为正式版本承诺。

### 原则七：分层抽象

所有 AI 模型统一按照智力等级标准化分层，业务层无感知底层模型差异，实现模型能力标准化、可度量、可替换。

**约束条件**：
- 任何新接入模型必须归入既定智力等级分层体系，不得绕过等级定义直接暴露给业务方。
- 业务方调用时不得依赖具体模型名称或厂商标识，必须通过等级抽象或别名进行。
- 模型替换（同等级内切换）不得要求业务方修改任何调用逻辑。

### 原则八：智能路由

基于场景、模型等级、渠道状态、负载情况自动匹配最优模型渠道，支持多维度混合调度。

**约束条件**：
- 路由决策必须综合考虑模型等级、渠道健康状态、当前负载三个维度，不得仅依赖单一维度。
- 新增调度策略不得破坏已有路由规则的确定性（相同输入 → 相同输出）。
- 路由逻辑必须对业务方透明，业务方不得感知底层渠道选择细节。

### 原则九：高可用容错

全覆盖健康检查机制，秒级故障感知、自动降级、无缝切换，杜绝模型调用单点故障。

**约束条件**：
- 每个模型等级必须至少配置一个降级路径，不得存在无降级方案的模型调用链路。
- 健康检查覆盖所有活跃渠道，故障检测到切换完成必须在秒级窗口内闭环。
- 降级或切换过程不得向业务方抛出底层故障细节，必须以统一错误码或静默切换处理。

### 原则十：负载最优

内置多套负载均衡策略，动态分配调用流量，平衡各模型、各渠道算力压力，提升整体吞吐与响应速度。

**约束条件**：
- 必须至少提供轮询、加权、最少连接数中的两种负载均衡策略。
- 负载策略变更不得导致在途请求中断或丢失。
- 单渠道负载超阈值时必须自动触发流量转移，不得等待人工干预。

### 原则十一：可观测可管控

统一模型列表管理，全量记录模型状态、调用指标、故障日志、用量与成本数据，支持可视化运维与动态配置。

**约束条件**：
- 所有模型调用必须产出结构化指标（模型、渠道、延迟、Token 用量、状态码、调用 Key、部门维度），不得存在无日志的调用路径。
- 调用指标必须支持按天汇总用量（usage_daily），预留 dept_id 与 studio_id 维度。
- 模型列表、渠道配置的变更必须支持热更新，不得要求重启服务。
- 故障事件必须可回溯到具体渠道和时间窗口，不得出现不可追溯的调用失败记录。
- 模型必须配置输入/输出单价，用量数据须能按单价换算为估算成本，并提供按 Key 和时间的基础查询接口。

## 范围与边界

- 系统聚焦 AI 模型调用的统一调度底座，通过模型智力等级抽象分层，结合多渠道负载均衡、实时健康探测、全自动故障切换，为 Agent 开发、智能对话、代码自主开发、业务推理等上层场景提供标准化接入。
- 主版本范围内的能力，必须至少直接支撑以下核心价值之一：安全自助、数据透明、高可用、极简接入、可观测、业务解耦、成本可控、分层抽象、智能路由、负载均衡。
- 不能映射到上述核心价值之一的事项，不得进入主版本范围。
- 项目不承载与"统一模型网关"无直接关系的泛平台能力（Prompt 管理、Agent 编排、RAG/向量库托管、训练微调、工作流等）。
- 项目不在早期版本引入与阶段目标无关的后台复杂度。
