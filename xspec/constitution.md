## 核心原则

### 原则一：不开倒车（回归防护）

每次变更不能破坏已有功能。测试用例是功能的契约，新增功能必须同步建立测试基线。

**约束条件**：
- 每个变更必须附带覆盖其影响面的测试用例（新增或已有）
- 合入前必须全量通过 `make test` + 前端 `vitest run`
- 修改现有接口行为时，必须先确认该接口的契约测试存在且通过
- 禁止删除或跳过已有测试来"解决"测试失败

### 原则二：服务稳定（零破坏性变更）

作为公司 AI 基座，稳定性是第一优先级。对外接口和内部协议不允许 breaking change。

**约束条件**：
- 对外 `/v1/*` 接口保持向后兼容，不允许 breaking change
- 配置变更必须支持热加载，不得要求重启才能生效
- 新功能通过新增字段/端点实现，不修改已有字段语义
- provider snapshot 格式变更必须做前后兼容处理

### 原则三：服务快速（低延迟）

网关不能成为性能瓶颈，转发延迟必须尽可能低。

**约束条件**：
- 请求热路径（鉴权→调度→转发）禁止引入同步 IO 阻塞或重量级计算
- 缓存优先：鉴权结果、配置数据走本地缓存，避免每次请求远程调用
- 流式响应必须逐 chunk 转发，禁止缓冲完整响应后再发
- 新增中间件/拦截器必须评估对 P99 延迟的影响

### 原则四：架构清晰（简洁优先）

保持双服务架构的清晰边界，不增加不必要的复杂度。

**约束条件**：
- gateway 不直连数据库，配置只走 Redis snapshot / 控制面内部 API
- 新增组件/服务需说明为何现有架构无法满足
- 单一职责：每个 package 只做一件事，禁止 God Object / 万能 service
- 依赖方向单向：gateway → Redis/控制面内部API，控制面 → Postgres/Redis

### 原则五：交互至上（用户体验友好）

管理后台和 API 设计以用户直觉为导向。

**约束条件**：
- 管理面操作必须有即时反馈（loading / success / error 状态）
- API 错误响应必须包含可操作的信息（错误码 + 人可读描述 + 修复建议）
- 配置项采用合理默认值，用户"零配置"即可跑通基本场景
- 新功能的 UI 入口和操作路径必须直观，不超过 3 步完成核心操作

## 技术方向

| 领域 | 选择 | 说明 |
| :--- | :--- | :--- |
| 后端语言 | Go 1.26 + Gin | 高性能、低延迟，适合网关场景 |
| 前端 | Vue 3 + Element Plus + Vite + Tailwind | 管理面 SPA |
| 数据库 | PostgreSQL（控制面）+ Redis（缓存/配置同步） | gateway 不直连 PG |
| 认证 | JWT + OIDC + API Key | 双层缓存（本地 5s + Redis 15s） |
| 可观测性 | OpenTelemetry (OTLP trace) | 全链路追踪 |
| 部署 | Docker Compose + nginx 反代 | 双服务分流 |
| 测试 | Go test + Vitest + Playwright E2E | contract / integration / 前端单元 / E2E |

## 治理

- 本宪章是项目的最高准则，所有需求设计、技术方案和代码实现必须遵守
- 宪章修订需通过 `/xf/constitution` 命令执行，记录修订原因
- 修订采用语义化版本：MAJOR（原则重大变更）、MINOR（新增板块）、PATCH（措辞修正）
- 与宪章冲突的设计/实现必须先修订宪章或获得明确豁免
