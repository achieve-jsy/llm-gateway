## 2. 问题背景与约束条件（必填）

**为什么需要做这个决策？**

auth 模块使用 RS256 签发 JWT（Access Token 30min / Refresh Token 7d）。私钥由 auth 保管签发，公钥通过 `/auth/public-key` 端点分发给 gateway-api、ops-console 等验证方。当私钥需要轮换（安全合规要求、疑似泄露等场景）时，已签发的旧 JWT 仍在有效期内，若验证方只持有新公钥，这些旧 JWT 将无法验证——导致用户被迫重新登录，影响服务可用性。

**硬约束（不可违反）：**

- 必须使用 RS256 签名（HLD §4 技术选型已确定），不得改为 HS256
- 验证方（gateway-api、ops-console）不持有私钥，只能通过公钥验证
- 已签发的 JWT 在其声明有效期内必须能被正常验证，不得因密钥轮换而提前失效
- JWT 签发与验证的库必须使用项目已引入的 `golang-jwt/jwt/v5`（go.mod 已有 v5.2.1）

**软约束（有偏好）：**

- 优先选 OpenID Connect 标准兼容的方案 → 对应 §5「标准兼容性」维度
- 优先选实现复杂度低、可快速落地的方案 → 对应 §5「实现复杂度」维度
- 优先选对现有 HLD 设计改动最小的方案 → 对应 §5「设计冲击」维度

**不在本次研究范围内：**

- 密钥自动轮换策略（何时触发轮换）——属于运维流程，不影响验证逻辑设计
- HSM / KMS 密钥托管方案——属于密钥存储层面，不影响验证逻辑设计
- JWT 加密（JWE）——本项目 JWT 仅签名不加密

## 3. 前提假设（必填）

- 预计密钥轮换频率极低（每年 ≤ 2 次），不需要自动化轮换流水线
- Access Token 有效期 30min、Refresh Token 有效期 7d，轮换过渡窗口需覆盖最长的 Refresh Token 生命周期
- 验证方（gateway-api、ops-console）与 auth 模块共享同一 Redis 实例和内部网络
- SSO 联调期间可能有少量测试 JWT 需兼容，但量级极低

## 4. 候选方案（必填）

| 方案 | 简介 | 版本 / 来源 |
| :--- | :--- | :--- |
| **A：JWKS 端点 + kid 匹配** | auth 提供 `/.well-known/jwks.json` 端点，返回 JSON Web Key Set（含多个公钥，每个带 `kid` 标识）。签发时 JWT header 注入 `kid`，验证方从 JWKS 按 `kid` 匹配对应公钥验证。轮换时新旧公钥并存于 JWKS，过期后移除旧公钥。 | OpenID Connect Core §9 / RFC 7517 |
| **B：双公钥顺序尝试验证** | auth `/auth/public-key` 端点返回当前公钥。验证方 Keyfunc 依次尝试当前公钥 → 旧公钥验证。轮换过渡期内旧公钥通过配置注入验证方。过渡期结束后仅保留当前公钥。 | golang-jwt/jwt/v5 Keyfunc 多密钥模式 |
| **C：JWT header 不变 + 轮换后强制重新登录** | 密钥轮换时直接替换私钥，验证方同步替换公钥。旧 JWT 因签名不匹配全部失效，用户被迫重新 SSO 登录。过渡窗口 = 0。 | 最简方案，无额外实现 |

**未纳入评估的方案（违反硬约束或明显不适用）：**

| 方案 | 排除原因 |
| :--- | :--- |
| HS256 对称签名 + 共享密钥 | 违反硬约束：HLD 已确定 RS256，且密钥需分发给多个模块，对称密钥泄漏风险更高 |
| JWT 签名后再加密（JWE） | 不在研究范围，且过度复杂 |

## 6. 方案对比矩阵（必填）

| 维度（权重） | A：JWKS + kid | B：双公钥顺序尝试 | C：强制重新登录 |
| :--- | :---: | :---: | :---: |
| 标准兼容性（30%） | 5 | 3 | 1 |
| 实现复杂度（25%） | 4 | 3 | 5 |
| 设计冲击（20%） | 3 | 4 | 5 |
| 运维可操作性（15%） | 4 | 2 | 1 |
| 用户体验影响（10%） | 5 | 4 | 1 |
| **加权总分（满分 5.0）** | **4.20** | **3.15** | **3.00** |

**评分依据（按维度说明）：**

- **标准兼容性**：A：JWKS 是 OpenID Connect 标准端点，`kid` 是 RFC 7515 标准 JWT header 字段，与 SSO/OIDC 系统天然兼容；B：顺序尝试验证不是标准做法，依赖自定义 Keyfunc；C：无标准兼容性考量，仅为粗暴替换
- **实现复杂度**：A：auth 需新增 JWKS 端点和 kid 管理，验证方需改为 JWKS 拉取 + kid 匹配，但 golang-jwt/v5 原生支持 JWKS 验证模式；B：验证方 Keyfunc 需管理两份公钥和优先级，配置管理更复杂；C：最简实现，零额外代码
- **设计冲击**：A：需新增 `/.well-known/jwks.json` 端点，JWT 签发需注入 `kid` header，HLD 中 `/auth/public-key` 端点需改为 JWKS 格式；B：HLD 中端点不变，但验证方配置需支持双公钥注入；C：零冲击
- **运维可操作性**：A：轮换步骤明确：生成新密钥 → 新 kid 加入 JWKS → 等待过渡期 → 移除旧 kid；B：轮换需手动向多个验证方分发旧公钥配置，步骤多且容易遗漏；C：轮换即断服，运维风险极高
- **用户体验影响**：A：轮换期间用户无感知，旧 JWT 正常验证直到自然过期；B：轮换期间旧 JWT 可验证，但需验证方正确配置旧公钥；C：所有用户被迫重新登录，7 天内所有 Refresh Token 失效

## 7. 深度分析（适用时填）

### 关键差异：JWKS 端点对 HLD 设计的冲击

方案 A 的 JWKS 端点需要对 HLD 做以下调整：

1. **端点变更**：HLD §5.2 中的 `/auth/public-key` 端点改为 `/.well-known/jwks.json`（或同时保留两个端点，public-key 返回当前活跃公钥，JWKS 返回全量公钥集）
2. **JWT 签发逻辑**：`TokenService.SignAccessToken()` 需在 JWT header 中注入 `kid` 字段，标识使用哪个私钥签发
3. **验证方适配**：gateway-api 的 `JWTAuthMiddleware` 从 JWKS 端点获取公钥集，按 JWT header 中的 `kid` 匹配验证密钥；ops-console 前端同理
4. **密钥配置管理**：auth 需支持多私钥配置（当前活跃私钥 + 过渡期内旧私钥并存），环境变量从单个 `RSA_PRIVATE_KEY` 改为 `RSA_PRIVATE_KEYS`（JSON 或多行 PEM）

**方案 A 优势**：
- JWKS 是 OpenID Connect Discovery 标准组件，`/.well-known/jwks.json` 端点与 OIDC 服务天然配套
- `kid` 字段让验证方精确匹配密钥，无需"顺序尝试"的低效和不确定性
- golang-jwt/v5 的 `jwt.Keyfunc` 可直接从 JWKS JSON 构建 kid → 公钥映射
- 过渡窗口管理仅需在 JWKS 中增删条目，运维步骤清晰

**方案 A 风险**：
- JWKS 端点引入了新的外部依赖面——验证方需定期拉取 JWKS，若 auth 不可用则验证方缓存兜底
- `kid` 注入需要签发逻辑改动，但改动量很小（jwt.NewWithClaims 之前设置 header kid 字段）

### JWKS 端点缓存策略补充

验证方（gateway-api、ops-console）拉取 JWKS 的策略：
- **启动时加载**：服务启动时从 auth JWKS 端点拉取全量公钥集，缓存在内存
- **定时刷新**：每 300s 重新拉取 JWKS（与 Key 缓存 TTL 一致），确保新密钥及时生效
- **签名验证失败时刷新**：若 JWT 的 `kid` 在本地缓存中未找到，立即重新拉取 JWKS 再验证（防止因缓存延迟导致合法 JWT 误拒）
- **兜底机制**：若 auth 不可用，使用上次成功拉取的缓存继续验证（内存常驻）

## 8. 最终结论（必填）

**选择方案**：A — JWKS 端点 + kid 匹配

**核心理由**：
- JWKS + kid 是 OpenID Connect 标准做法，与 auth 模块 OIDC 服务定位天然匹配，长期兼容性最优
- kid 匹配验证比顺序尝试更精确高效，验证方无需管理"哪个优先"的逻辑
- 过渡窗口运维步骤清晰（增删 JWKS 条目），避免手动分发公钥配置的遗漏风险

**被否决方案的关键原因**：

| 方案 | 否决原因 |
| :--- | :--- |
| B：双公钥顺序尝试 | 非标准做法；需向多个验证方手动分发旧公钥配置，运维步骤多易遗漏；顺序尝试验证效率低（每个旧 JWT 需两次签名验证） |
| C：强制重新登录 | 用户体验极差（7 天内所有 Refresh Token 失效）；运维风险高（轮换 = 全量断服）；违反宪章"可验证交付"原则中服务可用性要求 |
