## 1. 业务背景与系统目标

* **业务背景**：当前项目需要形成公司统一的大模型调用入口，但接入能力仍停留在产品规划层，尚未明确统一入口在强兼容场景下应承担的业务行为边界。若没有一份清晰的统一接入需求规范，后续实现容易把主链路、模型选择、流式兼容和错误语义混写，导致替换 LiteLLM 的路径失焦。
* **核心目标**：定义统一接入强兼容主链路的业务需求，使业务开发团队能够通过统一入口完成模型选择、普通调用和流式调用，并在失败时获得一致、可理解的错误反馈，为后续逐步替换 LiteLLM 建立可验证的接入基线。

## 2. 关键概念

> 统一术语定义，后续所有章节直接引用此处概念名，避免歧义。

- **统一入口**：业务方唯一使用的模型调用入口，对外保持稳定兼容的调用方式。
- **模型选择**：业务方在发起调用时指定要使用的模型能力标识，由统一入口决定如何承接本次调用。
- **兼容调用**：在统一入口下完成的普通返回或流式返回调用体验，要求行为语义一致、可预期。
- **错误语义**：统一入口在调用失败时向调用方表达的失败类型与可理解结果，用于区分输入问题、模型不可用和临时失败等不同情形。

### 6.1 统一兼容调用入口

**A. 功能说明**

统一入口必须承接业务方的模型调用请求，并向调用方暴露一致的兼容调用体验。业务方应只关心“我要调用哪个模型能力、是否需要流式返回、得到什么结果”，而不需要感知底层承接差异。该功能是替换 LiteLLM 的主链路基础。

**B. 数据实体与关系**

- 调用请求：描述业务方本次调用意图的业务载体。
- 调用结果：描述统一入口最终向业务方返回的可消费结果。
- 失败结果：描述统一入口在调用失败时返回的可理解失败语义。

**C. 接口概要**

| 接口 | 方法 | 路径 | 说明 |
| :--- | :--- | :--- | :--- |
| 统一兼容调用 | POST | /v1/chat/completions | 承接普通调用和流式调用请求 |

**D. 业务规则与校验**

- 统一入口必须以稳定兼容的调用方式承接请求，不要求业务方因内部变化改造调用模式。
- 统一入口必须能够区分普通响应与流式响应两类调用体验，并保持结果语义一致。
- 当调用无法受理或执行失败时，必须向业务方返回可理解、可区分的失败结果。

**E. 异常与边界**

* **并发处理**：同一时段存在多笔调用时，每笔调用都应独立返回对应结果，不因其他调用存在而混淆响应语义。
* **幂等性**：业务方重复提交同一业务意图时，统一入口至少应保证每次返回结果语义自洽，不产生难以识别的异常状态。
* **超时降级**：当本次调用在合理等待期内无法完成时，统一入口应返回明确失败结果，而不是长时间无反馈。

### 6.2 模型选择与可用性约束

**A. 功能说明**

业务方在统一入口发起调用时，需要明确当前想使用的模型能力。统一入口必须对“可被选择的模型能力”给出稳定承接规则，避免业务方出现“能调用入口但不知道能用什么”的状态。

**B. 数据实体与关系**

- 模型能力标识：业务方在调用时选择的目标模型能力。
- 可用模型集合：当前对该调用主体可受理的模型能力范围。
- 调用主体：发起本次调用的业务侧身份上下文。

**C. 接口概要**

| 接口 | 方法 | 路径 | 说明 |
| :--- | :--- | :--- | :--- |
| 模型列表查询 | GET | /v1/models | 返回当前调用主体可见的模型能力集合 |

**D. 业务规则与校验**

- 调用主体只能在当前可用模型集合内选择模型能力。
- 当业务方选择了不可用模型能力时，统一入口必须直接返回明确失败结果。
- 模型列表查询结果必须与统一入口实际可受理范围保持一致。

**E. 异常与边界**

* **空集合**：当当前调用主体暂无可用模型时，应返回清晰结果，避免业务方误以为入口异常。
* **选择冲突**：当业务方请求中的模型能力不在当前可用范围内时，应立即阻断并返回可理解原因。
* **临时不可用**：当模型能力暂时不可承接时，应向业务方表达“当前不可用”而不是静默失败。

### 6.3 错误语义与兼容体验

**A. 功能说明**

统一入口不仅要在成功时兼容，更要在失败时兼容。业务方需要从失败结果中区分输入错误、模型不可用、临时失败等不同情况，以决定是否修正请求或稍后重试。

**B. 数据实体与关系**

- 输入错误：因请求内容不满足受理条件而产生的失败类型。
- 不可用错误：因当前模型能力不可承接而产生的失败类型。
- 临时失败：因短时异常导致本次调用未完成的失败类型。

**C. 接口概要**

| 接口 | 方法 | 路径 | 说明 |
| :--- | :--- | :--- | :--- |
| 错误结果返回 | POST | /v1/chat/completions | 在统一入口返回一致失败语义 |

**D. 业务规则与校验**

- 输入不合法、模型不可用、临时失败必须在返回结果中有明确可区分语义。
- 业务方不应从失败结果中接收到相互矛盾的提示。
- 同类失败在不同调用模式下应保持一致理解方式。

**E. 异常与边界**

* **输入缺失**：请求缺少必要信息时，应直接返回输入错误结果。
* **流式中断**：流式调用中途失败时，应让业务方明确本次返回已中断且未完成。
* **重复失败**：连续发生同类失败时，返回语义仍应保持一致，避免调用方误判。

## 7. 数据流与外部接口

* **数据导入**：本模块不涉及批量导入。
* **外部 API 对接**：统一入口在业务方发起调用时承接外部模型能力访问，并将结果回传给调用方。
* **消息/事件**：本次需求不要求异步消息驱动流程，统一以一次调用过程内的结果反馈为主。

---

## 8. 非功能需求

* **安全性**：统一入口返回的信息不得泄漏与业务调用无关的敏感内部细节。
* **并发与性能**：同一阶段的试点业务调用应具备稳定、连续的兼容体验，不因调用模式变化导致结果语义失真。
* **可观测性**：每次调用至少应形成可用于后续验证的结果表现，便于人工演示和问题回溯。

## 11. 变更记录 — CHG-20260523-001

### 新增功能：鉴权中间件与身份关联模型查询（版本 v1.1）

#### US-AUTH-01 — API Key 鉴权中间件 (P0)

**作为**业务开发团队，**我想要**通过 API Key 发起的调用自动经过鉴权中间件解析身份，**以便**网关能识别调用者及其所属部门并据此执行访问控制。

**功能说明**：
- 所有 API 调用（模型调用接口、模型列表查询接口、基于当前身份的模型查询接口等）必须在请求处理前经过鉴权中间件
- 鉴权中间件从请求中提取 API Key，依次解析为 User（员工身份）和 Department（部门归属），构成 API Key → User → Department 鉴权链路
- 鉴权成功的请求携带完整的身份上下文进入后续处理环节
- 鉴权失败的请求直接返回明确的失败结果，不进入任何业务处理环节

**异常与边界**：
- 请求未携带 API Key → 返回鉴权缺失错误，明确提示需提供有效的 API Key
- API Key 不存在或格式不合法 → 返回鉴权失败错误，不泄露 Key 是否存在的判断细节
- API Key 已被禁用 → 返回鉴权失败错误，提示该 Key 已不可用

#### US-MODELS-01 — 身份关联的可用模型查询 (P0)

**作为**业务开发团队，**我想要**查询当前认证身份下可用的模型列表，**以便**确认我可以调用哪些模型能力。

**功能说明**：
- 新增基于当前身份的模型查询接口，返回当前认证用户（经鉴权中间件解析后的身份）可用的模型列表
- 模型列表基于用户身份（User → Department）过滤，仅返回该身份有权限访问的模型
- 返回结果与模型调用接口实际可受理范围保持一致，即列表中的模型均可被当前认证用户调用

**异常与边界**：
- 认证用户当前无任何可用模型 → 返回空列表而非错误，明确表达"当前身份暂无可用模型"
- 认证用户所属部门尚未分配任何模型权限 → 同上，返回空列表

## 12. 变更记录 — CHG-20260525-001

## 变更摘要

引入模型组调用入口：业务方调用时传组名替代模型名，gateway-api 解析组名后委托 scheduler 选择组内目标模型，使用选中的模型完成实际调用。调用失败时触发故障切换，请求 scheduler 重新路由至同组其他健康模型。组名不存在或组内无可用模型时返回明确错误。

## 新增需求

### US-GROUP-INVOKE-01 — 组名调用入口 (P0)

**作为**业务开发团队，**我想要**调用时传入模型组名而非具体模型名，**以便**无需关心底层模型和渠道选择即可完成调用。

**功能说明**：
- 业务方调用统一入口时，请求中的模型标识字段传入组名
- gateway-api 解析到组名后，委托 scheduler 进行路由决策，获取同组内的具体目标模型
- gateway-api 使用 scheduler 返回的目标模型（含渠道信息）完成实际调用
- 调用成功后向业务方返回结果，与直接传模型名的行为语义一致

**异常与边界**：
- 传入的组名不存在 → gateway-api 在校验阶段直接返回"模型组不存在"错误，不经过 scheduler
- scheduler 返回该组无可用模型 → gateway-api 向业务方返回"该模型组当前无可用模型，请稍后重试"
- scheduler 不可用（宕机/超时）→ gateway-api 降级为选择组内首个注册模型直连调用

### US-GROUP-INVOKE-02 — 调用失败后自动切换 (P0)

**作为**业务开发团队，**我想要**组内模型调用失败时系统自动切换到其他可用模型，**以便**调用不因单个模型故障而中断。

**功能说明**：
- 使用 scheduler 选中的目标模型调用失败（超时、连接错误、服务端错误），gateway-api 请求 scheduler 进行故障切换
- scheduler 排除已失败的模型，从同组健康模型中重新选择新目标
- gateway-api 使用新目标重试调用，对业务方仅返回最终结果（成功或失败）
- 最多重试一次切换，避免在连续失败的组中陷入无限重试

**异常与边界**：
- 切换后新目标也调用失败 → 向业务方返回调用失败结果，不再继续重试
- 同组内已无其他可用模型 → 向业务方返回"该模型组当前无可用模型"
- 流式调用中途失败 → 流已中断，不切换重试（切换重试仅适用于尚未返回数据的失败场景）

### US-GROUP-INVOKE-03 — 组名调用与鉴权链路兼容 (P1)

**作为**系统，**我想要**组名调用与现有 API Key → User → Department 鉴权链路无缝兼容，**以便**组名调用不绕过身份追溯。

**功能说明**：
- 组名调用经过与模型名调用完全相同的鉴权中间件（API Key → User → Department）
- 调用日志中同时记录请求传入的组名和 scheduler 实际选中的目标模型标识
- 模型组可见性不做权限过滤（本次版本所有组对所有已认证用户可见）

**异常与边界**：
- 未认证的组名调用请求 → 鉴权中间件拦截，与模型名调用行为一致
- 组名调用的可用模型查询 → 返回当前认证用户有权访问的模型组列表，而非具体模型列表

## 变更摘要

将 `/v1/models`（或称 `/v1/me/models`）从返回个体模型列表改为基于 Key 绑定返回模型组名称列表，使模型组成为业务方看到的"模型"概念。组名调用路由链路（US-GROUP-INVOKE-01）已存在，本次重点在模型列表查询的语义变更和 Key 绑定生效逻辑。

## 新增需求

### US-GROUP-MODELS-01 — 基于 Key 绑定的模型组列表查询 (P0)

**作为**业务开发团队，**我想要**通过 API Key 查询可用模型列表时得到的是我 Key 绑定的模型组名称，**以便**只看到我实际可调用的模型组，且不需要感知底层模型。

**功能说明**：
- 调用 `/v1/models`（鉴权后）返回该 Key 绑定且组内存在可用模型的模型组名称列表
- 不返回组内具体模型名称，对调用方而言模型组即是模型
- 返回结果中每个模型组展示：组名称（即 publicName，作为调用时的模型标识）、组是否可用（组内有无可用模型）
- 返回结果格式保持与 OpenAI `/v1/models` 兼容

**异常与边界**：
- Key 未绑定任何模型组 → 返回空列表，不报错
- Key 绑定了某个组但该组内无可用模型 → 该组仍在列表中返回，标注不可用状态
- Key 被禁用 → 鉴权中间件拦截，不进入该接口逻辑

### US-GROUP-MODELS-02 — 以组名调用校验绑定关系 (P0)

**作为**系统，**我想要**在业务方以组名发起调用时校验该组名是否在当前 Key 的绑定范围内，**以便**确保未绑定的组不可被调用。

**功能说明**：
- 业务方以组名发起调用时，gateway-api 先校验该组名是否在当前 Key 绑定的模型组列表中
- 未绑定的组名 → 直接返回"模型组不可用"错误，不经过 scheduler
- 已绑定且组内存在可用模型 → 委托 scheduler 执行组内路由决策
- 组名调用路由和故障切换逻辑沿用 US-GROUP-INVOKE-01 和 US-GROUP-INVOKE-02 已有定义

**异常与边界**：
- 调用方传入的组名存在但不在 Key 绑定范围内 → 返回"模型组不可用"，不泄露该组是否存在的信息
- 调用方传入的组名已在 Key 绑定范围内但该组无可用模型 → 与 US-GROUP-INVOKE-01 行为一致，返回"该模型组当前无可用模型"
- 调用方仍尝试直接传模型名（非组名）→ 对该 Key 有模型组绑定的情况下，应引导使用组名而非直接传模型名 [待确认: 是否允许无组绑定的 Key 按原模型名调用的兼容期]
